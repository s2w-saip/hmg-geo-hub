## Requirements
### Requirement: 세션 기반 인증
애플리케이션은 Supabase Auth로 사용자를 인증하고 서버단 세션(@supabase/ssr)을 유지해야 한다(SHALL).
인증 제공자는 인터페이스 뒤에 격리해 추후 교체(예: 설치형 SSO) 가능해야 하며, scope workspace key는
최종 사용자 인증에 사용되지 않는다.

#### Scenario: 로그인이 세션을 생성함
- **WHEN** 사용자가 유효한 자격 증명으로 Supabase Auth에 로그인하면
- **THEN** 서버단 세션이 생성되고 사용자가 인증된 라우트에 도달할 수 있다

#### Scenario: 세션 없으면 보호 접근 차단
- **WHEN** 유효한 세션 없는 요청이 보호 라우트나 scope API handler에 도달하면
- **THEN** 접근이 거부된다

#### Scenario: 인증 제공자가 격리됨
- **WHEN** 인증 제공자를 교체해야 하면
- **THEN** 인증 인터페이스 구현만 바뀌고 호출 측 코드는 변경되지 않는다

### Requirement: 데이터 범위 계층을 가진 역할 모델
시스템은 각 사용자에게 역할(HQ / 권역 / 국가 / 관리자)을 부여해야 하며(SHALL), 역할과 허용 범위는
`profiles`(사용자가 수정 불가, 서버에서 read)에서 관리되어 브랜드 > 권역 > 국가 > 차종 계층을 따르는
허용 데이터 범위로 매핑되고, 관리자에게는 추가로 관리자 콘솔이 부여된다.

#### Scenario: 역할이 허용 범위로 매핑됨
- **WHEN** 국가 역할 사용자가 로드되면
- **THEN** profiles에서 도출된 허용 범위가 해당 국가(및 하위)로 제한된다

#### Scenario: 사용자가 자신의 역할을 변경할 수 없음
- **WHEN** 클라이언트가 자신의 역할/범위를 바꾸려 시도하면
- **THEN** 역할/범위는 서버 통제 저장소(profiles)에서만 결정되므로 반영되지 않는다

### Requirement: 서버단 범위 강제 필터
hmg-geo 서버는 모든 scope 호출에서 인증 사용자의 역할로 도출한 권역/국가 필터를 서버단에 강제 주입해야 한다(SHALL).
클라가 보낸 location 파라미터는 무시하며, 각 scope 호출에 대해 사용자별 attribution을 기록해야 한다.

#### Scenario: 클라가 보낸 location이 무시됨
- **WHEN** 국가 사용자가 허용 범위 밖의 location 파라미터를 담아 요청하면
- **THEN** 서버는 클라 값을 버리고 역할에서 도출한 필터를 적용한다
- **AND** 응답에는 사용자의 허용 범위 내 데이터만 포함된다

#### Scenario: 사용자별 감사 attribution
- **WHEN** BFF를 통해 scope 호출이 일어나면
- **THEN** 서버는 어떤 인증 사용자가 시작했는지 로그에 남긴다

### Requirement: 역할 기반 라우트 접근 정책
시스템은 인증 뒤 라우트에 대한 역할별 접근 가능 여부를 단일 정책 모듈로 정의해야 하며(SHALL),
서버는 매 요청마다 이 정책을 평가해 비허용 라우트 요청을 차단해야 한다. 정책은 4개 역할
(HQ / 권역 / 국가 / 관리자) × 5개 라우트(통합 대시보드 / 고객 관심 / AI 답변 / 개별 프로젝트 /
관리자 콘솔)를 모두 표현한다. 클라이언트 라우팅만으로 차단하지 않는다.

#### Scenario: 비허용 라우트 URL 직접 입력이 차단됨
- **WHEN** 권역 역할 사용자가 통합 대시보드 라우트 URL을 직접 입력해 접근하면
- **THEN** 서버 가드가 정책으로 차단하고 `/no-access`로 리다이렉트한다

#### Scenario: 관리자 콘솔이 관리자에게만 열림
- **WHEN** HQ·권역·국가 역할 사용자가 관리자 콘솔 라우트에 접근하면
- **THEN** 가드가 차단하고 비허용 경로로 리다이렉트한다
- **AND** 관리자 역할 사용자는 관리자 콘솔에 접근할 수 있다

#### Scenario: 정책이 단일 진실의 원천
- **WHEN** 라우트별 접근을 결정해야 하면
- **THEN** 모든 호출 경로가 동일한 정책 함수를 통과한다(중복 정의 금지)

### Requirement: 역할 기반 네비게이션 가시성
인증 뒤 화면의 네비게이션은 사용자 역할이 접근 가능한 라우트만 렌더해야 한다(SHALL). 가시성은
라우트 접근 정책과 동일한 진실의 원천에서 도출되어, *보이는 것 = 갈 수 있는 것* 이 성립한다.

#### Scenario: 권역 사용자에게 통합 대시보드 메뉴가 보이지 않음
- **WHEN** 권역 역할 사용자가 보호된 레이아웃을 렌더하면
- **THEN** 네비게이션에 통합 대시보드 메뉴 항목이 표시되지 않는다
- **AND** 고객 관심 / AI 답변 / 개별 프로젝트 메뉴는 표시된다

#### Scenario: 국가 사용자에게 어떤 메뉴도 보이지 않음
- **WHEN** 국가 역할 사용자가 보호된 레이아웃을 렌더하면
- **THEN** 네비게이션은 메뉴 항목 0개를 렌더한다(빈 상태)

#### Scenario: 관리자에게만 관리자 콘솔 메뉴가 보임
- **WHEN** 관리자 역할 사용자가 레이아웃을 렌더하면
- **THEN** 관리자 콘솔 메뉴 항목이 추가로 표시된다

### Requirement: 접근 가능 메뉴 부재 사용자의 빈 상태 페이지
시스템은 접근 가능 라우트가 없는 인증 사용자를 위한 빈 상태 페이지를 제공해야 한다(SHALL).
이 페이지는 사용자가 관리자에게 권한을 요청해야 함을 안내하고, 로그아웃 외 액션을 제공하지 않는다.

#### Scenario: 국가 사용자가 로그인하면 빈 상태 페이지로 이동
- **WHEN** 국가 역할 사용자가 로그인을 완료하면
- **THEN** `/no-access` 화면이 렌더되어 접근 가능한 메뉴가 없음을 알린다

#### Scenario: 빈 상태 페이지에서 로그아웃이 가능
- **WHEN** 사용자가 빈 상태 페이지에서 로그아웃을 선택하면
- **THEN** 세션이 종료되고 로그인 라우트로 이동한다

### Requirement: 관리자 사용자 관리 액션의 권한 보호
시스템은 관리자 콘솔의 사용자 관리 액션 진입에서 호출자가 관리자 역할인지 검증해야 한다(SHALL).
액션(사용자 생성·사용자 프로필 갱신·사용자 삭제)은 서버 액션으로 구현되고, 비관리자 호출은
즉시 거부되며, 권한 인증용 자격(Supabase 서비스 키)은 브라우저에 노출되지 않는다. 사용자
프로필 갱신은 역할과 허용 범위를 단일 액션에서 원자적으로 갱신해야 하며, 부분 갱신을
허용하지 않는다. 관리자는 자기 자신을 삭제하거나 자기 자신의 관리자 권한을 강등할 수 없다.
시스템에는 항상 최소 한 명의 관리자가 존재해야 하며, 마지막 관리자를 강등하거나 삭제하는
시도는 거부되어야 한다.

#### Scenario: 비관리자가 사용자 생성 액션을 호출할 수 없음
- **WHEN** 권역·국가 역할 사용자가 사용자 생성 액션을 직접 호출하면
- **THEN** 액션이 권한 검증에서 즉시 실패하고 어떤 효과도 일어나지 않는다

#### Scenario: 관리자가 사용자 생성에 성공
- **WHEN** 관리자가 신규 이메일로 사용자 생성을 요청하면
- **THEN** 인증 사용자 레코드가 즉시 사용 가능 상태(이메일 확인 완료)로 생성되고
- **AND** profiles 레코드가 동일 식별자로 함께 생성되며 기본 역할이 부여된다
- **AND** 임시 비밀번호가 호출자 UI에 1회 표시된다(저장되지 않음)

#### Scenario: 사용자 생성 중 profiles 삽입 실패는 인증 사용자도 롤백
- **WHEN** 인증 사용자 생성 직후 profiles 삽입이 실패하면
- **THEN** 시스템이 방금 생성된 인증 사용자를 삭제 시도해 일관성을 회복한다

#### Scenario: 관리자가 사용자의 역할과 범위를 단일 액션으로 갱신
- **WHEN** 관리자가 특정 사용자의 역할과 허용 범위(브랜드/권역/국가)를 동시에 변경해 저장하면
- **THEN** 시스템은 단일 서버 액션 호출로 profiles 행을 한 번에 patch하고
- **AND** `updatedAt`이 서버에서 갱신되며
- **AND** 부분 저장(일부 필드만 반영되거나 일부만 실패)은 발생하지 않는다

#### Scenario: scopeAll=true 갱신은 세부 범위 필드를 함께 비운다
- **WHEN** 관리자가 사용자 프로필 갱신 시 `scopeAll`을 true로 설정해 저장하면
- **THEN** 서버는 brands/regions/countries를 모두 null로 함께 갱신한다

#### Scenario: 비관리자는 사용자 프로필 갱신 액션을 호출할 수 없음
- **WHEN** 권역·국가·HQ 역할 사용자가 사용자 프로필 갱신 액션을 직접 호출하면
- **THEN** 액션이 권한 검증에서 즉시 실패하고 profiles 행은 변경되지 않는다

#### Scenario: 관리자가 사용자를 삭제하면 auth와 profiles에서 모두 제거된다
- **WHEN** 관리자가 사용자 삭제를 요청하면
- **THEN** 시스템은 profiles 행과 auth.users 레코드를 모두 제거하고
- **AND** 감사 로그가 기록된다

#### Scenario: 관리자가 자기 자신을 삭제하려는 시도는 거부된다
- **WHEN** 관리자가 현재 세션과 동일한 사용자 식별자로 사용자 삭제를 요청하면
- **THEN** 액션이 거부되고 어떤 데이터도 변경되지 않는다

#### Scenario: 관리자가 자기 자신의 관리자 권한을 강등할 수 없다
- **WHEN** 관리자가 자기 자신의 역할을 admin이 아닌 다른 역할로 변경 요청하면
- **THEN** 액션이 거부되고 어떤 데이터도 변경되지 않는다
- **AND** 다른 관리자가 존재하더라도 본 규칙은 동일하게 적용된다

#### Scenario: 시스템에는 항상 최소 한 명의 관리자가 존재해야 한다
- **WHEN** 관리자가 다른 사용자(현재 admin 역할)의 역할을 admin이 아닌 값으로 변경하려 하고, 그 변경이 적용될 경우 시스템에 admin 역할 사용자가 0명이 되면
- **THEN** 액션이 거부되고 어떤 데이터도 변경되지 않는다

#### Scenario: 마지막 관리자는 삭제될 수 없다
- **WHEN** 관리자가 다른 admin 역할 사용자를 삭제하려 하고, 삭제 후 시스템에 admin 역할 사용자가 0명이 되면
- **THEN** 액션이 거부되고 어떤 데이터도 변경되지 않는다

#### Scenario: 비관리자는 사용자 삭제 액션을 호출할 수 없음
- **WHEN** 권역·국가·HQ 역할 사용자가 사용자 삭제 액션을 직접 호출하면
- **THEN** 액션이 권한 검증에서 즉시 실패하고 어떤 데이터도 변경되지 않는다

#### Scenario: 서비스 키가 클라이언트에 노출되지 않음
- **WHEN** 관리자 콘솔이 렌더되거나 액션이 호출되면
- **THEN** 서비스 키는 서버 액션 내부에서만 읽히고 브라우저 번들에 포함되지 않는다

### Requirement: 관리자 콘솔 사용자 목록의 검색
관리자 콘솔의 사용자 목록은 텍스트 검색을 지원해야 한다(SHALL). 검색은 이메일과 역할
표시명(번역된 라벨)을 대상으로 부분 일치하며, 결과가 없을 때 명시적 빈 상태를 보여야 한다.

#### Scenario: 이메일 부분 일치 검색
- **WHEN** 관리자가 검색 입력에 이메일 일부 문자열을 입력하면
- **THEN** 목록은 해당 문자열을 포함하는 이메일을 가진 사용자만 표시한다

#### Scenario: 역할 표시명 부분 일치 검색
- **WHEN** 관리자가 검색 입력에 역할 표시명 일부(예: "권역")를 입력하면
- **THEN** 목록은 해당 역할의 사용자만 표시한다

#### Scenario: 검색 결과 없음의 빈 상태
- **WHEN** 검색어와 일치하는 사용자가 없으면
- **THEN** 목록은 0개 행 대신 명시적 빈 상태 메시지를 표시한다

#### Scenario: 검색어 제거 시 전체 목록 복원
- **WHEN** 관리자가 검색 입력을 비우면
- **THEN** 목록은 모든 사용자를 다시 표시한다

### Requirement: 관리자 콘솔 사용자 편집은 다이얼로그에서 진행된다
사용자 목록의 행은 디스플레이 전용이어야 하며(SHALL), 행 진입 시 다이얼로그를 통해서만
역할과 범위를 편집할 수 있어야 한다. 다이얼로그는 단일 저장 버튼으로 변경을 commit하고,
취소 시 변경이 폐기되며, 변경분이 없을 때는 저장 버튼이 활성화되지 않는다.

#### Scenario: 행 클릭이 편집 다이얼로그를 연다
- **WHEN** 관리자가 사용자 목록의 행을 클릭하거나 행에 포커스 후 Enter/Space를 누르면
- **THEN** 해당 사용자의 현재 역할과 범위로 초기화된 편집 다이얼로그가 열린다

#### Scenario: 저장 버튼이 단일 commit 지점
- **WHEN** 관리자가 다이얼로그에서 역할 또는 범위를 변경한 후 저장 버튼을 누르면
- **THEN** 단일 서버 액션이 호출되고 다이얼로그가 닫히며 목록이 갱신된다

#### Scenario: 변경분이 없으면 저장이 비활성
- **WHEN** 관리자가 다이얼로그를 연 후 어떤 값도 바꾸지 않으면
- **THEN** 저장 버튼은 활성화되지 않는다

#### Scenario: 취소는 변경을 폐기한다
- **WHEN** 관리자가 다이얼로그에서 값을 변경한 후 취소 또는 닫기를 누르면
- **THEN** 어떤 데이터도 서버에 전송되지 않고 목록은 변경 전 상태를 유지한다

#### Scenario: 저장 실패는 다이얼로그 내 inline 메시지로 표시된다
- **WHEN** 저장 액션이 실패하면
- **THEN** 다이얼로그는 닫히지 않고 실패 사유가 다이얼로그 내부에 inline으로 표시되며
- **AND** 관리자가 즉시 재시도할 수 있다

#### Scenario: 사용자 삭제는 다이얼로그 내 "위험 영역"에서만 가능
- **WHEN** 관리자가 사용자 편집 다이얼로그의 위험 영역에서 삭제를 확정하면
- **THEN** 사용자 삭제 서버 액션이 호출되고 다이얼로그가 닫히며 목록에서 해당 사용자가 사라진다
