# Design — context map query

조사 근거는 proposal.md 참조. 여기서는 **결정과 그 이유**만 남긴다.

---

## D1. 캡을 넓히지 않고 페이징으로 간다

**선택**: Top-N 캡을 제거하고 페이지 단위 질의로 대체한다.

**왜**: 캡은 원인 처방이 아니었다. `scope-context-map.ts:28-41` 주석이 비용 분해를 이미
적어뒀다 — 전체 로드 6.4초 중 **3.9초가 evidence**(긴 텍스트 14,384행)다. 엔티티 4,136행을
훑는 비용은 무시할 만하다. 즉 병목은 **행 수가 아니라 fan-out 과 wire 시간**이다.

그래서 두 가지를 분리한다:
1. 목록 = 얇은 컬럼만, 페이지당 50행
2. 상세(evidence/domains) = 다이얼로그 열 때만

이러면 캡이 필요 없어지고, 페이로드는 지금(Top-350 + fan-out 번들)보다 **작아진다**.
"더 많이 보여주기 위해 더 많이 내려받는다"가 아니라는 점이 핵심이다.

**기각한 대안**:
- *캡을 1000으로 올린다* — 10MB/16초 구간으로 되돌아간다. 주석이 경고한 그대로다.
- *클라이언트 검색만 추가한다* — 350행 안에서만 찾는다. "4,136개라 쓰여 있는데 150개만 보인다"는
  근본 문제가 그대로 남는다. 검색창이 생겨서 **오히려 "없다"는 오답을 확신시킨다**.

## D2. `getMatrix` 는 두 개의 다른 요구를 겸하고 있다 — 분리한다

`getMatrix` 호출부는 둘뿐인데 요구가 정반대다:

| 호출부 | 필요한 것 |
|---|---|
| `social-scraping/page.tsx:56` | 사용자가 **훑고 찾을** 목록 → 페이징·검색 |
| `_actions.ts:154` (프롬프트 시드) | **상위 신호 N개** 한 묶음 → 페이징 무의미 |

**선택**: 시드 경로를 `getSeedPool()`(Top-N 유지, fan-out 없이 얇게)로 분리하고, 목록 경로만
페이징한다.

**주의 — 기존 주석과의 불일치**: `generate-context-prompts.ts:56` 은 시드 풀을
"contexts 1.7k / conditions 2.4k / combinations 5.7k 롱테일"이라 적어뒀지만, 실제로 건네받는
matrix 는 이미 Top-150/200/500 으로 잘린 것이다. 즉 **주석이 의도한 롱테일에 코드가 닿은 적이
없다.** 시드 풀을 분리하면서 이 의도가 무엇이었는지 작성자 확인이 필요하다. 임의로 넓히면
"더 생성" 소진 지점이 850 → 9,800 프롬프트로 바뀌어 **비용(OpenRouter 호출) 성격이 달라진다.**

## D3. 검색 인덱스는 측정 후에 넣는다

**선택**: `mention_count` 인덱스는 **넣고**, 검색용 trigram 인덱스는 **넣지 않는다**(일단).

**왜**:
- `mention_count`: 모든 목록 질의가 `ORDER BY mention_count DESC`다. 인덱스가 없어서 매번
  4,136행 정렬이 돈다. 명백한 누락이고 비용이 없다.
- 검색(`ILIKE '%q%'`): 4,136행 seq scan 은 수 ms다. pg_trgm 확장 + GIN 인덱스는 쓰기 비용과
  운영 복잡도를 더하는데, **이 테이블은 읽기 전용 미러이고 행 수가 두 자릿수 배로 늘 계획이
  없다.** 측정해서 느리면 그때 넣는다.

`scope_context_*` 에는 FK 가 하나도 없다(0027). 이 change 는 그 결정을 건드리지 않는다 —
미러는 scope 가 채우고 우리는 읽기만 한다.

---

## D4. 표시 범위가 부분집합이면 UI 가 반드시 말해야 한다

현재 버그의 본질은 성능이 아니라 **정직성**이다. 헤더가 "4,136"이라 말하고 테이블이 150행을
그리는데, 그 간극을 알려주는 것이 아무것도 없다. 사용자는 검색해서 못 찾으면 "없다"고 결론낸다.

**선택**: capability 요구사항으로 못박는다 — 표시 집합이 코퍼스의 부분집합이면 UI 는
(a) 전체 대비 몇 개인지, (b) 왜 잘렸는지를 드러내야 한다. 페이징 이후에는 잘림 자체가
사라지므로 이 요구는 자연히 "검색 결과 N / 전체 M" 표시로 수렴한다.

이 요구를 spec 에 넣는 이유: 나중에 누군가 성능 때문에 다시 캡을 넣더라도 **말없이 자르는 것은
막기 위해서**다.

## D5. 프롬프트 blob 은 그대로 둔다

**선택**: `scope_context_prompt_cache` 를 관계형으로 정규화하지 **않는다**.

**왜**: 프로덕션 실측 최대 84행 / 10.5KB (9개 프로젝트 중 6개는 14행). 2MB Next 캐시 한도 대비
**헤드룸 200배**. 생성 상한도 ~850행이라 한도에 닿을 수 없다. 정규화는 마이그레이션 + 액션
재작성 비용만 있고 얻는 게 없다. **blob 은 이 규모에서 옳은 선택이다.**

다만 blob 이기 때문에 생기는 **lost-update 는 별개 문제**이고 실재한다(D6).

## D6. Lost-update 는 검색과 무관하지만 같이 고친다

`generateMoreSocialPrompts`(`_actions.ts:157→186`)와 `removeSocialPrompts`(`225→239`)는 둘 다
`get()` → JS 에서 수정 → `set()` 전체 덮어쓰기다. 락도, 버전 컬럼도, `jsonb_set` 도 없다.
동시 조작 시 한쪽이 **조용히** 사라진다.

**선택**: `generated_at` 을 낙관적 잠금 토큰으로 쓴다 —
`UPDATE ... WHERE project_id = ? AND generated_at = ?`, 0행이면 충돌로 처리해 재시도/안내.
새 컬럼 없이 기존 컬럼으로 해결된다.

**왜 이 change 에 묶나**: 이 액션들을 어차피 건드리고, 사용자가 볼 증상("삭제했는데 다시 생김")이
검색 개선의 체감을 그대로 깎아먹기 때문이다. 단, **독립 단계로 두어 빼기 쉽게** 한다(tasks 5).

---

## D7. UI 는 하우스 패턴을 따른다 (새 패턴 만들지 않음)

- 정렬: `useSortableTable` + `SortableHeader` — `ContextMapView` 는 이미 4개 탭 모두 준수.
  `ContextNodeMapView` 만 하드코딩이라 여기로 맞춘다.
- 검색 입력: `useDeferredValue`. `citations-view.tsx:185-190` 이 선례이며 주석에
  "per-keystroke re-sort 로 INP 회귀가 나서 debounce 대신 선택"이라 적혀 있다.
- 검색→필터→정렬 조합의 정본: `project-list.tsx:65-90`.
- 페이지네이션 자리: `TableShell` 의 `footer` 슬롯 — **이미 정의돼 있고 아무도 안 쓴다**
  (`context-map-view.tsx:227,247-251`). 새로 만들 필요 없다.

**서버 페이징인데 왜 클라이언트 정렬 훅을 쓰나**: 정렬 키는 서버로 보내고(`sort`/`dir`),
`SortableHeader` 는 표시·토글 UI 로만 쓴다. 훅의 `sorted` 는 쓰지 않는다. 헤더 UI 를 두 벌
만들지 않기 위해서다.
