## ADDED Requirements

### Requirement: 컨텍스트 맵 조회는 페이지 단위 서버 질의여야 한다

시스템은 `scope_context_*` 미러 조회를 **페이지 단위 질의**로 제공해야 한다(SHALL):
검색어·정렬 키·정렬 방향·페이지·페이지 크기를 인자로 받고, 해당 페이지의 행과 **검색 적용 후
전체 개수**를 함께 반환한다.

목록 질의는 엔티티의 얇은 컬럼만 반환해야 한다(SHALL). 인용문(evidence)·도메인(domains)은
목록에 포함하지 않아야 한다(SHALL NOT) — 이들이 wire 시간의 지배 요인이며, 목록에 필요하지 않다.

시스템은 코퍼스 전체를 한 번에 로드하거나, 조회 가능 범위를 상수 상한(Top-N)으로 제한하지
않아야 한다(SHALL NOT). 표시 범위는 페이지 크기가 결정하며, 페이지를 넘기면 코퍼스의 모든 행에
도달할 수 있어야 한다(SHALL).

#### Scenario: 상위 N 밖의 엔티티에 도달할 수 있음
- **WHEN** 사용자가 언급수 상위 150개 밖에 있는 컨텍스트 이름으로 검색하면
- **THEN** 그 컨텍스트가 결과에 나타난다

#### Scenario: 목록은 상세를 싣지 않음
- **WHEN** 컨텍스트 목록 한 페이지를 조회하면
- **THEN** 응답에 인용문·도메인 행이 포함되지 않는다

#### Scenario: 페이지 응답은 전체 개수를 동반함
- **WHEN** 검색어가 적용된 페이지를 조회하면
- **THEN** 응답은 해당 페이지 행과 함께, 검색 조건을 만족하는 전체 개수를 반환한다

### Requirement: 상세는 요청 시점에만 조회한다

시스템은 인용문·도메인·연결 조건을 **해당 엔티티의 상세가 요청될 때만** 조회해야 한다(SHALL).
목록을 그리는 시점에 상세를 미리 싣지 않아야 한다(SHALL NOT).

#### Scenario: 목록 렌더는 상세를 조회하지 않음
- **WHEN** 사용자가 컨텍스트 탭을 열어 목록만 보면
- **THEN** 인용문·도메인 질의가 발생하지 않는다

#### Scenario: 다이얼로그를 열면 그 엔티티만 조회함
- **WHEN** 사용자가 한 행의 자세히보기를 열면
- **THEN** 그 엔티티의 상세만 조회하며, 다른 행의 상세는 조회하지 않는다

### Requirement: 표시 집합이 코퍼스의 부분집합이면 UI 가 이를 드러내야 한다

화면에 보이는 행의 집합이 코퍼스 전체가 아닐 때, 시스템은 **전체 대비 몇 개를 보고 있는지**를
사용자에게 표시해야 한다(SHALL). 잘린 사실을 표시 없이 감추지 않아야 한다(SHALL NOT).

이 요구는 헤더 통계와 테이블 행 수가 서로 다른 모집단을 말하는 것을 금지한다: 통계가
코퍼스 전체를 세면서 테이블이 부분집합을 그린다면, 그 간극이 화면에 드러나야 한다(SHALL).

#### Scenario: 검색 결과 수와 전체 수를 함께 보여줌
- **WHEN** 사용자가 검색어를 입력하면
- **THEN** 조건을 만족하는 전체 개수와 현재 페이지 범위를 함께 표시한다

#### Scenario: 통계와 표시 행이 다른 모집단이면 그 사실을 표시함
- **WHEN** 어떤 이유로든 표시 행이 헤더 통계의 부분집합이면
- **THEN** UI 는 부분집합임을 나타내는 표시를 함께 렌더한다

### Requirement: 컨텍스트 맵 데이터는 검색 가능해야 한다

시스템은 컨텍스트·조건·컴비네이션 각 목록에 대해 **이름 기준 텍스트 검색**을 제공해야 한다(SHALL).
검색은 표시 중인 페이지가 아니라 **코퍼스 전체**를 대상으로 수행해야 한다(SHALL).

#### Scenario: 검색은 현재 페이지에 갇히지 않음
- **WHEN** 3페이지를 보는 중에 1페이지에만 있는 이름으로 검색하면
- **THEN** 그 행이 결과에 나타난다

#### Scenario: 결과 없음을 명시함
- **WHEN** 검색 결과가 0건이면
- **THEN** 빈 상태를 표시하며, 헤더만 남은 빈 테이블을 그리지 않는다

### Requirement: 프롬프트 카탈로그는 클라이언트에서 검색·필터한다

프롬프트 카탈로그는 프로젝트당 단일 JSON blob 으로 저장되므로, 시스템은 이에 대해 서버 측
검색·정렬·페이징을 제공하지 않아야 한다(SHALL NOT). 대신 질문 텍스트 검색과 layer·funnelStage
필터를 클라이언트에서 제공해야 한다(SHALL).

이 결정은 규모에 근거한다: 카탈로그는 프로젝트당 수십 행이며, 생성 상한이 존재한다. 규모가
이 가정을 벗어나면 blob 저장 방식 자체를 재검토해야 한다.

#### Scenario: 카탈로그 검색은 서버 왕복을 만들지 않음
- **WHEN** 사용자가 프롬프트 카탈로그에서 질문 텍스트를 검색하면
- **THEN** 이미 로드된 프롬프트 집합 안에서 필터링하며 서버를 호출하지 않는다

### Requirement: 프롬프트 blob 갱신은 동시 수정에서 안전해야 한다

시스템은 프롬프트 blob 을 read-modify-write 로 갱신할 때 **동시 수정에 의한 유실을 방지**해야
한다(SHALL). 두 갱신이 겹치면 나중 것이 앞선 것을 조용히 덮어쓰지 않아야 한다(SHALL NOT).

#### Scenario: 겹친 갱신은 유실 없이 처리됨
- **WHEN** 같은 프로젝트의 프롬프트 생성과 삭제가 동시에 일어나면
- **THEN** 한쪽의 변경이 조용히 사라지지 않는다(충돌을 감지해 재시도하거나 사용자에게 알린다)
