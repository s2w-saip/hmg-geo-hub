## 3. 우리 이해와 다른 점 (미팅에서 반드시 확인)

1. **공급 경로가 두 가지로 적혀 있다.** 10/2 협의안 v0.1은 "Scope 원문 API(`/measurements/{run}/raw`, `/turns/{id}/response`)를 S2W 키로 직접 호출"인데, 이 문서의 Phase #1은 "앤서가 운영하는 HUB RDS의 ing 스키마를 S2W가 읽기". 둘의 관계(Phase #1 = RDS, Phase #2 = Scope API?)와 각 단계의 기간을 물어야 한다. RDS 경로는 job 단위라 턴 원문이 없고(H2), Scope API 경로는 반복×턴 원문을 준다.
2. **Phase #1 운영 주체.** 문서는 S2W를 AWS scope 계정 밖의 '외부'로 다루고, S2W 시스템은 Azure에서 운영된다고 쓴다(S2W 구조도 v0.12 인용). 즉 Phase #1에서는 **HUB RDS·적재 워커를 앤서가 계속 운영**하고 S2W는 읽는 쪽이라는 뜻으로 읽힌다. 우리 ②는 "S2W가 hub-share를 인수해 운영"을 전제로 썼다. 대상 독자 표기 "S2W(GEO-HUB 신규 개발)"도 S2W가 새 시스템을 짓는다는 뉘앙스다. 확인 질문: Phase #1에서 적재·RDS 운영은 누가, 언제까지 하나? S2W 시스템은 Azure에 새로 짓나, hub-share를 받아 돌리나?
3. **H-Cloud가 한 번도 안 나온다.** S2W가 Azure에서 돌린다면 H-Cloud 사양(Node 22·PG 설치형·SSO·외부 통신 허용)은 누구에게 적용되나. 우리 ② D절의 전제가 바뀔 수 있다.
4. **C1(과거 분석값)이 사실상 '재계산'으로 적혀 있다.** 분석 결과 4종은 이관 불요, 검산용 1회 덤프만. HUB 설계는 v0(Scope 수신분)을 ing에 그대로 두고 이력은 v0로 보는 구조(결정 37)라, **HUB RDS의 ing에 과거 분석값이 얼마나 적재돼 있는지(Q1)**가 C1의 실질 변수다. 적재가 최근분만이면 과거 추이는 S2W 엔진 재계산 또는 덤프 적재가 필요하다.
5. **scope_prompts 정본.** 업무 데이터 15종과 공급 DB 양쪽에 걸쳐 있어 S2W가 정해 달라고 한다. 제안: 측정 등록의 정본은 Scope(ing.prompt/Scope API), HMG `prompts`·`prompt_candidates`는 편집·후보 원천으로 둘 다 이관.
6. **우리가 못 가진 입력 문서 2개.** '협의자료 v0.12'(앤서 이관 후보 수집 문서)와 'S2W 구조도 v0.12'. 전자는 3-1 목록의 근거라 사본이 필요하다.

## 4. H1·H2에 S2W가 준비할 입력

| 협의 | 앤서가 요구한 입력 | 우리 준비 상태 |

## 5. 미팅 질문 추가분 (기존 메모 3절에 더할 것)

- Phase #1·Phase #2 정의와 기간. RDS 읽기(이 문서)와 Scope 원문 API(협의안)의 관계.

- Q1 ing 적재 진행 범위(과거 회차 얼마나), Q3 loader_ro 실권한, Q4 라이브 RDS 사양·force_ssl.
- 3-3 회신 일정: drops/anchors 레지스트리(현 수치 재현에 필수), 검수 이력, 감사 로그(H-Cloud 로그 보존 요구가 있으면 이관 필요).
- 분석 결과 1회 덤프 형식·시점(동치 검증 비교 기준으로 필요).
- stg 브랜치에만 있는 배포·시크릿 스크립트(65·70·ops/back-secrets-init) 포함한 원본 저장소 권한.
- Supabase 행 수 정확값(count) 요청. 09-27 조사와의 차이 설명.
