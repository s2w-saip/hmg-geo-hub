작성2026-10-06 (미팅 10-07) 근거보고서 ① GEO 개념 요약 · ② 현황 분석 · 기능 보유 현황표 · 앤서 협의안 v0.1 (10-02) 인수물hub-share 72c260a3 (10-02) 하나. 협의 완료. 9/22 zip은 참고본

한눈에 — 다섯 문장

  1. 인수물은 hub-share 하나다. 10/2 스냅샷(72c260a3)으로 협의가 끝났다. 그래도 그대로 배포는 못 한다. 보안 4건, 운영 배포 워크플로, 테스트 실행 기록, 환경변수 목록이 비어 있다.
  2. 고객 화면은 옛 경로로 돈다. 20분 크론이 Scope 결과를 Supabase에 복사하고 화면이 DB를 직접 집계한다. 새 백엔드(FastAPI, 기능 72개)는 운영 전이고 운영 환경은 정지 상태다.
  3. 분석값은 전부 앤서가 계산해 준다. 앤서가 원문만 주는 날(C5, 날짜 미정)부터 우리 엔진이 없으면 지표 13개가 멈춘다. 우리 엔진은 설계 초안(약 44.5인일)뿐이고 코드는 없다.
  4. H-Cloud 사양과 새 백엔드가 충돌한다. 사양은 Node 22·PostgreSQL 설치형·SSO·외부 통신 3건인데, 설계는 FastAPI·RDS·Supabase 로그인·LLM 외부 호출이다.
  5. 가장 먼저 받을 숫자는 C5 전환일이다. 그다음이 원본 저장소 권한과 계정 소유 확인이다. 이 둘이 없으면 일정도 크기도 못 잰다.

2앤서 협의안 미결 C1~C5

항목내용앤서 쪽 기존 입장우리가 할 일
C1 과거 분석값과거 회차 값을 그대로 쓸지, 원문 받아 새 엔진으로 재계산할지과거 회차 재계산 후 1회 고지(A4), 리포트로 발행한 값은 유지(A5), 전환 이전 이력은 옛 값(결정 37)받을지 결정. 재계산하면 추이가 한 번 끊긴다
C2 수동 측정키당 하루 한도, 초과 처리, 비용 정산한도 둔다, 값은 협의반복 측정 확대(오차 범위)와 묶어 협의
C3 호출 한도동기화 배치 호출량, 주기429 + Retry-After20분 pull 유지 가능한지 확인
C4 키 교체교체 주기, 전달 경로앤서가 발급·교체, 유예 뒤 옛 키 만료보관 위치·교체 절차 정하기
C5 전환 일정원문 API 개시일, 현 연동 종료일미정가장 먼저 받을 숫자. 정해지는 순간 엔진 마감이 생긴다

3미팅에서 물을 것, 정할 것

앤서에게

  1. 원본 개발 저장소 읽기 권한. 스냅샷에서 뺀 배포 워크플로·비용 산정·내부 메모.
  2. AWS 'scope' 계정·Supabase·Vercel·도메인·GA4 OAuth 주체의 소유자와 이관 방식(이관 vs 재구축).
  3. Scope 카탈로그 내보내기(S-A2) 일정. 최신 scope-analysis(10dd345) 열람 가능 여부(동치 검증 비교용).
  4. C5 날짜, C2 한도. 구두라도 범위를 받아 온다.
  5. 보안 4건이 원본 저장소에 반영됐는지. 됐다면 그 커밋 수령.
  6. 측정 지연·엔진 변경 통보 규칙. run 1건 측정 소요·회차 마감 사유(closed_by) 수치 요청(운영 DB에만 있음).
  7. 엔진 추가(Google AI Overviews·Perplexity·네이버), 조합당 반복 측정 확대 가능 여부와 비용.

HMG·이노션에게

  1. H-Cloud에서 FastAPI 예외 협의를 시작할지, Node.js로 다시 쓸지. 결정 전 새 백엔드 추가 투입은 보류가 권고.
  2. SSO(OIDC) 연동 가이드. 8/6 요청 후 미수령.
  3. 외부 통신 허용 목록에 LLM 공급자 추가 가능 여부. 안 되면 분석 엔진 자체가 사양 위반.
  4. 5단계 게이트의 현재 위치와 일정.
  5. AWS·Supabase·Vercel 계정이 HMG 소유인지 앤서 소유인지.

S2W 내부 입장 (정해 둘 것)

  1. 기준 코드 = hub-share 하나. 보안 4건은 직접 수정, Node 22.
  2. 순서: 접근 확보 → 안전하게 돌리기(CI·배포·감시·환경변수) → 결정 대기(H-Cloud·C1·C5) → 엔진 구현·동치 검증.
  3. 엔진 설계 초안에 없는 새 제안 3가지: 분석 결과 버전 관리, 지표 분모 문서화·회귀 테스트, 사람이 만든 정답 세트.
  4. 전환 전후 옛 값·새 값 병행 산출. 없으면 "왜 숫자가 바뀌었나"에 답 못 한다.
  5. 분석 엔진은 hub-share 설계(Python 재구현)대로. 앤서 TypeScript 서비스는 비교 기준으로만.

4리스크와 조심할 말

리스크 3가지

  • 시계. C5가 정해지는 순간 분석 엔진 마감이 생긴다. 날짜가 없어 지금은 크기를 못 잰다.
  • 매몰. H-Cloud 런타임 결정에 따라 새 백엔드 72개 기능이 상당 부분 재작성될 수 있다.
  • 숫자 변동. 엔진과 경로를 바꾸면 고객이 보는 값이 달라진다. 병행 산출 없이는 설명 불가.

단정하지 말 것 (추론·2차 기록)

  • 보안 4건은 코드 차이가 사실이고 심각도는 추론. "취약점 4건"이라 부르지 않는다.
  • hub-share에 테스트 실행 기록 없음. 9/22 문서의 "3,900개 통과"는 옛 참고본 기준이라 인용 안 함.
  • 1회차 소요 시간은 코드 주석 출처, 표본 두 회차. 순수 측정 시간 기록은 없다.
  • SAIP Factory 평가는 명세 스냅샷 기준 추정. "핵심 처리 부적합, 후방 탐색 레이어로 가능"까지만.
  • 앤서 원본 저장소에는 보안 4건이 이미 반영됐을 수 있다. 확인 전엔 "front 스냅샷 기준"이라고 붙인다.
