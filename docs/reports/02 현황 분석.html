한눈에 보기

  1. 인수물은 hub-share 하나다. 10월 2일 스냅샷(72c260a3)으로 협의가 끝났고, 9월 22일 인계 zip은 참고본으로 보관한다(_archive/). 그래도 그대로 운영 배포는 못 한다. 지금 고객 화면은 옛 경로(DB 직접 조회)로 돌고, 새 백엔드(기능 72개)는 운영 전이다.
  2. 기능은 62개 항목 중 있음 34·상당 4·일부 7·없음 17. 핵심 지표, 출처 분석, 질문 관리, 검수 콘솔은 갖춰져 있다. 없는 것은 측정 범위(앤서 소관), 통계적 신뢰, 외부 데이터 연동, 행동 제안이다.
  3. 가장 큰 공백은 S2W가 운영할 분석 엔진이다. 지금 화면의 분석값은 앤서 Scope가 계산해 넘겨준다. 앤서가 원문만 주는 방식으로 바꾸는 날(C5, 날짜 미정)부터 새 엔진이 없으면 분석값 갱신이 멈춘다.
  4. 배포 전에 막을 것: hub-share front에 없는 보안 수정 4건(9/22 참고본에는 있음), 운영 배포 워크플로 부재, 테스트 실행 기록 0건.
  5. 남의 손에 있는 것: 측정·엔진 추가·수동 측정 한도(앤서), H-Cloud 런타임·SSO·외부 통신 허용(HMG·이노션), AWS·Supabase·Vercel 계정 소유(확인 필요). 아래 결정 2개·요청 4개, 할 일 15개는 ③에서 크기를 잰다.

결정이 필요한 것 (S2W 내부·고객)

  1. H-Cloud 백엔드 런타임. FastAPI 예외 협의를 시작할지, Node.js 백엔드로 갈지. 결정 전에는 새 백엔드 추가 투입을 보류한다.
  2. C1·C5. 과거 분석값을 다시 계산할지, 전환일을 언제로 할지. 앤서 쪽 입장은 이미 문서에 있다(D절).

앤서에게 요청할 것

  1. 원본 개발 저장소 읽기 권한과 스냅샷에서 뺀 자료(배포 워크플로, 비용 산정, 내부 메모).
  2. AWS 'scope' 계정·Supabase·Vercel·도메인·GA4 OAuth 주체의 소유 확인과 이관 방식.
  3. 최신 scope-analysis(10dd345, 코어 ec6bccb1)와 Scope 카탈로그 내보내기(S-A2) 일정.
  4. 원문 API 개시일과 현 연동 종료일(C5), 수동 측정 하루 한도(C2).

C품질·보안·운영 준비

코드는 있지만, 안전하게 배포해 돌릴 준비는 되어 있지 않다.

보안 수정 4건 — hub-share front에 없다 (9/22 참고본에는 있음, 우리가 직접 반영)

1담당 범위가 없는 일반 계정. 9/22 참고본은 로그인을 거부하지만 front에는 그 검사가 없다8. 참고본 인수 문서에 범위 미배정 계정 3개가 실제로 있다고 적혀 있다4. 실제로 무엇이 보이는지는 범위 정책 기본값에 달려 있어 미검증. 심각도 높음(추론).
2검수 콘솔 비밀번호. front는 환경변수가 없으면 코드에 적힌 기본값으로 넘어가는 분기가 남아 있다(값은 공유용으로 치환됨). 참고본은 세 가지 설정이 모두 있어야 콘솔을 연다9. 옛 경로에만 해당. 새 백엔드는 기본값 없이 전부 거부한다.
3프로젝트 목록 API. front는 로그인한 사용자 모두에게 작업공간 전체 프로젝트 목록을 돌려준다. 참고본은 권한별로 거르고 시험 9건을 둔다10. 노출되는 정보의 범위와 실제 사용 경로는 미확인.
4로그인 폼 언어값 미검증. front는 폼의 locale 값을 그대로 이동 주소에 넣어 외부 주소로 보낼 수 있다(열린 리다이렉트). 참고본은 허용 목록으로 거른다11.

네 건 모두 코드 차이 자체는 확인된 사실이고, 심각도는 추론이다. 참고본의 수정 코드를 hub-share front에 옮겨 직접 고친다. 앤서 개발 저장소에 이미 반영됐다면 그 커밋을 받는 쪽이 빠르다. 원본 저장소 접근 뒤 확인한다.

분석 엔진

  • S2W가 운영할 엔진은 미구현이다. hub-share에는 앤서 분석 과정(15단계)을 Python으로 다시 만드는 설계 초안만 있고(상태 '검토중', 약 44.5인일 추정), 코드는 없다12.
  • 분석 서비스 코드는 인수물에 없다. 9/22 참고본의 scope-analysis(TypeScript)는 설계가 이식 대상에서 뺐고(동치 검증의 비교 기준으로는 쓸 수 있음), 그 안의 분석 코어도 설계가 참조한 최신판보다 이전 버전이다12.

테스트·검증

  • 실행 기록이 없다. 테스트 파일은 새 백엔드 237개, front 560개가 있지만 hub-share에는 실행 결과가 없고, CI 정의는 참고본이라 돌지 않는다(원본은 사내 전용 러너 전제)13. 9/22 참고본 문서의 "3,900개 통과"는 옛 갈래 기준이라 hub-share의 근거로 쓰지 않는다4.
  • 분석 품질은 검증된 적이 없다. 분석 코어의 골든 테스트는 LLM 대신 고정 스텁을 쓴다. 코드가 같은지를 볼 뿐, 분류가 맞는지는 보지 않는다12.

운영 준비

  • 배포 경로. front의 운영 배포 워크플로는 스냅샷에서 제외됐고(9/22 참고본에는 있음), 새 백엔드는 EC2 배포 템플릿만 있다14.
  • 감시. 상태 확인 주소, ALB 헬스체크, Slack 웹훅(미설정 시 로그만)뿐이다. 경보·지표·로그 보존 설정이 없다15.
  • 설정 목록. front는 약 60개, 새 백엔드는 약 50개의 환경변수를 읽지만 정리된 목록이 없다. 예시 파일에는 6개만 있다16.
  • Node 버전. hub-share CI와 H-Cloud 사양은 22다(9/22 참고본은 24). 22로 간다13.

D외부 의존과 제약

측정은 앤서가, 인프라 사양은 HMG가 쥐고 있다. 새 백엔드 설계는 HMG 전용 클라우드를 고려하지 않고 확정됐다.

  • 앤서(Scope). 측정 실행, AI 서비스 추가, 수동 측정 개방(변경 예정, 하루 한도·비용은 C2 협의)이 앤서 손에 있다. 원문 API는 신설 예정이다17. 과거 분석값(C1)에 대한 앤서 쪽 입장은 이미 있다. 과거 회차는 다시 계산하고 한 번 고지한다(A4), 리포트로 발행한 값은 유지한다(A5), 전환 이전 이력은 옛 분석값으로 둔다(설계 결정 37)18. S2W는 이를 받을지 정하면 된다.
  • H-Cloud(HMG 전용 클라우드, 사양 7월 29일 제출·검토중). 서버는 Node.js 22(표준은 Tomcat이라 이미 예외 1건), DB는 PostgreSQL 17.6 설치형만 허용한다. 새 백엔드(FastAPI)와 관리형 DB(RDS)는 "H-Cloud 미고려"로 확정된 설계라(D2·D3), FastAPI는 두 번째 예외가 된다. 앤서도 이 충돌을 이미 짚고 "예외 협의 착수 또는 TypeScript 백엔드"를 권고했다19.
  • H-Cloud 보안 요구. HMG SSO(OIDC) 필수인데 현 설계는 Supabase 로그인 유지(A8)다. 외부 통신 허용 목록은 Scope·DataForSEO·GA4 3건뿐이라, S2W 분석 엔진이 LLM 공급자로 답변 원문을 보내는 경로가 사양에 없다. 관리자 화면은 사내망 한정, 로그 보존 3~5년 요구도 있다19. 담당: HMG 보안·이노션
  • 전환 조건. 고객과 약속한 '데이터 영향 변경 5단계 게이트'가 있다. 새 백엔드로 바꾸는 것 자체가 지표 계산 방식 변경이라, 옛 값과 새 값의 대조가 전환 조건이다. 단계표(S0~S11)는 있으나 날짜와 현재 위치가 없다20.
SAIP Factory 검토 결과 (3줄) ① 'Factory'라는 이름은 SAIP 저장소에 없다. 데이터 가공 모듈(Builder의 Pipeline·Datasets, 실행 엔진 Airflow)로 해석해 평가했다(추정, SAIP 팀 확인 필요). ② 핵심 처리에는 맞지 않는다. 답변 1건씩 LLM 분석을 돌리는 구조가 아니고(노드 실행당 LLM 1회 호출), 모델 버전 고정·JSON 검증·재시도가 없으며, 서버 스택(Python·Airflow·Temporal·Redis·OpenSearch)이 H-Cloud 사양과 어긋난다. 근거는 프론트 저장소와 API 명세 스냅샷(0.9.0, 6월 12일)이라 '명세상 미충족'이다. ③ 후방 탐색 레이어로는 가능하다. 완성된 KPI 테이블을 읽어 온톨로지·대화형 조회·계보 추적을 얹는 용도. 사람·운영 노하우 재사용은 ③에서 본다. 상세 판정표와 SAIP 팀 질문 8개는 별도 메모21.
