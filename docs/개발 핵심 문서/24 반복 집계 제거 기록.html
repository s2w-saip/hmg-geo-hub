19·20번의 반복 계산 중 무엇을 줄였는가?

입력이 바뀌지 않았는데 매 요청 다시 돌던 집계 네 가지를 건너뛰게 했다. 결과는 같고 실행 문장 수만 줄었다.

QA 진행률의 같은 범위 이중 집계, GA4 대시보드 카드의 페이지별 집계, 표준·관리자 프롬프트 목록의 범위 메타, 프로젝트 프롬프트 목록의 태그 값 집계다. 화면·문구·지표 정의·권한은 바꾸지 않았다. 19·20번 문서는 당시 점검 스냅샷으로 그대로 둔다.

운영 API·인증·DB 요청 0건. 로컬 합성 DB(PostgreSQL 17)·모의 응답·단위/동등성 시험으로만 검증했다. 실행 시간은 측정하지 않았고, 줄어든 것은 실행되는 SQL 문장의 수다.

결과 동일성과 보존 범위

  • 값의 의존 관계를 근거로 재사용한다. 카탈로그 메타는 SQL상 base(계정 범위)와 draft만 읽고, 기존 시험이 “필터·검색으로 선택지 모집단이 줄지 않는다”를 이미 고정하고 있다. 태그 값 제안은 프로젝트에만 의존한다. 원본 화면도 목록 전체를 한 번 받아 이 값들을 진입 시 한 번만 만들었다.
  • 쓰기 직후 낡은 값이 남지 않는다. 관리자·프로젝트 화면의 변경은 서버 액션 후 revalidatePath로 다시 렌더되고, 새 remote를 받은 화면은 재사용 기준을 새 초기값으로 바꾼다.
  • 남는 차이(경합 시에만): 다른 사용자가 동시에 카탈로그·태그를 바꾸면 그 사용자의 다음 쓰기·새로고침 전까지 선택지·통계·제안이 진입 시점 값이다. 수정 전에는 다음 페이지 조회에서 갱신됐다. 필터 총건수와 행은 매번 새로 읽는다.
  • 화면 구조 변경 없음: 세 목록 컴포넌트는 로더 연결(useMemo)만 바뀌었고 JSX·문구는 그대로다. legacy 카탈로그 저장소는 함수로 나눴지만 SQL 조각 29개와 쿼리 빌더 호출 구성은 원본과 같다.

API 계약 변경과 배포 순서

선택 파라미터 3개를 추가했다(모두 기본값 = 기존 동작). 기존 operation 218개·스키마 612개의 수는 그대로다.

파라미터수정 전 백엔드에 수정 프런트가 붙을 때
include_pages(conversion)공통 필터 모델이 모르는 파라미터를 무시하므로 기존처럼 페이지까지 계산한다. 오류 없음.
include_meta, include_values(/screen)/screen 4개 자체가 이전 리팩토링(977186e)의 신규 API라 원본 백엔드에는 없다. 18번 문서대로 수정 백엔드를 먼저 반영해야 하는 조건이 이미 있으며 추가 조건은 없다.

/screen의 응답 필드 count·facets·columns(카탈로그)와 values(프로젝트)는 건너뛴 경우 null이 된다. 프런트의 기존 전체 조회 경로는 이 값을 반드시 받으며, 없으면 오류로 처리한다.
