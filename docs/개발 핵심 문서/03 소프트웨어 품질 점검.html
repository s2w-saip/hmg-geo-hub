50개씩 보이지만, 표준 프롬프트는 먼저 전량 조회한다

/standard/prompts

실제 어댑터 함수에 모의 10,001행을 넣어 전량 반환 확인 · UI 슬라이스는 정적 확인 (R01)

확인한 동작
legacy 쿼리는 스코프에 속한 전체 행을 LIMIT 없이 읽는다. API 경로는 all=true로 페이지당 25,000행을 요청하고 최대 4페이지를 합친다. 화면에는 전체 rows가 전달되고, 브라우저에서 필터·정렬 후 기본 50행을 slice한다.
발생 조건
계정이 조회 가능한 프롬프트 수가 늘어나면 발생한다. API의 정상 커서 진행 기준 상한은 25,000 × 4 = 100,000행이다. 실제 운영 행 수가 10,000건을 넘는지는 확인하지 않았다.
사용자 영향
첫 화면에 50행만 보여도 전체 데이터의 DB 조회·전송·직렬화 및 클라이언트 배열 처리가 필요하다. 데이터 증가에 따라 초기 진입과 검색·정렬 비용이 커진다.
판정의 범위
클라이언트 페이지네이션은 있다. 따라서 ‘한 화면에 표준 프롬프트 10,000행을 모두 그린다’는 설명은 부정확하다. 확인한 문제는 전량 로딩이다. 응답 크기·초 단위 지연·메모리 사용량은 실측하지 않았다.
수정 방향
목록 화면에서 all=true와 fetchAllPages를 제거하고 검색·정렬·필터·커서를 서버에 전달한다. 전체 엑셀 내보내기는 별도 다운로드 경로로 둔다.
완료 확인 기준
10,001행 데이터에서도 초기 목록 응답은 선택한 pageSize 이하이며, 다음 페이지 이동 때만 추가 조회된다. 검색·정렬 결과와 전체 건수는 서버 기준으로 일치해야 한다.

관리자 목록과 프로젝트 프롬프트 목록은 sorted.map으로 필터에 남은 모든 행을 만든다. 후보 목록도 같은 구조다. 페이지 단위 slice나 가상 스크롤이 없다. API도 페이지들을 모두 모아 전달하고 legacy는 LIMIT 없는 쿼리로 읽는다.
발생 조건
필터에 많은 행이 남는 경우다. 예를 들어 관리자 API는 상한 이내의 10,000행이 모두 활성 행이면 10,000개 tr을 만든다. 프로젝트 프롬프트는 10,001행도 조회 상한 20,000행 이내라 같은 전체 렌더링 경로를 탄다.
사용자 영향
행마다 셀·배지·체크박스·편집 UI가 늘어나 초기 렌더링, 정렬, 선택 변경 때 브라우저가 처리할 작업이 커진다. 프로젝트의 사용자 정의 열 수가 늘면 셀 수도 함께 늘어난다.
판정의 범위
성능 병목을 만드는 구조를 확인한 것으로, 특정 브라우저에서 멈춤이나 OOM이 발생했다는 실측 결과는 아니다. 필터나 삭제됨 탭에 따라 실제 렌더링 행 수는 줄어든다.
수정 방향
서버 페이지네이션을 먼저 적용한다. 한 페이지도 큰 경우에는 행 가상화를 추가한다. 전체 선택은 ‘현재 페이지’와 ‘검색 결과 전체’를 구분해 서버 작업으로 처리한다.

발생 조건
관리자 카탈로그 10,000건은 20회 조회 후 성공하지만 10,001건은 20회 조회 후 실패한다. 프로젝트 프롬프트는 20,001건에서 40회 후 실패한다. 관리자 조회에는 soft-delete된 행도 포함되므로 활성 행 수만 보면 임계값을 놓칠 수 있다.
사용자 영향

판정의 범위
API 전환 경로에 한정된다. 이는 조용히 일부 데이터를 누락하는 버그가 아니라 명시적인 실패다. 커서 반복·무한 조회를 차단하는 helper의 보호 자체는 필요하며 상한만 늘리는 방식은 해결책이 아니다.
수정 방향

P1SW04 · 저장·정합성 · 공통

QA 판정 저장이 실패해도 이전 ‘저장됨’ 표시가 남는다

/raw-data-qa/answers/[jobId]

실제 save·setFlag 함수로 성공 → 수정 → HTTP 401·422·500 시나리오 재현 (R04)

확인한 동작
save는 409 충돌과 res.ok만 처리한다. 그 외 HTTP 오류에서는 에러 메시지를 만들지 않고 saving만 false로 바뀐다. 성공 시 설정한 savedAt은 이후 판정을 수정해도 지워지지 않으며, 하단 바는 savedAt이 있으면 계속 ‘저장됨’을 표시한다.
발생 조건
한 번 저장한 뒤 판정을 변경하고, 다음 PUT /api/qa/review가 세션 만료·검증 오류·서버 오류로 실패하는 경우다. 첫 저장부터 실패해도 사용자에게 저장 실패 안내가 없다.
사용자 영향
사용자가 최신 변경까지 저장됐다고 오인한 채 다음 항목으로 이동할 수 있다. 서버에 반영되지 않은 판정 변경이 사라진다. 네트워크 reject는 로컬에서 잡지 않으며 단축키는 void save()를 호출한다.
판정의 범위
409 충돌은 잠금 상실·읽기 전용 상태로 처리한다. 문제는 나머지 실패와 수정 상태 관리다. 데이터 손실 사례를 운영에서 확인한 것은 아니며, 모의 HTTP 응답으로 저장 핸들러 동작을 재현했다.
수정 방향
저장 상태를 idle/dirty/saving/saved/error로 관리하고 변경 즉시 dirty로 전환한다. 모든 non-2xx와 네트워크 예외를 사용자에게 표시한다. 실패 시 입력을 유지하고 재시도를 제공하며 미저장 상태의 이동을 보호한다.
완료 확인 기준

완료 확인 기준

요청한 대량 로딩과 silent failure를 중심으로 hmg-geo-hub-share의 실제 호출 경로를 확인했다. _archive를 현행 구현으로 취급하지 않았다. 이 보고서는 전체 보안 감사나 운영 성능 인증이 아니다. 운영에서의 발생 여부를 확정하려면 활성 소스 플래그, 스코프별 행 수, 응답 크기·시간, DOM 수, DB 실행 계획, 오류 로그와 캐시 상태를 해당 배포에서 확인해야 한다.
