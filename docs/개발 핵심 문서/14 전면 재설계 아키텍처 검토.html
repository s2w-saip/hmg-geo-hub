DECISION REVIEW · 01

검토의 출발점: 제품 요구부터 다시 결정

전면 재설계에서는 Next.js·React·FastAPI·현재 DB 스키마·기존 워커를 모두 선택지로 돌린다. 업무 의미와 데이터 보존 의무를 먼저 확인하고, 도구는 그 요구를 가장 작은 운영 부담으로 충족하는지 검증해 선택한다.

작성안을 3회 순차 재검토해 보완한 의사결정 검토서다. 1차 사실·합의 5건, 2차 정합성·실패 7건, 3차 실행 가능성·일관성 5건을 반영했다. 동일 작성자의 연속 검토이며 독립된 3인 심사는 아니다. 회차별 문제·수정·검증 기록에서 확인할 수 있다. 새 스택의 구현·성능 실증은 수행하지 않았으며 팀·허용 런타임·일정·호환 범위는 미결이다.

초기 선정 기록을 반영한 후속 수정: 5/22의 Next BFF 채택·Vite SPA 기각 이유를 확인해 SPA 우선 추천을 철회했다. 브라우저 세션/BFF 위치를 먼저 정하고 Next 유지·축소안과 API에 BFF를 통합하는 SPA안을 동등 조건으로 비교한다. 기존 3회 이력에 후속 6개 항목을 별도로 연결했다. 6절의 선정 근거 재검토

최신 기술 스택 기획: 사용자가 Python·TypeScript 모두 운영 가능함을 확인했다. A Next 16 웹/BFF + FastAPI + Python 워커를 우선 실증하고 B React Router SPA + API 내 BFF와 비교한다. C/D의 채택 조건, 라이브러리·세션·작업·Azure 배포·총비용을 별도 3회 검토로 구체화했다. 구성안별 기술 스택 기획과 3회 수정 기록에서 현재 착수 순서를 확인한다. 최종 선정·앱 실증 완료를 뜻하지 않는다.

기술 가정부터 검증

Next.js는 필수인가, Python이 허용되는가, 서버 렌더링과 별도 BFF가 필요한가를 각각 판단한다.

현재 정보로 우선 비교할 기준 조합

도메인 모듈 + 브라우저 보안 경계 + 분리된 수집/분석 워커 + PostgreSQL·객체 저장소를 논리 기준으로 둔다. 웹 프레임워크와 API의 별도 배포는 아직 선택하지 않는다. 독립 API가 필요하면 Python 허용·팀 역량에 따라 FastAPI, Node 조건이면 Node API를 비교한다. TS 웹 서비스만으로 충족할 수 있으면 Next 웹 API+별도 worker 안도 검토한다.

현재 Next가 맡는 세션·토큰·중계 책임을 제거한 것으로 가정하지 않는다. 같은 보안·업무 조건에서 배포 역할, 초기 렌더링, 오류/갱신 처리, 개발·운영 비용을 비교한다. SPA는 렌더링 구성이고 Next는 프레임워크로 서로 배타적인 분류가 아니다. Next도 SPA·정적 export를 지원한다. W01 ↗ W40 ↗ W05 ↗

읽는 순서: 요구·기존 결정 차이(2절) → 핵심 데이터/실패 계약(3·8·10·11절) → 실증과 선정 순서(15절) → 22개 ADR(17절). 라이브러리 전수 목록과 출처는 마지막 두 절에 둔다. 기술 선택은 필수 조건 충족 여부를 먼저 보고, 통과한 후보끼리 구현·운영 비용을 비교한다.

현재 아키텍처 분석은 현황 근거로 유지한다. 이 검토서는 기존 설계 결정을 새 아키텍처에 그대로 적용하는 문서가 아니다.

GEO 전용 설계: 화면보다 먼저 고정할 데이터 단위

다음 항목은 새 도메인 모델 제안이다. 공급자 API의 확정 필드나 이미 존재하는 신규 테이블 이름이 아니다. 글로벌·웹사이트·프로젝트는 공통 측정·권한·카탈로그 모델의 서로 다른 범위로 표현하는 편을 권한다. 공통 ID·원문·작업 기반을 공유하더라도 회차·모수·앵커·제외·발행 게이트는 범위별 정책으로 보존한다. 단일 SQL이나 같은 분모로 강제 통합하지 않는다.

측정 계획·셀프롬프트 버전, 시장/언어, 엔진·실행 경로, 조건·반복 계획측정 대상이 바뀌어도 같은 시계열처럼 합치는 것

반복 측정과 재시도의 식별

하나의 측정 셀에서 의도한 반복 표본, 그 표본을 얻는 외부 실행 시도, HTTP 재전송, 원문 수정판을 서로 다른 단위로 둔다. 같은 답변 문자열도 독립 측정이면 별도 표본이다. 같은 외부 응답의 중복 전달은 새 표본이 아니다. 공급 ID는 공급자·환경·자료 종류를 포함한 namespace와 함께 매핑하고, content hash만으로 측정 ID를 만들지 않는다.

예를 들어 계획된 3회 반복 중 두 번째가 timeout으로 재전송되더라도 모수가 자동으로 4가 되지 않는다. 공급자가 별도 실행을 만들었다면 두 외부 실행을 보존하고 어느 결과를 유효 표본으로 선택할지 코드 규칙과 이력으로 정한다. 턴·부모·반복 키가 없는 입력은 합성해 채우지 않고 지원 불가/검수 상태로 둔다. 모수에는 계획·수신·분석 완료·제외·결손 수와 기준 시각을 함께 제공한다.

고객 질문·프롬프트·엔진 경로·언어·표본 구성이 바뀐 전후를 동일 모집단의 개선 효과로 표시하지 않는다. 동일 조건의 코호트 비교와 전체 변화량을 구별하고 표본 수·결손·버전 경계를 노출한다. 통계 구간을 쓸 때도 반복·턴 간 의존성을 고려한 분석 단위를 먼저 정한다. 이는 지표 정의의 구현 계약이며 TypeSafe 확률을 측정 오차 범위로 대체하지 않는다.

근거: 측정 유효성 검토 · 기존 분석 엔진 초안. Python·15단계 구현은 재선정 대상이다. 과거 재해석의 별도 노출은 미결이며 발행값 보존 의무와 구별한다.

DECISION REVIEW · 04

서비스 구조: 모듈과 배포 단위를 분리해서 결정

후보장점비용·제약현재 판단

2. 현재 API가 대신하는 것과 Next에 남아 있는 것

5. 결정을 바꿀 실증과 현재 권고

P1/P6는 로그인 → 갱신/동시 요청 → 권한 철회 → 목록·상세 → mutation → 비동기 export → 다운로드/로그아웃을 같은 IdP·범위·데이터 조건으로 검증한다. CSRF/Origin, 다중 인스턴스 세션, 401/403/429/5xx, QA 별도 진입, client IP 신뢰 경계를 포함한다. 합성 mock 통과와 실제 IdP 검증은 분리한다. 초기 표시·후속 탐색·JS/메모리·서버 홉·API/DB 시간·운영 비용·교체 범위를 측정하고 선택 전 수용 기준을 정한다.

1만 건 전량 조회·silent failure·비싼 SQL·긴 작업의 웹 실행은 프레임워크와 별도로 고쳐야 한다. Next 제거만으로 이 문제의 해결이나 성능 향상을 주장하지 않는다. 이번 재검토는 문서와 소스 근거의 보완이며 A~D 구현 비교 결과는 아직 없다.

5. 컷오버·정리최종 증분 이관·운영/고객 확인·롤백 기록·legacy 종료새 시스템에서 발생한 쓰기를 포함한 복원/롤백 절차 검증

처음부터 읽기/쓰기를 양쪽에 무조건 동시에 수행하지 않는다. 전환 기간에 한쪽을 정본으로 두고 명시적으로 동기화한다. UI 라우팅 rollback만으로 신규 DB의 writes를 되돌릴 수 없으므로 forward-fix·정지 창·역동기화 중 현실적인 절차를 미리 시험한다.

컷오버 런북: 앱 운영 쓰기·발행·외부 측정 등록 각각의 소유자를 정하고, 전환 경계에서 기존 writer/스케줄러의 신규 작업 접수를 차단한다. 진행 중 operation과 외부 측정 요청은 원장으로 대조해 인계하며 단순히 두 스케줄러를 동시에 켜지 않는다. 공급자의 원문 측정 지속 여부는 별도 협의 사항이고 앱 쓰기 동결과 같은 것으로 취급하지 않는다.

최종 증분·운영 원장·QA·사용자/권한·GA4 OAuth 주체·객체/리포트 파일을 함께 대조한 뒤 트래픽을 전환한다. 전환 후 장애의 중단 조건과 책임자, 신규 쓰기를 포함해 돌아갈 수 있는 지점, 돌아갈 수 없는 변경을 기록한다. DB migration은 구/신 앱 공존이 가능한 expand→backfill/검증→전환→contract 순서로 설계하고, 파괴적 스키마 정리는 복구 창 종료 뒤에 둔다. backup 파일 존재만으로 완료하지 않고 격리 환경 복원·재개를 리허설한다.

기존 코드에서는 지표 사전·테스트 시나리오·권한 반례·재현 자료·이관 원장을 검증 자산으로 가져온다. 현재 legacy/API 분기, 여러 캐시/요약 우회, 순차 워커, 오류→빈 값, 대량 페이지 수집을 새 제품의 기본 구조로 복제하지 않는다. UI 재사용·SQL 재사용도 모듈별 품질 검증 후 선택한다.
