어떤 화면 지표가 조회할 때 JOIN하고 다시 계산되는가?

인용 도메인 통계·톤별 인용·ACR·GA4 전환·검수 진행률에 조회 시 JOIN·집계가 남아 있다. 요약 KPI·언급·GEO는 사전 계산 열, 동결 VIEW, legacy 미러 경로를 구분해야 한다.

조회 시 계산하는 13개 지표 묶음과 저장값을 읽는 대조 사례 1개를 화면에서 SQL까지 추적했다. 이는 실행 구조의 확인이며 실제 지연 순위나 운영 병목의 확정은 아니다.

운영 API·인증·DB 요청 0건. 소스·로컬 실행 설정만 확인했다. 쿼리 실행, 부하 시험, 캐시/DDL/서비스 코드 변경 없음.

‘매번 계산’의 정확한 조건

  • API — 결과 캐시 미적용: GA4 전환과 QA 진행률은 기존 분석 결과 캐시 허용 목록 밖이다. 유효 데이터가 있는 요청은 집계 서비스로 들어간다. QA는 필터 범위와 전체 범위를 각각 계산한다. S37 · S51 · S09
  • API — 캐시를 켤 수 있는 분석 GET: KPI·언급·인용·추이·GEO·ACR은 결과 캐시 적중 시 계산을 생략할 수 있다. 기본값은 꺼짐이며, 이번에 읽은 로컬 백엔드 컨테이너 설정에도 HGH_RESULT_CACHE가 없었다. 운영 활성화 여부는 미확인이다. S10 · S09
  • legacy 직접 DB 조회: 주요 분석 리더는 Next unstable_cache 기반 mirrorCache로 감싸며 기본 TTL은 7,200초다. 미적중·무효화·다른 필터·실패 후 재시도 등에서 집계한다. ‘새로고침마다 반드시 무거운 SQL 전체 실행’으로 단정할 수 없다. GA4는 별도 24시간, QA 진행률은 30초 캐시다. S07 · S08 · S40 · S53
  • 실제 선택 경로: HGH_SOURCE 그룹별로 API/legacy가 달라지며 소스 기본값은 legacy다. 로컬 preview 실행기는 G1~G7을 api로 지정한다. 이번 점검은 요청 추적을 하지 않았으므로 운영 화면의 실행 경로를 확정하지 않는다. S56

먼저 확인할 네 가지

  1. 인용 도메인 목록: 한 페이지를 반환해도 인용 전체 모집단을 접고 출처·오버라이드를 JOIN한 뒤 순위를 만든다. 검색·정렬·페이지 요청별 반복 비용을 확인한다. J03
  2. GA4 대시보드 카드: 카드에는 요약·커버리지·경우에 따라 추이만 쓰지만, API 서비스는 페이지별 집계도 실행한다. 캐시 미적용 상태에서 화면에 필요하지 않은 연산이 포함된다. J08
  3. ACR: 한 요청이 브랜드·추이·배틀·차종·점유 맵을 위해 여러 JOIN/집계 문장을 실행한다. 공통 cells는 각각의 SQL 문장 안에서 정의되며 결과 전체가 미리 저장된 것은 아니다. J07
  4. QA 진행률: API는 scoped/total을 매 요청 각각 계산한다. 필터가 비어 두 범위가 같을 때도 별도 호출한다. 기존 30초 캐시가 있는 legacy와 차이가 있다. J13

위 순서는 코드에서 확인한 반복·불필요 계산을 조사할 우선순위다. 실행시간을 측정해 정한 병목 순위는 아니다.

S54

동결 스냅샷과 결과 사전 계산은 다르다

frz.card_answer 등은 DDL에서 CREATE OR REPLACE VIEW로 정의한 일반 VIEW다. 발행 시점 데이터·판정을 고정하지만, 화면 조회 때 필요한 JOIN과 SUM/COUNT까지 모두 없애지는 않는다. 글로벌 카드 VIEW는 대표적으로 다음 경로를 읽는다. 보관행·표면별 UNION ALL 갈래도 존재한다.

KPI 요약 요청 → fetch_counts → frz.card_answer → frz.cell JOIN frz.prompt JOIN rd.answer/보관행 → 필터 범위 SUM·COUNT → 화면 비율

이 경로는 card=true, freeze_at_publish, 동결 창 판정을 만족해야 선택된다. 프로필 기본값은 off이며 로컬 컨테이너의 HGH_LEGACY_PROFILE도 미설정이었다. 따라서 로컬 KPI가 현재 이 VIEW를 사용한다고 주장하지 않는다. S11 · S12 · S13 · S14

인용 SQL의 WITH ... AS MATERIALIZED도 영구 저장된 집계 테이블이나 요청 간 캐시가 아니다. 한 SQL 실행 안에서 중간 결과를 재사용하는 구조다.

이미 줄인 연산과 현재 비활성인 화면

  • API의 언급 수·우호도·기본 순위 값은 적재된 answer/answer_brand 열을 합산한다. legacy처럼 원문 언급을 매번 정규화·순위 산정한다고 설명하면 부정확하다.
  • 인용 카테고리·유형은 cit_c*·t_own 열 우선이다. 데이터 미채움·재판정 지연에서만 JOIN 폴백이 생긴다.
  • URL 인용률에는 발행값·저장된 URL 판정값을 쓰는 분기가 있다. 모든 요청이 원문 URL 비교를 다시 하는 것은 아니다.
  • 소셜 스크래핑의 언급·감성·동시 언급 값은 스냅샷 저장값이다. 이름 JOIN과 총건수 COUNT는 있으나 원천 지표 재생성 사례와 구분했다.
  • 스탠스 분포 SQL은 있지만 현재 표준 언급 화면은 STANCE_CARD_ENABLED = false여서 활성 지표 사례에서 제외했다. S55

이 분석으로 확정한 것과 다음 검증

확정: 화면 호출 경로, SQL에 존재하는 JOIN·집계, VIEW 정의, 코드의 캐시 적용 범위, 일부 불필요·중복 계산. 미확정: 운영 캐시 적중률, 실제 필터별 선택 경로, 인덱스 사용 여부, 행 증폭, 실행시간·부하·잠금 영향.

다음 검증은 동일 화면 조건의 비운영 데이터로 수행한다. API/legacy·프로필·캐시 적중/미적중을 기록하고, 대표 SQL의 실행계획에서 실제 행 수·반복 횟수·버퍼 읽기·정렬/해시 디스크 사용을 비교해야 한다. 불필요한 페이지 집계 분리, 동일 범위 중복 계산 제거, 사전 계산·캐시 범위 조정은 그 결과를 근거로 판단한다. 기존 지표 결과와 권한 동등성을 함께 검증해야 한다.

현재 프로젝트에서 선택한 소스 근거 56개 중 55개는 원본 저장소 파일과 바이트 단위로 동일하다. 서로 다른 경우는 아래 JSON의 same_as_original에 표시하며 해당 코드에 한정해 해석한다. 정적 점검용 해시와 행 번호를 검증 JSON에 기록했다.

코드 안의 과거 성능 수치는 이번 측정 결과로 인용하지 않았다. 새로운 성능 테스트나 운영 EXPLAIN은 실행하지 않았다.
