코드에서 확인한 핵심 발견

P0 · 전환 전1. GA4는 분모가 바뀌는데 화면의 사용자 라벨이 남는다

레거시는 key events ÷ activeUsers, 새 백엔드는 conversions ÷ sessions를 계산한다. 어댑터는 세션 수를 aiUsersTotal·users 필드에 넣고, 한국어 문구는 “활성사용자”라고 설명한다. 어댑터 주석도 G3/G4/G6 전환 때 라벨을 바꿔야 한다고 명시한다. 이는 전환 조건에 따라 나타나는 명확한 해석 위험이다. 현재 운영에서 이미 발생한다고 단정하지 않는다. E09 E10 E11 E12 E13

가상 예: 이벤트 24건, 활성 사용자 20명, 세션 24회
legacy = 24/20 = 120% → API = 24/24 = 100%
성과 변화가 없어도 정의 변경만으로 20%p 하락한다.

조치: 화면·툴팁·분모 단위를 함께 바꾸고 전환일에 기준선을 나눈다. “전환한 사용자 비율”과 “사용자/세션당 이벤트 발생 수”를 구분한다. GA4는 Scope 측정과 조인하지 않으므로 이 값으로 GEO 활동의 인과효과를 계산할 수 없다.

P0 · 정의 확정2. 대표 1건·결손 포함·별칭 중복은 설정에 따라 달라진다

cell_rep가 켜지면 셀 대표를 사용하며 gap_in_population에 따라 분석 결손도 모수에 포함된다. brand_exposure_per_alias가 켜지면 경쟁 브랜드의 노출 답변 수가 count(*) 대신 sum(rid_n)이 된다. 소스의 DEFAULT_SPEC는 off다. 원문에서 지적한 문제는 존재하지만 적용 조건을 확인해야 한다. E03 E04 E07

영향: 같은 원천으로 다시 계산해도 환경 설정, 삭제 질문 포함 여부, 발행값 선택, 대표 셀 규칙이 다르면 수치가 달라진다. 별칭 중복이 모든 KPI에 똑같이 적용되는 것은 아니다. 해당 코드의 직접 영향은 경쟁 브랜드 exposure_answers다.

조치: 화면 원천과 프로필을 측정 결과의 버전 정보에 묶는다. “운영과 같은 값” 검증과 “원하는 정의로 정확한 값” 검증을 각각 수행한다.

P0 · 지표 설명3. 지표 이름보다 산식의 의미가 좁다

우선 노출도는 순위가 있는 답변만 분모로 삼는다. 글로벌 인용 점유율은 선택 답변의 Official (HMG) 카테고리를 세며 선택 브랜드 고유 출처만 세는 값이 아니다. 인용 정확도는 타겟 URL 적중 관계이지 인용 내용의 사실성 검증이 아니다. 답변 톤별 인용 SQL은 답변 톤과 인용 URL을 연결하지만 인용 페이지 본문을 검증하지 않는다. E05 E06

가상 예: A는 100개 답변 중 10개에서 1등 → 노출률 10%, 평균 순위 1
B는 100개 중 80개에서 2등 → 노출률 80%, 평균 순위 2
평균 순위만으로 A의 전체 가시성이 더 높다고 결론 낼 수 없다.

웹사이트 URL 지표는 라이브 답변 비율·발행 프롬프트 값·별도 프롬프트 집계를 함께 다룬다. 특정 필터 변경으로 report에서 live로 바뀔 수 있으므로 원천·분모 단위가 다른 수치를 단순 비교하면 안 된다. API에는 이 차이를 설명할 메타데이터가 이미 있다. E20

P0 · 분석 인수4. 검수 기록이 판정 정확도의 증거로 이어지지 않는다

QA는 섹션별 ok/issue를 app.qa_answer_review에 저장한다. 분석 조회·적재·공통 계층에서 이 테이블을 직접 읽는 경로는 이번 정적 검색에서 확인되지 않았다. 저장된 검수만으로 언급·감성의 정답률이나 KPI 보정이 자동으로 만들어지지는 않는다. E15

새 분석 엔진 설계는 스텁 재생, 원본 엔진 동치, 같은 엔진 재실행과의 비교를 계획한다. 이들은 이식 품질과 비결정성 점검에 유용하다. 그러나 원본의 오류를 함께 재현할 수 있어 사람 정답 대비 정확도 검증은 별도로 필요하다. 언급 유형별 감성 매트릭스는 모듈 명세 자체가 근사이며 유형 간 합산 금지라고 적는다. E16 E17 E21

조치: 국가·언어별 정답셋, 평가 기준, 오류 사례, 수정 이력을 먼저 확보한다. 분석 엔진 교체의 통과 조건에 동치와 정답 정확도를 모두 넣는다.

P1 · 비교 신뢰도5. 추이 변화에서 표본·모델·판정 변화가 분리되지 않는다

엔진 카탈로그는 웹 UI 수집에서 모델을 고정하지 않는다고 명시한다. 답변 상세에는 model_slug를 담을 수 있지만, 확인한 추이 구현에서는 모델·분석 버전별 기준선 분리 경로가 보이지 않았다. 신뢰구간·오차 범위 산출도 확인한 back/app·front/lib·docs 범위에서는 찾지 못했다. E08

이는 웹 서비스의 현재 답변을 관측하는 목적 자체를 무효화하지 않는다. 다만 기간 차이를 콘텐츠 개선 효과로 해석하려면 질문 세트, 회차, 수집 경로, 측정 모델, 분석 모델·규칙의 변화를 구분해야 한다. 질문별 답변 수와 고유 질문 수도 서로 다른 표본 정보다.

조치: 공통 질문 세트의 비교 결과와 전체 운영 결과를 함께 보여 주고, 반복 측정 파일럿으로 변동 폭을 먼저 구한다. 모델을 고정할 수 없는 웹 수집은 변경 여부·관측 가능한 버전 정보와 수집 조건을 기록한다.

P1 · 화면 사용 범위6. ACR은 표준 실데이터와 웹사이트 정적 표본을 구분해야 한다

표준 ACR은 실제 집계 경로가 있으나 웹사이트 ACR 화면은 소스에서 정적 표본으로 명시돼 있다. 해당 페이지의 API 전환은 필터 옵션을 가져오는 동작이며 본문을 실데이터로 바꾸지 않는다. E14

계획 반복 수는 기본 10회지만 ACR 집계의 분모는 실제 유효 반복 수다. 반복이 있다는 이유만으로 충분한 신뢰도를 인정하거나, 2턴 유도 질문에서의 AI 선택을 구매확률로 해석할 수 없다. E24

조치: 성과 보고서에서 정적 화면을 제외하고, 실제 ACR은 프롬프트·유효 반복 수·후속 질문·선택 판정 버전을 표시한다.

활용할 기반7. 집계·재판정·동결·버전 관리 구조는 재사용 가치가 높다

분자·분모 정수 쌍, 결손·숨김 사유, 증분 적재와 일괄 적재의 동치 시험, 멱등 처리, 회차 발행 게이트, 엔티티 버전 미리보기·되돌리기 구조가 있다. 이를 활용하면 수치의 계산 경로를 추적하고 변경을 통제할 수 있다. 시험 파일 존재를 확인했으며 운영 데이터로 해당 시험을 재실행한 것은 아니다. E05 E22 E23

주의할 범위도 있다. 발행 게이트는 모든 표면에 동일하지 않고 강제 발행·봉인 예외가 있다. 엔티티 버전 기능은 기존 72개 분류표 밖이며 API 연결 모드에서만 제공된다. 이 조건까지 포함해 인수해야 한다. E23 E25

P0 · 원문 인수8. 영구 DB 접근만으로 새 분석 엔진의 입력이 완성되지 않는다

현재 DDL의 ing.answer는 job 단위 answer_text·model_slug·analysis_version·content_hash 등을 보관한다. mention_occurrence와 answer_stance에는 turn_index가 있지만, 검사한 합본 DDL에는 턴별 질문·답변 원문을 담는 ing.turn 테이블이 없다. “턴 정보가 전혀 없음”과 “턴별 원문을 재구성할 수 없음”은 구분해야 한다. E18
