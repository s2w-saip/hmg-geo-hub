기획 결론과 확정 범위

우선 실증: A · Next 16 웹/BFF + FastAPI + Python 워커. 사용자 확인으로 두 언어 운영 제약이 해소됐고, 현 코드에서 확인한 웹 세션 책임을 명시적으로 유지하면서 GEO 업무·분석 계층을 분리할 수 있다. 웹과 API의 추가 배포 비용은 남는다. 따라서 A를 기획 기준으로 먼저 구체화하되 B와 동일 업무로 대조한다. 이것은 착수 순서의 추천이며 성능 우위나 최종 채택 확정이 아니다.

B · React Router SPA + FastAPI 내 BFF를 단순화 대안으로 비교한다. C는 공용 BFF 기반이 있을 때, D는 독립 API가 불필요할 때만 추가 실증한다. 네 제품을 모두 완성하는 방식으로 검토하지 않는다.

사용자 확인(2026-10-08): Python과 TypeScript 모두 운영 가능. 인원·일정·React 숙련도·고객 런타임 승인은 미확인.

구분이번 기획의 전제
사용자 확인Python·TypeScript 운영 가능. 언어를 하나로 줄여야 한다는 전제는 두지 않음.
기존 합의S2W Azure 운영 방향, 공급 RDS ing 직접 읽기. 도구는 전면 재선정 가능하되 발행값·운영 데이터 보존 계약은 유지.
미결H-Cloud Node 22 조건의 적용 범위, Python/Node 24 허용, 실제 IdP·통신·리전·관리형 서비스 승인. 팀 역량 확인은 고객 환경 승인과 다름.
추천 근거와 한계React는 현재 업무 UI와 시각화 자산을 비교할 수 있어 우선 후보. 기존 Next 코드 수 자체를 매몰비용 가점으로 주지 않음. 새 팀이 다른 UI에 강하면 같은 기능으로 재평가.

기존 전체 재설계 검토의 업무·데이터·발행·권한·복구 계약을 이어받는다. 이번 문서는 그 위에 라이브러리·배포 단위·검증 순서를 구체화한 후속 기획이다. 전체 요구·구조 검토 · 이전 판단 스냅샷 (원본 바이트 보관용; 탐색은 현재 검토서 사용)

라이브러리 선택의 이유: FastAPI는 Python 운영과 기존 명시적 SQL·권한 시험을 재사용할 비교 기반이 있고, 업무 API와 분석 워커가 같은 도메인 패키지를 사용할 수 있다. Django는 관리 CRUD가 중심인 제품으로 바뀔 때, 별도 NestJS 도메인 API는 TS 조직 표준이 확정될 때 재검토한다. 현재 C의 NestJS는 웹 BFF 책임에 한정한다. React·Recharts·Tailwind는 실사용 자산이 있어 우선 비교하지만 번들·접근성·교체 비용이 나쁘면 대체한다.

데이터와 오류의 소유자를 하나로 둔다

A/D의 첫 페이지는 RSC에서 1페이지를 읽고, 이후 대화형 데이터가 필요하면 그 결과를 동일 Query key로 hydrate한다. RSC 값과 Query 값을 독립 정본으로 유지하지 않는다. B/C의 route loader는 Query의 동일 조회 함수를 연결한다. BFF의 서버 fetch는 초기 no-store, Query의 화면 상태·재조회·권한 무효화는 새 UI 계약으로 기록한다.

캐시의 기존 결정은 계층·시점별로 다르다. 9/30 API 결정은 제한된 백엔드 분석 GET의 데이터 버전 기반 결과 캐시를 승인했고 코드 기본값은 끔이다. 이를 캐시 전면 금지로 읽지 않는다. A/B 비교는 우선 같은 캐시 설정으로 측정하고, 기존 승인 범위를 넘는 결과 캐시·사전 집계는 별도 ADR로 검토한다. 9/30 결과 캐시 승인 원문

openapi-fetch는 HTTP 오류를 반환 객체의 error로 제공한다. 공통 어댑터가 비정상 응답을 제품 오류로 정규화해 throw하고 Query/화면이 실패로 처리한다. transport 오류·timeout·abort도 구별하며 catch에서 빈 배열/0을 반환하지 않는다. logout·권한 변경 때 범위별 Query를 폐기하고 유료 mutation은 자동 재시도하지 않는다. S09

기본 표는 서버에서 기본 50·최대 100행, 응답 1 MiB 이하를 초기 제안값으로 검증한다. 무한 자동 페이지 수집은 금지한다. 전체 export는 비동기 작업으로 처리하고 total count·본문·집계의 DB 비용을 별도 측정한다. 상한 숫자는 기존 제품 확정값이 아니다.

제품 규칙은 서비스 코드로 소유하고 범용 UI 동작은 재사용한다. 문서 확인: S04 · S05 · S06 · S07 · S08 · S31 · S32 · S33

인증·세션·BFF의 구체적 배치

현재 Next+Supabase 연결은 현재 구현이다. 새 고객 SSO/OIDC 연결은 별도 목표이며 완료된 것으로 보지 않는다. OAuth/OIDC 프로토콜·암호 구현은 검증된 라이브러리를 사용한다.

안프로토콜 후보GEO의 세션·인가 책임
A/DNode openid-client; 기존 Supabase 유지 시 공식 Supabase 어댑터Next 서버가 브라우저 세션과 토큰을 소유. A의 FastAPI는 사용자 식별/권한을 최종 검증; D의 공통 application 모듈도 요청마다 검증.
BAuthlib Starlette/FastAPI 통합web-session 모듈이 로그인·callback·refresh·logout을 소유. API의 Bearer 검증만으로 이 작업이 끝나지 않음.
CNestJS/Fastify + openid-clientBFF에 웹 세션을 통합. GEO 데이터 권한은 FastAPI가 다시 확인. 네트워크 내부라는 이유로 인가를 생략하지 않음.

목표는 HttpOnly·Secure 쿠키의 불투명 세션 ID와 서버 토큰 저장이다. 세션 저장소는 PostgreSQL의 별도 권한 영역을 초기 후보로 두며 메모리만 사용하는 세션은 제외한다. 로그인·갱신·CSRF·로그아웃·권한 철회·다운로드를 같은 조건으로 검증한다. S13 · S14 · S15

A/C의 서버 간 사용자 증명: 고객 IdP가 GEO API용 access token을 발급하면 API가 허용 issuer·audience·서명·만료를 검증한다. ID token이나 브라우저 전달 역할 값을 API 인가에 쓰지 않는다. IdP가 그 계약을 지원하지 않으면 조직 인증 계층의 교환/검증 방식을 먼저 확정하며, BFF가 임의 사용자 헤더를 붙이는 것으로 대체하지 않는다. Supabase 유지 경로와 고객 OIDC 경로는 별도 어댑터이며 검증 전 동등하다고 보지 않는다.

SSO의 (issuer, subject)를 기존 계정 ID·프로젝트 membership에 명시적으로 매핑하고 이메일 문자열만으로 계정을 합치지 않는다. B/D도 동일 계정·범위 정본을 조회한다. QA 별도 게이트는 고객 SSO 전환에 섞지 않는다.

인증 라이브러리가 대신하지 않는 운영 계약

책임설계·실증 조건
세션 저장A/C의 웹 세션 전용 PG 어댑터는 postgres 드라이버, B는 SQLAlchemy Core, D는 공통 Drizzle 계층. BFF DB 권한은 세션 영역에 한정. 불투명 쿠키 ID의 해시·만료·철회 상태와 암호화된 토큰을 서버에 저장. 공급 토큰·원문을 쿠키 payload에 넣지 않음.
동시 refresh세션 revision + 짧은 lease/CAS로 갱신 경쟁 제어. 외부 IdP 호출 중 DB 트랜잭션을 유지하지 않음. 다중 인스턴스·refresh rotation·프로세스 중단·logout 이후 늦은 응답을 검증하고 오래된 실행자의 저장을 거부.
CSRF·callbackAuthlib/openid-client의 state·nonce·PKCE 검증을 실제 IdP에서 시험. 같은 origin의 변경 요청은 CSRF token·Origin 검증, 허용 callback/redirect 목록 적용. SameSite만으로 방어가 끝났다고 보지 않음.
철회·QA·신뢰 헤더서버 세션 철회와 도메인 계정/범위 확인을 함께 수행. QA는 별도 쿠키·범위·감사 경계 유지. ingress가 외부의 내부용 identity/IP 헤더를 제거하고 신뢰 프록시를 고정.
다운로드권한 철회 즉시 차단이 필요하면 다운로드 gateway가 요청마다 인가하고 비공개 Blob을 읽어 전달. SAS/서명 URL을 발급하면 이미 발급한 URL의 유효기간 동안 잔여 접근 가능성을 명시하고 허용 기준을 별도 결정.

Starlette SessionMiddleware의 서명 쿠키는 내용이 읽힐 수 있다. 그 예제를 서버 토큰 저장 구현으로 복사하지 않는다. 서버 세션 어댑터·암호키 교체·TTL 정리·CSRF 연결은 구현과 운영 비용에 포함한다. S15 · S38

PostgreSQL 17을 우선 검증하고 대형 원문·파일은 객체 저장소에 둔다. 캐시·집계 추가는 기존 D8/A5 결정과 변경점을 기록해야 한다. Redis·ClickHouse·검색/벡터 DB·Kafka는 현재 기본 구성에서 제외한다.

A/B/C의 GEO·세션 스키마 migration owner는 Alembic 배포 작업 하나, D는 Drizzle Kit 배포 작업 하나로 둔다. API·worker·웹 기동 때 각자 DDL을 실행하지 않는다. 읽기 API·업무 쓰기·세션·수집·분석·migration의 DB 역할을 나누고 최대 replica 수까지 반영해 총 연결 예산을 정한다. 병렬 작업 사이에 하나의 transaction/session 객체를 공유하지 않는다. request timeout 때 SQL 취소와 statement timeout도 검증한다.

공급 읽기는 허용된 RDS 복제본/VPN 경로에서 제한된 배치로 수행한다. 체크포인트는 로컬 원문·해시·수신 원장 커밋과 연결하고, load_id 순서만으로 늦은 commit·수정·삭제가 모두 잡힌다고 가정하지 않는다. 겹침 구간 재조회·내용 해시 대조·삭제 신호/전체 대조 및 재수집 조건을 공급 계약으로 확정한다. 외부 DB·Blob·모델 호출과 로컬 DB 사이의 단일 원자 트랜잭션을 전제하지 않는다.

작업 실행기·AI 판단·실패 복구

장기·다단계·검수 대기 작업에는 Temporal을 우선 실증한다. Python SDK는 A/B/C, TypeScript SDK는 D 워커에 둔다. Temporal 서버 또는 Cloud의 허용 환경·운영 책임은 별도 확인한다. Azure 관리형만 허용될 때는 Durable Functions를 비교한다. Celery/BullMQ는 단순 작업 큐 요구에는 후보지만 이번의 장기 상태·검수 대기를 같은 비용으로 제공하는지 확인 전 추가하지 않는다. S17 · S18 · S44 · S45

업무 작업 원장과 outbox를 같은 PG 트랜잭션으로 접수하고 실행기로 전달한다. 실행 이력은 workflow가, 업무 결과·발행 정본은 PG가 소유한다. 외부 I/O와 모델 호출은 Activity 경계에 둔다. 단순 독립 작업뿐이면 PG 작업 큐 후보를 다시 비교한다.

실행기 선택실증에서 확인할 책임도입 경계
Temporal 우선 실증서비스/Cloud 접근·보관·지역·비용, deterministic workflow·Activity timeout/heartbeat·취소·worker 버전 호환·장기 이력 분할워크플로 제어기는 기본 서비스 외 운영 단위다. managed 승인 시 Cloud 후보, self-host는 DB·복구·업그레이드를 맡을 운영자가 있을 때만.
Azure Durable Functions 조건부동일 업무의 orchestration replay·활동 재시도·검수 대기·상태 보관·관측·함수 호스팅 제약Temporal과 함께 도입하지 않음. Azure 선택만으로 Durable가 자동 채택되는 것은 아님.
PG 큐 조건부짧고 독립된 작업에 한해 claim/lease·heartbeat·retry·dead letter·스케줄링·운영 UI를 포함한 비용외부 서비스 하나가 줄어도 내구성·관측 코드는 남음. 장기 검수·다단계 분석을 단순 cron+메모리 상태로 축소하지 않음.

재시도와 유료 호출은 명시적인 상태 기계로 다룬다

업무 operation의 멱등 키, outbox 전달 ID, workflow ID, 외부 시도 ID를 구분한다. PG 커밋 후 전달 실패는 재전송하고 같은 workflow 시작을 중복 수용하지 않는다. Activity의 DB 결과 쓰기는 unique key·현재 실행 세대 확인으로 중복과 늦은 쓰기를 막는다. 큐 전달과 외부 과금이 exactly-once라고 보장하지 않는다.

TypeSafe·공급 API가 요청 멱등 키/상태 조회를 지원하는지 각각 확인한다. 응답을 받지 못한 유료 호출은 outcome_unknown으로 기록하고 자동 재청구 대신 대조·검수 경로를 둔다. SDK·HTTP·workflow가 각각 retry해 시도 수가 곱해지지 않도록 재시도 소유자는 workflow로 통일하고 SDK 정책을 명시한다. 취소 요청 후 늦게 온 결과는 보존하되 발행에 섞지 않고 실제 외부 과금과 취소 완료를 구별한다. S17 · S36 · S37

workflow payload에는 원문 대신 권한 영역·원문/판정 ID·버전 등 최소 참조를 넣는다. 원문·토큰·모델 응답이 workflow history/검색 속성에 무분별하게 남지 않도록 한다. 모델 결과 캐시는 격리 영역+정규화 입력/근거 hash+질문/사전/모델 버전의 멱등 원장으로 만들고 동시 계산은 lease와 결과 unique 제약으로 합친다.

Azure 배포가 돌아가기 위한 추가 조건

공용 ingress는 TLS·같은 origin 경로를 제공한다. A는 Next, B는 정적 웹과 API의 경로 분기, C는 정적 웹과 BFF, D는 Next로 연결한다. 브라우저가 A/C의 내부 API를 우회하지 않게 제한한다. 원본 데이터를 내보내는 외부 통신은 TypeSafe/IdP/공급별로 허용 범위를 확인한다.

워커에 ingress를 끄고 scale rule도 없이 minReplicas=0을 두면 깨울 경로가 없다. 초기 poller/dispatcher는 minReplicas≥1을 비용 가정에 포함하거나 검증된 backlog trigger를 둔다. HTTP의 scale-to-zero 콜드 시작과 DB 연결 폭증을 시험하고, rolling 중 구·신 worker가 동시에 결과를 쓰는 상황을 차단한다. Next 인스턴스 간 세션·암호키·빌드 전환도 같은 시험에 포함한다. S19 · S20

경보는 5xx뿐 아니라 200+빈값 대조, 수신/분석/발행 신선도, outbox 최대 대기, outcome_unknown, DLQ/검수 대기, DB 연결 포화·cancel 실패를 포함한다. 요청 trace와 업무 operation ID를 연결하되 원문·쿠키·토큰·키 값을 trace attribute에 넣지 않는다.

실증 이후의 선택 규칙

안최종 선택으로 올릴 증거현재 처분
A브라우저 경계와 독립 API의 편익이 있고 추가 홉/배포 비용이 허용 범위. 기존 자산 재사용량은 실제로 측정.추천 기획 기준·우선 실증. B 대비 우승 확정은 아님.
BAPI 세션/CSRF/다운로드 인수가 동등 기준으로 통과하고, 필요한 화면 동작과 총비용이 A보다 유리하다는 증거.A와 같은 얇은 업무 경로로 비교. SSR 필요가 없다는 이유만으로 자동 채택하지 않음.
C이미 제공되는 공용 BFF 또는 복수 UI·조직 소유권의 구체적 이점이 새 서비스 비용을 상쇄.그 근거가 없으므로 지금 별도 BFF 구현 착수 제외.
D독립 API의 외부 클라이언트/배포/언어/조직 이점이 작고 TS domain/worker로 옮긴 총비용이 유리.웹/API 통합 실증 필요가 생길 때 추가. Python도 운영 가능한 현재 조건에서 언어 통일만을 목적으로 우선하지 않음.

첫 개발 묶음은 공통 계약/fixture → 권한 있는 목록·상세 → 세션·오류 경계 → 작업 접수·export·취소 → A/B 측정 순서다. 별도 API 이점이 처음부터 없다고 확인되면 큰 FastAPI 구축 전에 D의 얇은 기능을 추가 비교한다. 기능 전체 이관은 스택 선택과 복구 게이트를 통과한 뒤 시작한다.

이번 기획의 3회 순차 검토

이번 기술 스택 기획은 앞선 아키텍처 3회 검토·Next 근거 후속 검토와 별개다. 동일 작성자가 앞 회차 수정본을 다시 검토한다. 독립 3인 심사나 앱 실증 결과가 아니다. 현재 3/3회 수정 반영.

1차 · 요구·원래 선정 근거·팀 조건·지원 버전 적합성

초안 HTML과 초기 Next 결정, 인수 문서, 현재 선언 의존성, 공식 지원·클라이언트 계약 문서를 대조했다. A~D 구성과 후속 요구를 유지한 채 아래 4개 묶음의 본문을 보완했다. 설치·앱 실증은 하지 않았다.

S1-01 · 두 언어를 운영하는 팀 조건이 고객 환경 승인과 혼동될 수 있고 React 우선 이유가 약했다.

수정: 사용자 확인·기존 합의·미결·추천을 표로 분리. H-Cloud/Python/Node24 승인 미결과 React 자산 비교 근거·전면 재작성의 매몰비용 배제를 명시.

근거: 사용자 응답, 인수 올인원 H-Cloud/Azure/Node22 기록, 초기 Next 선정 design.md · 본문 recommendation · variants

S1-02 · Next의 신규 메이저와 Node의 지원 종료를 포함한 운영 기준이 불명확했다.

수정: A/D Next16·React19, Node24 LTS 신규 목표와 Node22 허용 환경 분기 및 종료 전 전환 조건을 명시. 정확 버전 잠금·조합 검증, async RSC의 E2E 범위를 구분.

근거: Next 지원 정책·Vitest 문서, Node 공식 schedule.json, 현재 front/package.json · 본문 variants · platform

S1-03 · SSO 라이브러리와 도메인 API 사이의 사용자 증명·계정 이관 계약이 빠졌다.

수정: API audience/issuer의 access token 검증과 미지원 시 인증 계약 선결을 추가. ID token·임의 역할 헤더를 인가에 쓰지 않고 issuer/subject를 기존 계정에 명시적으로 연결.

근거: 현 Next auth.ts·API core/auth.py, openid-client·Authlib 공식 프로토콜 지원 · 본문 auth

S1-04 · Query·RSC·loader의 데이터 중복과 openapi-fetch의 오류 반환을 처리할 책임이 부족했다.

수정: 첫 페이지와 후속 Query의 단일 조회 소유, no-store·권한 캐시 무효화, 오류 어댑터의 throw, mutation retry 제한과 서버 페이지/응답 초기 상한을 추가.

근거: TanStack Query/Table와 openapi-fetch 공식 응답 계약, 기존 D8·silent failure 개선 요구 · 본문 ui · domain

2차 · 세션·동시성·유료 재시도·데이터 정합성·실제 배포 실패

1차 수정본의 인증·DB·워커·배포 경계를 장애 상황에 대입했다. 서명 쿠키와 서버 세션, SDK 재시도와 workflow 재시도, ingress 없는 worker의 scale-to-zero 제약을 공식 문서로 대조하고 5개 묶음을 수정했다. 장애 주입 실행 결과는 아니다.

S2-01 · 세션 저장 기술만 있고 refresh 경쟁·CSRF·QA·다운로드 철회의 실제 계약이 부족했다.

수정: 안별 세션 PG 어댑터, 토큰 서버 저장, lease/CAS·revision, CSRF/Origin·callback 제한과 QA/신뢰 헤더를 명시. signed cookie의 읽기 가능성과 서명 URL의 잔여 접근을 구분.

근거: Starlette SessionMiddleware, OWASP CSRF, 초기 BFF·현행 QA 경계 · 본문 auth

S2-02 · API와 worker의 공유 코드만으로 migration·연결 예산·외부 저장 정합성 책임이 정해지지 않았다.

수정: 안별 단일 migration owner·DB 역할·replica 포함 연결 예산, 취소/timeout을 정의. 공급 늦은 commit/수정/삭제 대조, Blob 확정/고아 회수, Python/TS export와 Azure SDK를 구체화.

근거: SQLAlchemy·Alembic·Drizzle, 10/7 RDS 읽기 합의, Azure Blob·XlsxWriter 문서 · 본문 domain

S2-03 · Temporal 제품명만으로 제어기 운영·버전 호환·대체 실행기의 비용이 드러나지 않았다.

수정: Temporal Cloud/self-host, Durable Functions, PG 큐의 배타적 선택과 운영 조건을 추가. worker 버전·긴 이력·검수 대기·큐 복구를 제품 선정 책임으로 명시.

근거: Temporal Activity/개발 문서, Durable Functions 개요, 장기 분석·검수 요구 · 본문 worker

S2-04 · 다중 retry·유료 호출 결과 불명·취소 후 늦은 쓰기와 AI 캐시 동시성 처리가 빠졌다.

근거: Temporal Activity 재시도/멱등 책임, TypeSafe Python/JS retry 공식 문서 · 본문 worker

수정: 안별 ingress 경로·내부 API 우회 방지, min replica 또는 backlog trigger, rolling worker 충돌과 세션 공유 조건을 명시. 작업/데이터 상태 기반 경보와 trace 비밀 배제를 추가.

근거: Azure Container Apps scale 문서의 ingress 없는 0 replica 제약, 기존 품질 개선 요구 · 본문 platform

3차 · 비용·선정 규칙·구현 착수·전환 수용 가능성

2차 수정본을 개발 착수 문서로 읽고 추천의 증거, 누락된 계약 생산자, 측정/비용/복구 게이트를 점검했다. 아래 4개 묶음을 보완한 최종 기획이다. 문서 표시·해시 검증은 별도 QA 기록에 남기며 앱 성능·보안·비용은 아직 실증하지 않았다.

S3-01 · A 우선 이유가 추상적이고 다른 후보를 최종 선택할 증거·추가 구현 조건이 약했다.

수정: 사용자가 확인한 두 언어 운영과 현재 웹 세션 책임을 A의 착수 근거로 명시. B의 인수/총비용 조건, C의 공용 BFF 근거, D의 독립 API 불필요 조건과 조기 비교 분기를 정리.

근거: 사용자 팀 조건, 초기 Next BFF·현 auth 코드, 네 안의 실제 배포 책임 비교 · 본문 recommendation · execution

S3-02 · 좋다는 판단을 내릴 측정 범위·실패 조건·전체 비용 항목과 기존 성능 기준이 충분히 구체적이지 않았다.

수정: 권한·발행·전체 읽기 API cold p95 1초/10배·20분 반영·대량 목록·작업·복구 게이트를 정의. 대표 PoC와 전체 API 검증을 구분하고 초기+12개월 비용식·미결 체감 예산을 추가.
