이번 리팩토링에서 바뀐 범위

기준 복사본 f6f6f54와 점검 기준 ec3f3f6를 비교하면 back/app/core, back/app/features/analytics, back/db에 변경이 없다. 기존 읽기 모델·분석 집계·결과 캐시는 인수한 구현을 유지했다. 신규 화면 조회 API 4개가 추가되었다는 사실만으로 이 영역까지 최적화됐다고 판단할 수 없다.

프런트 API 클라이언트는 cache: "no-store"를 사용한다. 대시보드 React cache의 공유 범위는 같은 요청 안이며 사용자 새로고침 간 공용 결과 캐시가 아니다. 백엔드 결과 캐시와 구분해야 한다. API/legacy 전환 설정에 따라 직접 DB 조회 또는 FastAPI를 사용하므로 실제 배포 경로도 함께 확인해야 한다.

로컬 Next 개발 실행에서 production 실행으로 바꿔 빨라진 결과는 빌드·프런트 실행 방식의 개선 증거다. 운영 DB 집계 최적화가 끝났다는 근거로 사용하지 않는다.

전체 내보내기와 전체 선택은 사용자가 요청한 전체 작업이다. 본문 전체를 첫 화면에서 자동 로드하는 문제와 구분하며, 기존 기능을 없애거나 임의로 결과를 자르지 않는다.

서버팀 전달 및 후속 개발 범위

  1. 신규 조회 API 4개: DB 수준 페이지네이션·전체 범위 필터/정렬·정확한 총건수·권한을 유지한다. 필터 옵션과 태그 후보를 매 페이지 다시 계산하지 않도록 변경 감지와 재사용 전략을 설계한다. 태그 후보를 임의로 잘라 기존 동작을 바꾸지 않는다.
  2. 남은 대량 조회: 소셜 스크래핑은 표시할 생성 문구의 후보 등록 여부만 일괄 확인하는 방식 등을 검토한다. Google 키워드 탭도 기존 접근·선택 기능을 보존하면서 조회를 분리한다. 두 경로 모두 잘림을 정상 전체 결과로 취급하는 동작부터 해결한다.
  3. 대시보드: 기존 결과 캐시의 사용 조건·권한 키·적재/검수/설정 변경 시 무효화를 검증한다. 미적중 요청의 비용을 측정한 뒤 필요한 지표만 사전 집계하거나 기존 발행값을 재사용한다. 지표의 모수·기간·브랜드·회차 규칙은 유지한다.
  4. 완료 판정: 운영을 대표하는 비운영 데이터에서 첫 요청·반복 요청·필터 변경·깊은 페이지·동시 요청을 비교한다. SQL 실행계획, 처리 행 수, 버퍼 읽기, 정렬 비용, API 지연 분포, 응답 크기, 캐시 적중과 변경 반영을 확인한다. 허용 지연 목표를 정하고 기존 결과와 동등성도 검증한다.

위 항목은 후속 작업 제안이다. 이번 점검에서는 캐시 활성화·API 변경·DDL 변경·성능 부하 시험을 수행하지 않았다. 실제 서버 반영과 운영 성능은 미검증이다.
