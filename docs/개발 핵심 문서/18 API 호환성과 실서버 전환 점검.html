기존 API 계약은 유지했습니다. 현재 프런트를 원본 백엔드에 주소만 바꿔 연결하는 것은 충분하지 않습니다.

확인 결과

기존 214개 API + 기존 602개 스키마는 변경·삭제 0개입니다. 다만 읽기 전용 API 4개와 스키마 10개를 추가했고, 수정 프런트의 API 모드 목록은 새 경로를 호출합니다. 현재 합계는 218개 API·612개 스키마입니다.

대조 기준은 원본 커밋 392ca454, 복사본 문서 커밋 7fedc29(애플리케이션 수정 b67d5eb)입니다. 실제 배포 서버의 코드 버전은 확인하지 않았습니다.

원본과 복사본에서 API 명세를 각각 다시 생성했습니다. 네트워크가 차단된 컨테이너와 읽기 전용 소스 마운트를 사용했고, 두 결과 모두 각 저장소의 OpenAPI와 일치했습니다. 기존 요청·응답·오류 응답 정의를 포함한 기존 operation 객체와 스키마를 전체 비교했습니다.

실제 연결에 필요한 반영

  1. 백엔드 버전: 추가된 4개 경로가 포함된 수정 FastAPI를 먼저 반영합니다. 실제 서버가 아직 원본 버전이면 주소 변경만으로는 목록을 사용할 수 없습니다.
  2. 프런트 빌드: 실제 NEXT_PUBLIC_SUPABASE_URL·NEXT_PUBLIC_SUPABASE_ANON_KEY로 다시 빌드합니다. 현재 로컬 빌드의 서버 JS 4개에서 모의 인증 URL이 실제로 포함된 것을 확인했습니다. 주소 하나만 바꿔 기존 로컬 빌드를 재사용하지 않습니다.
  3. 서버 환경: HGH_API_BASE_URL과 HGH_SOURCE_SESSION/G1~G7을 실제 구성에 맞춥니다. 소스 플래그가 없으면 legacy가 기본입니다. legacy와 API는 데이터 연결 경로가 다르므로 플래그를 임의로 섞지 않습니다.
  4. 인증·계정: 백엔드 HGH_JWKS_URL·HGH_JWT_ISSUER·audience가 실제 인증 프로젝트와 맞아야 하며, JWT 사용자 ID와 DB의 활성 계정·권한이 연결돼 있어야 합니다. 로컬 시험 계정은 운영 계정으로 사용할 수 없습니다.
  5. 로컬 장치 제외: 로컬 launcher는 주소를 127.0.0.1로 고정하고 NODE_OPTIONS에서 e2e/lib/no-egress.cjs를 로드합니다. 이 외부 fetch 차단 장치를 실제 연결용 실행에 포함하지 않습니다. 이 점검에서 차단 장치를 해제하거나 실제 서버로 연결하지는 않았습니다.
  6. DB·연동: 이번 리팩토링에 DDL 변경은 없지만, 대상 DB가 원본의 스키마·권한·데이터를 갖춰야 합니다. 새 정렬 조회는 en-x-icu·ko-x-icu를 사용하므로 실제 DB의 사용 가능 여부를 확인해야 합니다. GA4·Scope·DataForSEO와 QA 설정은 해당 기능을 사용할 때 실제 환경에 맞춰야 합니다.

계약 유지와 동작 개선의 구분

기존 백엔드 app 파일 658개를 대조했습니다. 기존 파일 중 4개 라우터에 조회 함수만 추가됐고, 기존 함수·클래스 정의 변경은 없었습니다. Next의 app/api, 인증·Supabase 연동, DB DDL도 기존 파일 내용이 유지됐습니다.

오류 처리 동작은 의도적으로 바꿨습니다. QA 저장·잠금 실패를 성공처럼 표시하지 않고, 대량 태그 부분 저장을 구분하며, Scope/DFS 결과 불명 작업의 자동 재전송을 막습니다. Scope 요청 경로·본문은 유지하지만 POST의 429/5xx 자동 재시도 정책은 변경했습니다. 따라서 ‘기존 HTTP 계약 유지’를 ‘모든 오류 상황의 처리도 과거와 동일’하다는 뜻으로 쓰면 안 됩니다.

현재 운영 서버의 버전·환경 변수·DB·실제 인증·외부 응답은 미검증입니다. 이번 확인은 파일 대조와 네트워크 차단 환경의 명세 생성만 수행했으며, 운영 서버 요청·로그인·데이터 변경은 0회입니다.
