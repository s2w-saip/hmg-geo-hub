통계 데이터별 사전 집계·적재 설계

수집·재판정이 끝날 때 통계를 계산하고, 화면에서는 준비된 집계값과 필요한 식별자 집합을 읽습니다.

기존 14개 지표 묶음과 키워드·상세 통계·측정 모수 보완 항목을 대상으로 저장 단위, 컬럼, 갱신 조건, 읽기 경로를 정리했습니다. 화면·산식·필터·권한·API 응답은 유지합니다.

상태: 구현 전 설계 제안 · 기준 코드: 복사본 refactor/preserve-service / 15e0b1c · 운영 요청·DB 접속·DDL 적용 없음
새로 제시하는 stat.* 이름은 논리 설계용입니다. 기존 rd·frz·summary와 중복되는 저장소는 구현 시 재사용합니다.

설계 원칙지표별 적재표산식 보존테이블·키필터·권한갱신·발행조회 경로구현·검증코드 근거

1. 권장 구조와 적용 범위

① 수집 결과와 통계를 분리기존 ing → rd 투영 뒤에 통계 빌드를 둡니다. API 요청 중 원문 언급·인용을 다시 결합해 통계를 만드는 작업을 워커로 옮깁니다.
② 합계와 중복 제거를 구분횟수·분자·분모는 집계 테이블에 저장합니다. 프롬프트·답변·URL 고유 수는 식별자를 남겨 필터 적용 후 정확히 셉니다.
③ 완성된 버전만 공개새 통계를 별도 세대에 적재하고 검증한 뒤 읽기 포인터를 전환합니다. 실패·늦은 데이터·재발행은 상태와 버전으로 관리합니다.
1 · 기존 수집·판정ing / rd / 판정 변경 큐
2 · 입력 스냅샷 확보모수·회차·규칙 버전 고정
3 · 통계 적재필터용 최소 행 + 합산용 집계
4 · 검증·활성화동등성·누락·중복 검사
5 · 기존 API 조회집계 합산·집합 병합·표시 정렬

처음부터 모든 필터 조합별 완성 응답을 저장하지 않습니다. 프롬프트×엔진×국가 등의 기본 셀과 자주 사용하는 상위 합계를 저장합니다. 여러 국가·엔진·기간을 합치는 요청은 작은 집계를 합산하고, 고유 수·순위처럼 필터에 따라 달라지는 결과만 조회 시 마무리합니다.

따라서 목표는 반복되는 대형 사실 테이블 JOIN과 판정 계산을 조회 경로에서 제거하는 것입니다. 모든 요청을 단일 행 SELECT로 바꾸거나, 모든 JOIN·COUNT DISTINCT를 없앤다는 설계는 아닙니다. 상세·복합 필터에서는 범위가 제한된 얇은 투영을 읽으며 실제 효과는 실행 계획과 응답 시간을 측정해야 합니다.

기존 자산을 활용합니다. rd.answer의 언급·순위·인용 판정 열, rd.acr_cell/choice, rd.report_unit_value, frz와 기존 summary는 이미 계산 결과를 일부 보관합니다. 이 정의를 빌더에서 재사용하며 새로운 산식으로 다시 해석하지 않습니다. 특히 기본 프로필 off를 current로 바꾸거나, live 읽기를 임의로 동결 읽기로 전환하지 않습니다.

인덱스·파티션·용량의 출발점

공통 조회는 (generation_id, population_key, surface, project_key, cyc_key, engine_key, geo_key) 및 prompt/date 접근을 우선 후보로 삼습니다. 인용 구성원은 (generation_id, source_key, prompt_key), (generation_id, url_key), 답변 참조 인덱스를 검토합니다. GA4는 property·date 범위가 먼저 제한되어야 합니다. 모든 조합에 인덱스를 만들지 않고 대표 쿼리의 EXPLAIN으로 결정합니다.

대형 member는 기존처럼 surface와 날짜 범위 분할을 우선 검토하고, 작은 요약표는 우선 비파티션으로 둡니다. 실제 unique/PK에는 파티션 키 제약을 반영한 DDL 검토가 필요합니다. 셀 수가 답변 수와 거의 같거나 관점·모드 복제로 커지면 그 rollup의 물리화 범위를 줄입니다. QA의 가변 상태 열에는 불필요한 covering index를 늘리지 않습니다.

용량 추정은 실제 distinct(C)·인용 원소 수·ACR 엔티티 수·GA4 페이지 수에 사용 관점/프로필 수, 보존 세대 수, 인덱스 크기를 곱해 산정합니다. 운영 건수·증가율·디스크·목표 p95를 측정하지 않았으므로 용량과 지연 수치를 확정하지 않았습니다.

6. 필터와 권한을 잃지 않는 조회 규칙

조건설계
국가·브랜드·프로젝트·표면 권한기존 principal/scope resolver로 허용 집합을 먼저 계산. 권한으로 분리할 수 없는 상위 합계는 읽지 않음. 전체 통계를 읽은 뒤 화면에서 숨기는 방식 금지. 접근 권한 철회는 통계 재빌드와 무관하게 즉시 적용.
택소노미·커스텀 필드·검색기존 의미대로 조건을 적용해 적격 prompt_key 집합을 만들고 C에 EXISTS. 같은 프롬프트에 여러 카탈로그/태그가 있어도 가산 값이 배수로 늘지 않음. 축별 AND/OR와 삭제 카탈로그 포함 규칙 유지.
기간·회차·대표 선택현재 Window resolver가 선택한 family별 회차·날짜·숨김/노출 게이트를 그대로 사용. rollup이 표현하지 못하는 창/대표 조건은 answer_fact 등 좁은 투영으로 계산하고 그 경로의 비용을 별도 검증.
source[]·관점·언급 브랜드인용 category/owner 축과 answer_brand_member를 사용. M05와 자사 인용을 분리. 선택한 관점과 프로필에 준비된 집계가 없으면 다른 관점의 합계로 대체하지 않음.
필터 옵션·0건 항목옵션용 모수는 화면 데이터용 모수와 별도 계약. 예: ACR 언어 옵션은 언어·엔진·택소노미 필터 일부를 제외하며 국가 옵션은 계정 범위에 맞춤. QA 옵션의 현재 0건 항목과 GA4 미적재 시장도 유지.
전체 합계·정렬·페이지필터한 전체 결과에서 분모/순위를 결정한 후 검색·페이지 단계를 기존 순서대로 적용. page 크기나 Top N이 분모를 바꾸지 않음. 기존 반올림 기반 정렬·타이브레이커·커서·내보내기 계약 유지.
캐시기존 캐시 키에 release/generation, profile·metric_version, 권한 범위 버전 및 정규화 필터를 반영. GA4·QA를 임의 TTL로 묶지 않음. 캐시는 보조이며 준비되지 않은 집계를 완성시키는 수단이 아님.

7. 언제 계산하고, 어느 범위만 다시 적재할 것인가

발생 사건빌드/교체 단위반영할 지표공개 규칙
수집 배치 성공 / 회차 마감변경된 표면·프로젝트·회차. GA4는 property×date, 소셜은 snapshot해당 S01~S12·S16~S17 및 독립 외부 지표raw 저장만으로 완료 처리하지 않음. rd 투영·게이트·대표 선택까지 완료된 입력에서 빌드. 진행 중 회차의 live 갱신도 배치 완료 단위로 지원.
답변·인용 정정/삭제, ACR 반복 변경해당 답변의 이전·새 소속 회차, 대표 교체의 영향 회차KPI·언급·인용·ACR·추이·URL·모수영향 슬라이스를 새 세대로 교체. 사라진 행과 0건이 된 결과도 명시적으로 교체.
출처 분류 override / 소유·추적 URL 변경source_key·owner_key·project로 역추적한 회차인용 분포·M05·자사 인용·URL·추이판정 투영과 통계가 같은 버전이 될 때 전환. 기존 발행값을 자동 수정하지 않음.
엔티티·별칭·통합 관점 규칙 변경영향 브랜드/엔티티의 회차, 연결 ACR 셀언급·순위·유형·톤·ACR·경쟁사현재 rule_ver와 metric_version의 차이를 기록. 필요한 계열이 모두 준비되어야 해당 묶음 전환.
카탈로그·퍼널·커스텀·등록/삭제 변경옛·새 scope_prompt/project 연결 및 관련 회차모수·필터·주제·URL 등록 게이트·대표 선택에 영향단순 축 변경은 축 버전만 갱신 가능. 모수/게이트 변화는 기반 집계 재생성. live와 frozen의 기존 반영 시점 구분.
회차 숨김·노출일·고정/드롭창/세대 선택 메타, 필요 시 대표 셀해당 family 전체숨김/권한은 기존 조회 게이트에서 즉시 반영. 대표 집합이 바뀌면 재빌드; 누락 회차·비교 억제 의미 유지.
발행 후 늦게 들어온 데이터live의 영향 슬라이스 및 재발행 후보원천에 영향받는 전체 통계발행본은 유지하고 stale/재발행 대기 상태 기록. 기존 명시적 재발행 절차를 통과한 새 frz/pub 세대만 활성화.
GA4 재수집·이벤트 기준 변경해당 속성의 영향 날짜 전체. 규칙 변경이면 보존·노출 기간의 관련 날짜요약·일별·엔진·시장·페이지·이벤트덧셈 upsert가 아닌 날짜 슬라이스 교체. 늦은 GA4 정정도 반영. 전체/페이지 보고서 준비 상태와 coverage를 별도로 검증.
QA 저장/노트 변경job 현재 상태와 해당 카운터S13같은 트랜잭션. 노트 0→1은 notes +1, 1→2는 변동 없음, 마지막 삭제 1→0은 −1. 재시도에서 중복 가산 금지.
소셜/키워드 수집 성공snapshot 또는 성공 call/관측 버전S14·S15실패한 신규 결과로 성공한 기존 포인터를 덮지 않음. 스냅샷 내 통계·상세가 함께 준비된 후 공개.

초기 구현은 영향 회차/속성·날짜를 통째로 새로 계산하는 방식을 권장합니다. 수정·삭제·대표 교체·중복 제거가 많아 모든 KPI를 +1/−1 이벤트로 유지하면 복구가 복잡해집니다. 작은 QA 현재 상태 카운터만 트랜잭션 차등 갱신으로 시작하고, 나머지는 실제 빌드 병목이 확인된 계열부터 증분 최적화합니다.

실패·재시도·동시 실행을 처리하는 제어 테이블

  1. 입력 확정: 기존 수집/재판정 트랜잭션에 완료 이벤트를 내구성 있게 남깁니다. 기존 outbox·judgment_change 흐름에 연결하고 큐 전달 누락은 재조회로 복구합니다. 단순 MAX(load_id)는 커밋 순서나 전체 완료를 보장하지 않으므로 완료 집합/연속 적용 경계를 기록합니다.
  2. 일관된 추출: live rd는 갱신 가능한 테이블입니다. 여러 워커가 같은 load_id 이하를 읽는 것만으로 과거 상태가 복원되지 않습니다. 단일 일관된 DB 스냅샷에서 필요한 좁은 입력을 불변 staging으로 추출하거나 같은 snapshot을 공유합니다. 트랜잭션 장기 유지 비용을 측정하고, 이후 집계는 그 staging에서 수행합니다. frozen도 정확한 frz 세대를 고정합니다.
  3. 격리 적재: build_id 아래에 새 행을 작성합니다. 서로 독립적인 계열 작업도 하나의 입력 스냅샷과 의존성 manifest를 참조합니다. 재시도는 같은 출력의 교체/재개이며 기존 활성 통계에 SUM을 더하지 않습니다.
  4. 검증: 키 중복·필수 계열 누락·모수·원합·발행 출처·동등성 검사를 통과해야 validated. 유형 중복·GA4 이벤트 수 등 허용되는 관계에 잘못된 등식/상한 제약을 걸지 않습니다.
  5. 원자적 공개: 짧은 트랜잭션에서 기대하던 기존 release와 입력 버전을 확인한 뒤 새 manifest 포인터를 전환합니다. 독립 빌드가 먼저 공개되었다면 현재 manifest에 자기 변경을 다시 합쳐 검증하여 타 작업의 갱신을 잃지 않게 합니다. 오래된 빌드가 새로운 입력 버전을 덮지 못하게 합니다.
  6. 읽기·보존: API 요청 시작에 release_id를 한 번 고정하고 필요한 build를 읽습니다. 이전 세대는 진행 중 요청·커서·발행본·롤백 참조가 끝날 때까지 보존합니다. 해제되지 않은 frz/pub 참조는 정리하지 않습니다.
실패 시 동작: 실패한 build는 공개하지 않고 오류/재시도 상태를 기록합니다. 이전 정상 세대를 계속 보여줄 수 있는지는 기존 freshness·발행 계약에 따릅니다. 더 최신 상태가 필요하거나 최초 정상본이 없으면 기존 대기·오류 경로로 응답합니다. 실패를 empty/0/성공으로 바꾸거나 자동으로 대형 원문 JOIN을 실행하는 폴백은 두지 않습니다. 새로운 사용자 표시나 응답 필드가 필요하면 API 계약 변경으로 별도 다룹니다.

QA의 예외: 검수 리뷰·노트와 app.qa_stat_job/counter 갱신을 한 트랜잭션에 둡니다. job 단위 잠금·상태 버전을 사용해 before/after 차이를 한 번만 적용하고, 여러 카운터는 고정 순서로 잠급니다. loader의 job 수정도 같은 일관성 경계에서 투영해야 합니다. 정기 전체 대조/복구는 보완책이며 정상 요청의 즉시 일관성을 비동기 큐로 대체하지 않습니다.

혼합 세대 범위: 한 API 응답과 서버에서 한 번에 조립하는 화면 데이터는 동일한 release를 고정합니다. 브라우저가 별도 시점에 보내는 여러 API 요청까지 완전히 같은 세대로 묶으려면 기존 내부 BFF 요청 맥락에서 공유할 수 있는지 확인해야 합니다. 현재 계약만으로 화면 전체의 원자적 스냅샷을 보장한다고 주장하지 않습니다. GA4·소셜은 원래 수집 주기가 다르므로 동시 시각의 데이터라고 표현하지 않습니다.

페이지 안정성: 기존 커서가 입력 버전을 고정할 수 있으면 release 참조를 서버 내부에 유지합니다. 불가능하면 현행 커서의 변화 허용/무효화 계약을 유지하면서 경계 중복·누락을 검증합니다. 임의로 새 필수 cursor 파라미터를 요구하지 않습니다.

왜 전부 Materialized View로 만들지 않는가

PostgreSQL의 Materialized View는 결과를 실제 저장하지만, 기본 REFRESH는 정의 쿼리를 다시 실행해 내용을 교체합니다. CONCURRENTLY에는 이미 채워진 뷰와 전체 행을 대상으로 하는 적절한 UNIQUE 인덱스 등의 조건이 있습니다. PostgreSQL 17 저장 뷰 설명 · REFRESH 공식 문서.

GEO HUB에는 회차별 부분 재계산, 늦은 데이터, 발행본 보존, 여러 통계 계열의 함께 공개가 필요합니다. 따라서 기존 Python 워커가 관리하는 버전별 통계 테이블을 기본안으로 권장합니다. 작고 독립적인 전체 재계산 집계에는 MV를 사용할 수 있습니다. 새 OLAP DB·Redis·메시지 브로커를 이 설계만을 위해 필수 도입하지 않습니다.
