숫자를 읽는 기준

  • JOIN 수는 대표 SQL 분기의 명시적 JOIN 개수입니다. LEFT/CROSS/LATERAL 및 CTE와의 결합도 포함합니다. 실제 테이블 종류 수나 DB 실행 계획의 Join 노드 수와 같지 않습니다.
  • 동적으로 붙는 공통 권한·프롬프트·출처 필터와 VIEW 내부는 별도로 표시했습니다. 한 엔드포인트의 모든 분기를 합친 고정 총량이나 상한이 아닙니다. 명시적 JOIN이 0이어도 EXISTS/IN·서브쿼리·집계 작업이 있습니다.
  • 복잡도는 SQL 구조에 대한 정성 평가입니다. 실제 지연 시간·디스크 읽기·전체 테이블 스캔 여부는 운영 건수, 선택 범위, 인덱스, 통계, 캐시와 EXPLAIN 없이는 확정할 수 없습니다.
  • “조회 시 계산”은 해당 경로가 실행되는 경우입니다. API/legacy 분기와 결과 캐시·기존 summary 적중에 따라 생략될 수 있습니다. 운영 설정이나 실행 빈도는 이번에 확인하지 않았습니다.

JOIN보다 더 중요한 세 가지

인용 순위
선택 범위의 인용 → 출처×프롬프트 집계 → 출처별 합계 → 분류·전체 분모 → 전체 순위 → 검색 후 순위 → 페이지 LIMIT
웹 URL 정확도
타겟 URL 집합 → 해당 URL을 인용한 답변 DISTINCT → 전체 답변의 포함 여부 판정 → 분자·분모 COUNT
ACR 배틀
적격 셀 → 셀별 선택 결과 → 국가 등을 합쳐 prompt×engine×brand 합산 → 최고 선택 브랜드 → 프롬프트 이름·화면 행

페이지 행 수를 줄이는 것과 통계 계산량을 줄이는 것은 별개의 작업입니다. 중간 집합이 큰 집계·정렬·중복 제거를 먼저 처리하면 마지막 LIMIT는 응답 크기를 줄여도 그 앞의 계산을 없애지 못합니다.

반대로 이미 작은 집계에 브랜드 이름을 붙이는 JOIN은 원천 답변과 인용을 연결하는 JOIN보다 영향이 작을 수 있습니다. 따라서 S16의 7 JOIN을 S04의 2 JOIN보다 반드시 느리다고 해석해서는 안 됩니다.

API와 legacy를 구분해야 하는 이유

원본에는 두 경로가 함께 있습니다. API 언급/기본 KPI는 rd의 사전 판정 열을 읽는 비중이 높고, legacy 미러는 scope_* 원문과 대표 집합을 더 많이 결합합니다. legacy도 summary 저장값이나 캐시를 쓰면 그 계산을 매번 하지 않습니다.

대표적으로 legacy 언급은 핵심 브랜드 집계만 4 JOIN·6개 CTE·5개 GROUP BY·RANK()가 있고, API 브랜드 집계는 기본 사실 합산 본체에 JOIN이 없습니다. legacy QA는 공통 FROM+CTE에서 6 JOIN·7개 실제 테이블을 연결하지만 API QA는 job↔review 1 JOIN과 노트 EXISTS로 계산합니다.

사전 집계 우선순위에 주는 의미

  1. 인용 순위·톤·유형·상세: 인용×답변 결합, 출처/프롬프트 재집계와 고유 수 산출을 먼저 수집 후 작업으로 옮깁니다. 최종 검색·정렬·필터별 정확한 집합 계산은 유지합니다.
  2. ACR·GA4: 화면의 여러 영역에서 반복되는 셀/보고서 합계를 저장합니다. ACR 필터별 승자와 차종 분모, GA4 전체/페이지 보고서의 의미를 보존합니다.
  3. KPI·국가·추이·검수: JOIN이 적더라도 같은 범위의 반복 SUM/COUNT/DISTINCT를 줄입니다. QA는 수집 완료가 아니라 검수 쓰기 시점의 상태 갱신이 필요합니다.
  4. 소셜·키워드: 이미 적재된 지표는 유지하고 부가 COUNT·최신 관측 선택을 개선합니다. 원문 지표 재계산 제거를 주요 효과로 주장하지 않습니다.
위 순서는 구조 분석에 따른 구현 후보입니다. 실제 우선순위는 요청 빈도 × 선택 범위 × 실행 비용으로 확정해야 합니다. 느린 쿼리 로그와 대표 조건의 EXPLAIN (ANALYZE, BUFFERS)은 대표성 있는 비운영 환경에서 수행할 후속 검증이며 이번에는 실행하지 않았습니다.
