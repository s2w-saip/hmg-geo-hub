## 2. GEO 개념 요약 (보고서 ① 핵심)

- **GEO** = ChatGPT·Gemini 같은 AI 검색의 답 안에 브랜드·자사 출처가 나오게 하는 일. HMG에겐 "차 질문에 AI가 답할 때 현대·기아·제네시스가 어떻게 나오는지" 재는 일.
- **효과는 과장되기 쉬움.** "최대 40%"는 2023년 모의 실험 수치, 2025년 재검증(C-SEO Bench)은 54개 조건 중 3개만 유의. 노출 수단은 기존 SEO·PR과 같되 외부 매체(리뷰·언론·커뮤니티) 비중이 큼(미국 자동차 질의 인용의 82%).
- **측정이 어려운 이유 4가지:** ① 같은 질문에 답이 매번 다름(같은 브랜드 목록 재현율 1% 미만, 7회 반복해도 ±16%p) ② API vs 사용자 화면 결과 불일치(브랜드 겹침 15~24%) ③ 지표 이름 같아도 분모 다름(IAB 가이드라인 2026-08: 분모 명시·오차 범위·모델 변경 시 기준선 재설정) ④ LLM 채점기 오차(사람 일치도 0.43, 재실행 13.6% 뒤집힘)
- **대시보드 KPI:** ① 노출률(언급 답변÷전체) ② 점유율(언급 횟수 기준) ③ 우호도(언급 단위 긍정 비율) ④ 우선 노출도(답변 내 순위 평균) ⑤ 인용 점유율(글로벌=공식 HMG 카테고리) ⑥ 자사·타겟 URL 인용률(프롬프트 단위) · ACR(2턴×10회 반복) · ⑦ AI 유입 전환율(GA4 key events÷사용자, 100% 초과 가능)
- **현 대시보드 한계:** 조합당 답변 1건(ACR 제외), 오차 범위 없음, 검색 실행 여부 미기록, 웹 화면 수집은 모델 버전 미고정, 엔진 3종(ChatGPT·Gemini·DeepSeek)만 — Google AI Overviews·네이버 미측정

## 3. 시스템 현황 (보고서 ② 핵심)

### 3-1. 구조
```
Scope 코어 DB (앤서, 원본) ── 측정 결과 1회 기록
   │ Scope REST API
   ├─ 20분 cron (운영 중) ─▶ Supabase 미러 scope_* (레거시 대시보드가 SQL 집계) ─▶ 고객 화면
   └─ ingest.worker 20분 (설계) ─▶ HUB RDS ing(원본 불변) → rd(판정·투영) ─▶ FastAPI ─▶ 화면(HGH_SOURCE_* 전환)
                                     │
                                     └─ (확정) S2W가 ing을 DB로 직접 읽기 → S2W 분석 엔진·시스템(Azure)
```
- **미러 ≠ 원본.** 미러는 API 응답을 가공해 저장(measured_at을 회차 앵커로 덮어씀, ACR 반복 1건으로 접음, 인용 id 재싱크마다 변경). RAID·DB 리플리케이션과 다름.
- **HUB ing은 원본 그대로**(measured_at 원본, prompt_run_id·content_hash·analysis_version 있음). 단 **turn_index 없음** → H2.
- **현재 상태:** 미러만 살아 있음. HUB stg는 9/30·10/2 덤프 시드 상태, ingest 워커 가동 여부 미확인(Q1). prod RDS 개설 후 정지(7일 뒤 자동 기동, 유휴 비용 월 약 $60/환경).
- **규모:** 답변 69.9만·언급 550만·인용 450만(9/27 앤서 조사, 10/6 추정치는 85만·679만·718만으로 차이) · DB 21GB · 크롤 6GB. 콜드 로딩 28~38초 → 재설계 목표 1초.
- **1회차 수집 소요(코드 주석, 표본 2회차):** 글로벌 run 216개 도착 분산 39.9h, 웹사이트 186개 98.9h. 마감 36h 정온 / run 재확인 3일 / 분석 재확인 7일 / 발행 95% / 노출 지연 글로벌 2일·웹사이트 1일 → 수집~노출 글로벌 약 3일, 웹사이트 5~6일.

## 4. 데이터 공급·마이그레이션

### 4-1. 확정된 공급 구조 (10/7)
- 원문 공급 = HUB RDS `ing` DB 읽기, 영구. 읽기 롤 `loader_ro` 상속 `s2w_ro`(읽기 전용, statement_timeout, verify-full) 제안됨.
- **H1 접속 방식** (앤서 제시 A~D): A SSM 포트포워드(즉시, 터널 단절·EC2 경유) / B 사이트 간 VPN(Azure↔AWS, 대역 충돌 시 불가) / C 읽기 복제본(+경로) / D 퍼블릭+고정 IP(비권고). **S2W 입장: C+B, 초기 개발 한정 A.** 필요 입력: Azure 리전·VNet 대역·egress IP·조회 빈도·대상 환경.
- **H2 턴 원문:** ing.answer는 job 단위(turn-1 답만). A: job으로 시작 후 턴 키 추가 / B: 처음부터 턴 단위. **S2W 입장: 턴 필수, `ing.turn` 추가를 앤서 작업으로 요청.**
- **동기화 설계 변경:** API 호출이 아니라 RDS 증분 읽기(`load_id`·`first_seen_at`·`content_hash`). C3는 커넥션 한도·timeout·조회 빈도로.
- **운영 SLA 필요(영구 의존):** ingest 가동 보장, 측정 지연·적재 실패 통보, ing DDL 변경 사전 고지, DEFAULT PRIVILEGES 보장, RDS 정지/기동 정책, 복제본·VPN 비용 분담.

## 7. 리스크

1. **턴 원문 부재(H2).** ing.turn이 안 나오면 엔진 설계를 job 단위로 바꿔야 하고 멀티턴(ACR) 분석 정확도가 떨어짐.
2. **영구 의존.** ingest·RDS·DDL이 앤서 손에 있음. SLA·변경 고지 없이는 우리 배치가 예고 없이 깨짐.
3. **시계.** C5가 정해지는 순간 엔진 마감 발생. 날짜 미정.
4. **매몰.** H-Cloud 런타임 결정에 따라 back 72개 기능 재작성 가능.
5. **숫자 변동.** 엔진·경로 변경 시 고객이 보는 값이 달라짐. 전환 전후 병행 산출 없이는 설명 불가.
6. **시드 누락.** 문서만 믿고 컷오버하면 멤버·검수 이력·컨텍스트 맵이 빈 채로 넘어감.
7. **개인정보.** 전량 덤프에 auth.users·IP 해시·감사 로그 포함 → 전달 경로 암호화·보관 책임 명시.
