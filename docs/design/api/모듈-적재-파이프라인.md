# 적재 파이프라인(ingest) 모듈 설계

작성 2026-09-27. 입력: 단위 설계 IG-1·IG-2·IG-3, 설계 공용 계약 v2, 확정 DDL `db/DB-v2.sql`, `db/DB-보정.md`(§4 적재 흐름, ingestion_flow 0~17), 현행 코드 7639b9e(읽기 전용 확인). 파일·DB·git 변경 없음.

## 1. 개요

Scope API 를 20분마다 당겨 쓰기 스키마 `ing`(넓은 원본, 판정 없음)에 해시 diff 로 반영하고, **같은 트랜잭션에서** 읽기 스키마 `rd`(좁은 투영: 정수 키·판정 열·파티션)를 갱신한다(A10·A17·G-16). 파생 층은 없다(D8). 이 모듈은 `rd`·`ing` 의 유일한 쓰기 주체이며(loader 롤), 다른 모듈의 app 편집은 `app.judgment_change` 큐로 들어와 이 모듈이 반영한다.

단위 경계(DB-보정 §4 10단계 기준으로 재정의):

| 단계 | 내용 | 소유 |
| --- | --- | --- |
| 0 | 프로젝트 등록 동기화, 커서 임대, 프롬프트 증분 | IG-1 |
| 1 | run 대조(R12 워터마크), 스테이지 전량 수신 | IG-1 |
| 2 | 해시 diff, ing 원본 반영 | IG-1 |
| 3 | 회차 개설·좌석 배정(R02)·run 귀속 | IG-3 |
| 4~8 | rd.job·rd.answer 투영, 자식 투영, 당사 요약, 게이트 전파·불변식, R05 is_rep | IG-2 |
| 9 | 회차 카운터·종결(R01)·발행(R08)·노출일, rd.cycle 투영 | IG-3 |
| 10 | 세대 증가, run·load 마감, 커밋, 커밋 뒤 ANALYZE | IG-1(공유 finalize) |
| 큐 | 판정 입력 재판정 | IG-2 |
| 큐 | cycle_admin·report_publication·anchor_pin·answer_drop | IG-3(재투영은 IG-2 호출) |

HTTP 는 운영 조회 3개뿐이다. 회차 운영·리포트 발행 HTTP 는 AD-4 소관(명세 §8 admin 그룹)이고, 이 모듈은 그 요청의 소비자다.

## 2. 프로세스·실행 구조

- **API 프로세스**(api_ro): `/v1/admin/ingest/*` 운영 조회만.
- **워커 프로세스** `hmg.ingest.worker`(loader 롤, 직접 DB 연결, ECS 서비스 1개):
  - pull 루프 20분: IG-1 패스. 패스 벽시계 예산 15분.
  - queue 루프 60초: judgment_change 디스패처.
  - cycles_tick 20분: 적재가 없어도 시간이 흘러 바뀌는 판정(정온·재확인 창 종결, 발행 전이, 노출일, stale). 일 1회 파티션 선생성.
- **watch 태스크**(별도 스케줄 6시간): 회차 사슬·적재 적체·워커 하트비트 감시. 현행이 동기화 타임아웃에 관제가 같이 죽었던 전례(app/api/cron/cycle-chain-watch/route.ts:21-27) 때문에 분리한다.
- **CLI** `python -m hmg.ingest.cli sync --project <uuid> [--force] [--max-runs N]`: 수동·백필. 현행 `?force=1&maxRuns`(app/api/cron/sync-mirror/route.ts:326) 계승. HTTP 트리거와 크론 비밀은 폐기한다.

## 3. 엔드포인트·실행 단위 명세

### 3-1. GET /v1/admin/ingest/status (IG-1)
- 권한: role='admin'(현행 /admin ADMIN_ONLY, lib/auth/route-policy.ts:236-239). operator 축은 비용 액션용이라 쓰지 않는다.
- 파라미터: `surface`(선택, global·website·project), 공통 필터 축은 전부 `meta.ignored_filters`.
- 원천: `rd.v_ingest_status`(제안 뷰) = ing.sync_cursor + 프로젝트별 run LATERAL count(open_runs, blocked_runs).
- 응답: `{ data: [IngestStatusRow], meta: AdminMeta }`, 페이지 없음(프로젝트 수 소규모).

### 3-2. GET /v1/admin/ingest/backlog (IG-1)
- 조건: 재확인 창(recheck_until·analysis_recheck_until)이 닫혔는데 unresolved_jobs>0 또는 analysis_pending>0, 또는 sync_state='blocked'.
- 원천: `rd.v_ingest_backlog`(제안), 인덱스 run_open_idx(DB-v2.sql:279).
- 파라미터: `surface`, `limit`(기본 50, 최대 200), `cursor`(키셋: started_at, run_id).

### 3-3. GET /v1/admin/ingest/loads (IG-1)
- 원천: `rd.v_ingest_load`(제안), ing.load PK.
- 파라미터: `kind[]`, `status[]`, `started_from`/`started_to`(적재 원장 시각, 공통 필터 from/to 와 다른 이름), `limit`, `cursor`(load_id DESC).

### 3-4. pull 패스 (IG-1, 워커)
1. 프로젝트 등록 동기화: app.project·app.website_site 의 scope_project_id 를 ing.sync_cursor·rd.dim_project 에 INSERT ON CONFLICT DO NOTHING.
2. 커서 임대: `SELECT ... FROM ing.sync_cursor ORDER BY last_attempt_at NULLS FIRST FOR UPDATE SKIP LOCKED LIMIT 1`, last_attempt_at 선기록(에러는 지우지 않음, 현행 markSyncAttemptStarted lib/db/repositories/scope-mirror.ts:420).
3. 프롬프트 증분: listPrompts(updated_from = prompts_updated_to) → ing.prompt UPSERT. regions·lang·kind·text 변경분은 큐를 거치지 않고 별도 트랜잭션에서 `project.rejudge('scope_prompt', ...)` 직접 호출(loader 는 judgment_change INSERT 권한이 없다, DB-v2.sql:860-861).
4. run 대조(R12): 건너뜀 조건 = 이전 상태 있음 ∧ status 동일 ∧ total_jobs 동일 ∧ ((unresolved_jobs=0 ∧ analysis_pending=0) ∨ now > 두 재확인 창). 순서 신규 > 상태·총수 변경 > 재확인, 재확인만 프로젝트당 25(현행 RECHECK_MAX_RUNS_PER_PASS lib/scope/mirror/sync.ts:506).
5. 수신: open_load 로 load_id 선발급 → listRunJobs 페이지를 ing.stage_* 에 적재(load_id 태그), 본문 누락은 getQueryRun 보충, 실패는 unresolved. 중단 시 stage_cursor 저장 후 다음 패스 재개. UNLOGGED 유실이면 처음부터(멱등).
6. 적재 트랜잭션: 표면 공유 잠금 + 프로젝트 try 잠금 → 2단계 diff·ing 반영 → IG-3 attribute → IG-2 apply → IG-3 reevaluate → finalize → COMMIT → 건드린 leaf ANALYZE.

### 3-5. IG-2 project.apply / reproject / rejudge
- rd.job: run 의 모든 job UPSERT(status_code, dropped = ing.answer_drop 존재, served, measured_at, 필터 축).
- rd.answer: 완료·비드롭 changed job UPSERT. 판정 열: cat_mask(rd.catalog_entry bit_or), bgrp, elig, dflt(app.rule_param default_engines), is_acr(rd.dim_prompt.kind), acr_iter_rank, analysis_state.
- **acr_iter_rank(R13·A15)**: 접기 키 (run_key, prompt_key, engine_key, geo_key), 순서 measured_at DESC, answer_key DESC. 분석 유무에 의존하지 않는다. 현행 대표 규칙(완료 우선 후 최신, sync.ts:994-999)과 같은 방향.
- 자식: answer_brand(정본 브랜드명 정규화·비경쟁 제외·rank, 현행 ownBrandRankPerJobSql scope-aggregates.ts:493-538 이식), answer_stance(first_turn = 최저 turn_index, 현행 DISTINCT ON scope-aggregates.ts:7410), citation(dim_url upsert 후 cit_in·gap·loc_owned·tgt_hit·src_first·owner_key, 프로젝트 자사 기준 = 설정 ∪ 도메인 폴백 ∪ 카탈로그 루트), acr_cell·acr_choice·acr_cell_job.
- 당사 요약: own_mask·own_rk_h/k/g·ment_*·sent_*·has_cit·tgt_cited·own_url_cited. 불변식: 자사 answer_brand 합 = rd.answer 당사 열.
- 게이트 전파: rd.propagate_answer_gates(keys) 를 5만 단위 청크로 호출.
- R05 is_rep: 영향 셀 (surface, round_date, cyc_key, prompt_key, engine_key, geo_key) 에서 elig 후보 중 measured_at(rd.job 조인) DESC, answer_key DESC 1건. 회차 상태와 무관.
- 재판정: 프로젝트 한정 kind 는 rule_ver 유지, 전역 규칙 kind 는 새 rule_ver. leaf 재구축 전용 열(source_key·url_key·brand_key·competitive·rk·owner_key·loc_owned·tgt_hit)이 바뀌면 answer_key 단위 자식 삭제·재삽입, 영향 20만 초과면 escalated_rebuild.

### 3-6. IG-3 cycles
- attribute: ing.run.cycle_anchor_at 로 ing.cycle INSERT ON CONFLICT DO NOTHING, 앵커 우선순위 pin → 원장 → run 앵커 → 측정일(derived 회차), 좌석 배정은 현행 hmg_assign_cycle_rounds(0077_scope_answer_cycle_anchors.sql:673) 이식, ing.cycle_run 귀속.
- reevaluate: 카운터 갱신, 종결 3팔 술어(현행 summary-cycles.ts:1232-1258 그대로): 다음 앵커 ∧ 소속 run 존재 / 100% ∧ 소속 run started_at 이 모두 36시간 전 / 소속 run started_at 이 모두 재확인 창 밖. started_at NULL 이면 닫지 않는다. 발행: closed ∧ analysis_done_ratio ≥ analysis_publish_ratio(0.95) → published, view_anchor_at = 앵커 + view_delay_days. rd.cycle 투영.
- 운영 요청: cycle_admin(hide·unhide·close·set_view_date), report_publication(rd.report_unit_value 를 (round_date, file_seq) 로 교체, supersede 된 pub_id 행 삭제), anchor_pin·answer_drop(ing 레지스트리 쓰기 → 좌석 재평가 → IG-2 reproject).

## 4. 공통 구성요소

- 코드 상수 `ingest.codes`: surface 1·2·3, status_code 0~3, analysis_state 0 언급 있음·1 분석 완료 언급 0·2 미도착·3 실패/스킵, stance 1~4, hidden_scope 0~3, rd.cycle.status 0 open·1 closed·2 published·3 stale(DDL 미정의, 제안).
- 잠금: NS_SURFACE·NS_PROJECT·NS_DIM, 순서 surface → project → dim. 세션 잠금 금지(PgBouncer transaction 모드 비호환).
- LoadContext 와 ing.load 생명주기(open_load 별도 트랜잭션, finalize 같은 트랜잭션, fail_load 롤백 후 새 트랜잭션).
- 세대: finalize 가 rd 변화 있는 커밋에만 rd.surface_generation +1, rd.cycle.generation 은 그 값으로 SET.
- 좌표 해석: 모든 rd 사실 표 접근은 rd.job 경유 (surface, round_date) 등치.
- content_hash: 정규화 JSON sha256, 휘발 필드 제외.
- 큐 소비: FOR UPDATE SKIP LOCKED, 실패 기록은 새 트랜잭션.
- Pydantic: AdminMeta, IngestStatusRow, BacklogRow, LoadRow, Page[T].
- 경보: 라이브 이슈 Slack, 코드 수리 GitHub Issue(알림 라우팅 룰).

## 6. 권한

- 운영 조회: role='admin' 만, api_ro 커넥션, 뷰만 읽음.
- 워커: loader 롤. ing·rd·ext DML, app SELECT, judgment_change 상태 열 UPDATE, leaf 헬퍼 EXECUTE(DB-v2.sql:856-865). DDL 은 SECURITY DEFINER 헬퍼로만.
- 비밀값: Scope API 키·웹훅은 Secrets Manager → env, 로그·argv 에 남기지 않는다.
- HTTP 수동 트리거 없음(크론 비밀 폐기). 운영 요청은 AD-4·QA 가 api_rw 로 큐에 넣고 이 모듈이 반영.

## 7. 성능

- 운영 조회 3개: low. 원장 행(10배에서도 수십만 이하)을 인덱스로 읽는다.
- 적재 트랜잭션: **high(미측정)**. 3.85만 답변 전면 교체 7~22초·WAL 약 1.3GB, 6.6만 job 체인 미측정(DB-보정 §5 v3 적재 항목). 폭 10배면 run 당 job 이 수 배. loader statement_timeout 180s 에 한 문장이 걸릴 수 있어 문장 청크화(가시성은 커밋 1회 유지)를 기본으로 한다. 게이트 전파 배열도 5만 단위 청크.
- 재확인 패스: 해시 동일이면 쓰기 0(DN-7).
- 커밋 직후 건드린 leaf ANALYZE 로 읽기 API 추정 오차 창을 줄인다.
- 파티션: rd 사실 표 LIST(surface) → RANGE(round_date), ing 원본 RANGE(run_month). 선생성은 cycles_tick 일 1회.

## 8. 대조 방법

1. run 지문: 같은 run 을 미러(old)와 새 로더(new)에서 mig.run_fingerprint 로 비교(jobs·completed·mention_rows·citation_rows·jobs_without_analysis·job_set_hash·mention_sum). R12 로 new 가 분석을 더 가진 차이는 known_diff 로 설명.
2. 앵커 오라클: mig.row_oracle_diff(oracle='scope_answer_cycle_anchors') 로 job 단위 anchor·round_date 100% 일치 확인 뒤 현행 앵커 표 폐기(DB-이관 방침).
3. 판정 열: rd.answer.std_in·cit_in·acr_in 을 현행 산식(분석 결손·ACR 접기)과 job 단위 대조, 차이는 R13·A15·A16·G-21 g 로만 설명.
4. 기능 값: F01~F07 대조 하네스(values-old.jsonl)와 mig.parity_result, unexplained 0.
5. 불변식: 야간 감사로 answer_key 전역 유일(DB-v2.sql:581-583), 게이트 동치, 당사 합 불변식을 leaf 단위 재확인.

## 9. 열린 질문

1. ing.cycle 카운터(완료율·분석 완료율)를 운영자 화면에 보일지: 계약상 비노출. 필요하면 제품 결정으로 D8 예외 ③ 범위 확대.
2. R08 을 7일(analysis_recheck_days) 안에 못 넘긴 회차: 미발행 유지 + 경보인지, 결손 표시(A16)로 발행인지. cycle_admin op 에 publish 강제가 없다.
3. 적재 트랜잭션 statement_timeout: 청크화로 180s 를 지킬지, 적재 트랜잭션만 SET LOCAL 상향할지. RDS 실측 게이트에서 결정.
4. rd.report_unit_value PK (round_date, file_seq): 같은 round_date 에 brand_scope 가 다른 발행이 둘 이상 active 이고 file_seq 가 겹치면 충돌한다. 우선순위 규칙 필요.
5. rd.surface_generation.as_of: 적재 시점의 servable 최신 round_date 로 둘지, API 가 view_date ≤ 오늘로 매번 계산할지.
6. judgment_change 실패 재시도: 시도 횟수 열이 없어 failed 는 수동 재요청뿐. 자동 재시도가 필요하면 DDL 제안.
7. Scope 에서 run 목록에서 사라진 job(removed) 처리: ing 원본 불변 원칙과 rd 제거 사이의 규칙 미정.
8. 외부 적재(outbox 드레인·GA4·DataForSEO) 소유 모듈: 이 모듈에 IG-4 를 둘지 통합자 결정.
9. 병행 기간 Scope 이중 pull 수용 여부(G-10) 미확인.
