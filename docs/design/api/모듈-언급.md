## 2. 공통 규칙 (세 단위가 반드시 같게)

1. **관점과 당사**: 서버가 관점 비트 목록 `vp` 를 정한다(Hyundai [1], Kia [2], Genesis [4], HMG [1,2,4]). 원천은 project = `app.project.brand_code → app.brand.brand_bit`, website = `rd.dim_project.site_brand_bit`, global = 세션 스코프 brands ∩ brand[](비면 HMG)다.
   - 당사 행 = `own_bit = ANY(:vp)`.
   - 경쟁·비교 행 = `competitive AND NOT (own_bit = ANY(:vp))`. 현행 `trackedRollupIn`(scope-aggregates.ts:195) = 관점 ∩ 3사이므로 Kia 관점에서 Hyundai 는 경쟁 행이다.
   - 답변 단위 당사 노출 = `FILTER (WHERE own_mask & :vp_mask <> 0)`.
2. **모수**: `bgrp = ANY(:pop_masks)`. brand[] 는 카탈로그(프롬프트 모수) 필터이지 표시 브랜드 필터가 아니다(DB-측정-코어.md:65-66).
3. **회차**: `cyc_key = ANY(:cyc)`. 허용 회차 = servable, view_date ≤ `rd.today_kst()`, hidden_scope ∉ {1 all, 3 mentions}. 기간이 없으면 최신 노출 회차 1개(A1, mode=snapshot), 있으면 round_date 가 기간 안인 모든 완료 측정(D1, mode=cumulative).
4. **게이트**: 언급 계열 모수는 `std_in`(A15 ACR 접기·A16 결손 제외 포함, DB-v2.sql:470, 자식은 전파 사본)이다. 엔진이 비면 `dflt`.
5. **경쟁 행만**: 언급 계열은 `competitive = true` 행만 합산한다(M02 분모 ment_total 과 같은 정의).
6. **축**: geo_key = ANY, lang_key = ANY(global·website, project 는 ignored), 카탈로그 축과 커스텀 필드는 filters 모듈이 푼 `prompt_key = ANY`(1,000 초과면 semi-join). catalog_entry 를 사실 표에 직접 조인하지 않는다(행 복제로 합이 부풀려진다).
7. **SQL 규율**: WHERE 는 불리언과 `= ANY` 만 쓴다. 비트 식은 FILTER 안에서만 쓴다. 정렬·신호 열은 화이트리스트 조각으로만 넣는다. 비율은 `{num, den}` 정수로 낸다. 사전 집계·결과 캐시·차원 캐시는 두지 않는다(D8).

## 3. 엔드포인트 명세

### 3.1 M-1 `GET /v1/mentions/brands`

- 필터: 공통 전부. source[] 는 ignored.
- extra 파라미터: `top_n`(1~100, 기본 10), `sort`(mentions|share|avg_rank, 기본 mentions), `brand_key[]`(표시 브랜드 한정, 스파크라인 등 지정 조회용).
- 응답 `data`:
  - `totals`: `{answers, mentions_total, brand_count}`
  - `own`: `{vp_label, exposure:Ratio, share:Ratio, avg_rank:{sum, count, value|null}, mentions}`
  - `brands[]`: `{brand_key, name, is_own, rank, exposure:Ratio(den=answers), share:Ratio(den=mentions_total), avg_rank:{sum,count,value|null}, mentions, sentiment:{positive,neutral,mixed,negative}}`
- 당사 행은 top_n 과 무관하게 항상 포함한다. rank 는 전 브랜드 언급 수 내림차순이다(하네스 F03 정의 README:102).
- 쿼리 두 문장을 병렬로 실행한다.

```sql
-- (1) answer_totals: rd.answer, 당사 열(G-03)
SELECT count(*) AS answers, sum(ment_total) AS mentions_total,
       count(*) FILTER (WHERE own_mask & :vp_mask <> 0) AS own_exposed,
       sum(<own_ment_expr>) AS own_mentions,
       sum(<own_rank_expr>) FILTER (WHERE <own_rank_expr> > 0) AS own_rank_sum,
       count(*) FILTER (WHERE <own_rank_expr> > 0) AS own_ranked
FROM rd.answer
WHERE surface = :s AND round_date BETWEEN :lo AND :hi AND cyc_key = ANY(:cyc) AND std_in
  AND bgrp = ANY(:pop) AND geo_key = ANY(:geo) [AND lang_key = ANY(:lang)]
  AND <dflt | engine_key = ANY(:eng)> [AND prompt_key = ANY(:pk)] [AND project_key = ANY(:proj)];

-- (2) brand_rows: rd.answer_brand
WITH g AS (
  SELECT brand_key, count(*) AS exposed, sum(mention_count) AS mentions,
         sum(rk) FILTER (WHERE rk > 0) AS rank_sum, count(*) FILTER (WHERE rk > 0) AS ranked,
         sum(s_pos) p, sum(s_neu) n, sum(s_mix) x, sum(s_neg) g,
         bool_or(own_bit = ANY(:vp)) AS is_own,
         rank() OVER (ORDER BY sum(mention_count) DESC) AS rnk, count(*) OVER () AS brand_count
  FROM rd.answer_brand
  WHERE <공통 술어> AND competitive [AND brand_key = ANY(:brand_keys)]
  GROUP BY brand_key)
SELECT g.*, bn.name FROM g JOIN rd.dim_brand_name bn USING (brand_key)
WHERE g.is_own OR g.rnk <= :top_n
ORDER BY <SORT_SQL> DESC, brand_key;
```

- `<own_ment_expr>`·`<own_rank_expr>` 는 own_cols(vp) 화이트리스트에서 고른다. HMG 는 합, 순위는 `LEAST(NULLIF(own_rk_h,0), NULLIF(own_rk_k,0), NULLIF(own_rk_g,0))` 이다.
- M04 는 조회 시 sum/count 로 계산하고, 순위가 없으면 null 이다(0 아님).
- `brand_rows` 는 KPI 모듈(Overview 경쟁사 줄)과 trend 모듈(bucket 인자)에 내보낸다.

#### 3.1.1 값 갭 보강(BG-12~16·19, D13, 2026-09-28). 전부 선택 인자, 주지 않으면 위 계약과 모양·값이 같다

| 인자 | 값 | 응답 추가 | 비고 |
| --- | --- | --- | --- |

| `q` | 1~100자(SAFE_TEXT) | 없음 | BG-19. 경쟁 브랜드 이름 부분 일치(앱 casefold, SQL 경로 없음). 순위는 전체 기준 |

- `top_n` 상한은 100(설계 초안 50 에서 상향), `brand_key[]` 최대 100개·int4.

### 3.2 M-2 `GET /v1/mentions/types`

- 필터: 공통 전부. source[] 는 ignored. extra 파라미터: `split_own`(D13, 아래 3.2 추가 항목). stance_scope·top_brands 는 제거.
- 응답 `data`:
  - `answers_total`
  - `by_type[5]`: `{type, own_mentions, other_mentions, own_answers, other_answers, own_exposure:Ratio(den=answers_total), other_exposure:Ratio, own_share:Ratio(num=own_mentions, den=own_mentions+other_mentions)}`
  - `sentiment_matrix[10]`: `{type, scope: own|all, rows, positive, neutral, mixed, negative}`. 근사값이다. 한 행에 유형이 2개 이상이면 두 유형 모두에 계상되므로, 유형 간 합산은 금지하고 유형 안 구성비로만 읽는다.
  - `stance`: `{positive, neutral, mixed, negative, pairs}`. pairs = 4계열 합, 당사만. A3 규칙은 파생 비율을 만들 때만 적용한다.
- 쿼리:

```sql
-- (1) 유형·매트릭스: rd.answer_brand 1회 스캔, (answer_key, is_own) 로 접은 뒤 집계
WITH pa AS (
  SELECT answer_key, (own_bit = ANY(:vp)) AS own,
         sum(t_mention) m_n, bool_or(t_mention > 0) m_a, ... (5유형),
         sum(s_pos) FILTER (WHERE t_mention > 0) m_p, ... (5유형 × 4계열)
  FROM rd.answer_brand WHERE <공통 술어> AND competitive
  GROUP BY answer_key, own)
SELECT own, sum(m_n), count(*) FILTER (WHERE m_a), ..., sum(m_p), ... FROM pa GROUP BY own;
-- all 스코프 = own + other 합(서비스 층)

-- (2) 스탠스: 필터 축이 없어 rd.answer 등치 조인 필수
SELECT s.stance, count(*)
FROM rd.answer_stance s
JOIN rd.answer a ON a.surface = s.surface AND a.round_date = s.round_date AND a.answer_key = s.answer_key
WHERE s.surface = :s AND s.round_date BETWEEN :lo AND :hi AND s.first_turn AND s.std_in
  AND s.own_bit = ANY(:vp) AND <공통 술어 on a>
GROUP BY s.stance;
```

- 단일 관점이면 당사 쪽은 답변당 당사 행이 1개다. 그래서 count(*) FILTER 빠른 경로로 접기를 생략할 수 있다(구현 선택).
- answers_total 은 answer_totals 의 answers 를 재사용한다.
- 선택 인자 `split_own`(D13, 2026-09-28): 관점 비트가 둘 이상이면 `data.by_own_brand[]{own_brand_code, by_type[5], sentiment_matrix[10], stance}` 를
  더한다(비트가 하나면 `[]`, 인자가 없으면 키 없음). 판정·행 키는 M-1·trend 와 같다(`core.measure.split_own_scopes(ms)`, 비트의 부모 브랜드 코드).
  블록 = 그 비트만 당사로 둔 스코프로 (1)·(2)를 한 번씩 더 돈 값: own = 그 브랜드, other = 그 밖 경쟁 행 전부(형제 관점 브랜드 포함), 분모 answers_total 공유.
  당사 언급·당사 매트릭스·스탠스는 블록 합 = 합친 값(행 가산), own_answers 는 가산 아님. 추가 문장 = 비트 수(≤ 3) × 2.
  front `typesByBrand`(다중 관점)는 M-1 `split_own&include=types` 로도 받을 수 있다(두 경로 값이 같다: 회귀 시험 고정).

### 3.3 M-3 `GET /v1/mentions/prompts`

- 필터: 공통 전부(brand[] 포함, 모수 필터). source[] 는 ignored.
- extra 파라미터:
  - `mode`(brand|signal, 필수)
  - `brand_key`(int, mode=brand 필수, M-1 응답의 키, 없으면 404)
  - `signal`(SignalKey 9종, mode=signal 필수)
  - `limit`(1~200, 기본 50)
  - `cursor`
  - `answers_limit`(1~50, 기본 6: 현행 SIGNAL_REFS_PER_PROMPT scope-aggregates.ts:7264)
- 응답 `data`:
  - `mode`, `target{brand_key,name}|{signal}`
  - `items[]{prompt_key, prompt_id, prompt_text, funnel_code, count, providers[], answers[]{job_id, engine, region, value, position|null, measured_at, runs}}`
  - `meta.total`(전 프롬프트 count 합), `meta.page{next_cursor, has_more}`
- `count` 의 뜻: brand 모드는 해당 브랜드 경쟁 행 mention_count 합, signal 모드는 당사 행의 신호 열 합이다(현행 sum(col) 계승).
- 타깃 술어:
  - brand: `brand_key = :bk AND competitive`(ab_brand_idx 사용)
  - signal: `own_bit = ANY(:vp) AND competitive AND <SIGNAL_SQL> > 0`
- 프롬프트 페이지 문장: 타깃 술어 + 공통 술어로 GROUP BY prompt_key 한 뒤, `(count, prompt_key) < (:c, :k)` 키셋으로 ORDER BY count DESC, prompt_key DESC LIMIT :limit 한다. total 은 같은 문장의 sum(...) OVER () 로 구한다.
- answers 배치 문장(페이지의 prompt_key 에 1회): 타깃 행을 rd.answer(PK 등치, is_rep)와 rd.job(answer_key PK, job_id·measured_at)에 조인한다.
  1. 셀(prompt, engine, geo) 대표 1건과 runs 를 먼저 구한다: `row_number() ... ORDER BY is_rep DESC, measured_at DESC, answer_key DESC`.
  2. 그다음 프롬프트 안에서 `row_number() ≤ :answers_limit` 로 자른다.
- 이름 라벨은 dim_prompt·dim_taxon·dim_engine·dim_country PK 조인으로 붙인다. 하이라이트는 answers 모듈이 맡는다(단, BG-18 `terms` 는 아래).

#### 3.3.1 값 갭 보강(BG-17·18, 2026-09-28). 전부 선택 인자, 주지 않으면 위 계약과 모양·값이 같다

- mode=brand 타깃은 셋 중 정확히 하나(아니면 422):
  - `brand_key`(위, 1~2^31-1)
  - `mention_brand`(BG-17, 1~100자 SAFE_TEXT): 표시 브랜드명 → brand_key. `rd.dim_brand_name` 에서 name 일치 우선, 없으면 bare(소문자) 일치
    (`/v1/answers` 목록과 같은 해석), 없으면 404 brand_not_found.
  - `own=true`(BG-17): 당사 행 = `own_bit = ANY(관점 비트) ∧ competitive`, 값 = mention_count.
    `own_brand_code`(own=true 전용, 1~50자): D13 split_own 행 키(M-1 `split_own` 의 `own_brand_code`: 관점 비트가 둘 이상일 때 비트별 부모 브랜드 코드)만
    그 비트 하나로 받는다. 브랜드 코드가 아니면 422, 행 키가 아닌 코드(관점 밖·관점 안 하위 브랜드 예 ADMIN 의 `Hyundai N`·단일 관점)는 빈 목록.
- mode=signal 에 `brand_key`·`own`·`mention_brand`·`own_brand_code` 가 오면 422(예전에는 brand_key 를 조용히 무시했다).
- `data.target` 에 own 타깃이면 `own: true`, 좁혔으면 `own_brand_code` 가 붙는다. 커서 해시에 타깃이 들어간다(`terms` 는 제외: terms 만 바꾸면 커서 유지).
  새 타깃 인자(`mention_brand`·`own`·`own_brand_code`)는 값이 있을 때만 해시에 들어간다: 기본값 요청의 해시는 BG 라운드 전과 같아 배포 전 커서가 이어진다.
- `terms=true`(BG-18): `answers[].terms{brand[], model[]}` = 모달 원문 하이라이트 표기(현행 highlightTermsForBrand result-adapter.ts:300-349 이식).
  원천 = `rd.v_answer_mention_raw`(answer_key 배치 1문장, surface·project_key 재단언, fail-closed) + 엔티티 정본 브랜드(`rd.dim_entity → rd.dim_brand_name`).
  brand 타깃 = 그 브랜드(씨앗 = 표시명), own·signal 타깃 = 관점 비트(씨앗 = 그 답변의 타깃 Brand 행 정본 이름에 있는 관점 브랜드 코드만).
  2자 미만 제외·순서 유지 중복 제거·brand 에 있는 표기는 model 에서 뺀다. 상한: 답변 참조당 brand 8·model 24(현행 슬림 수준 0),
  요청 `limit × answers_limit ≤ TERMS_MAX_REFS`(1000, 넘으면 422).
- model 표기는 현행과 같이 롤업으로만 잇는다: 롤업 id 가 그 답변의 타깃 Brand 행(현행 brandIds)이거나 롤업 엔티티의 정본 브랜드가 타깃
  (현행 rollupBrandId). 엔티티 자기 정본 브랜드로는 잇지 않는다. 예: Hyundai 타깃에서 `Hyundai Creta`(정본 Hyundai, 롤업 = Tata)는 현행처럼 칠하지 않는다.
- mode=signal 의 `terms` 는 현행 신호 드릴다운(하이라이트 없음, scope-aggregates.ts:7329)에 없는 확장이다. 화면을 그대로 두는 어댑터는
  signal 에 `terms` 를 요청하지 않는다(요청하면 당사 비트 기준 표기가 나온다).

## 6. 권한

- A8: FastAPI 가 Supabase JWT 를 JWKS 로 검증한다. 미검증이면 401.
- 서버가 세션 role·스코프로 brand·country·project 허용 집합을 계산해 요청과 교집합한다. 권한 밖 값은 meta.dropped_filters 에 싣고, 스코프가 비면 빈 응답(default-deny)이다. 관점 브랜드는 클라이언트가 바꿀 수 없다.
- 행 수준 스코프가 곧 권한이다. 그래서 M-3 은 추적 브랜드 명부 검사를 하지 않는다(global 경쟁사 드릴다운 회귀 방지).
- 쓰기가 없다(api_ro). 접근 감사는 AU-1 미결 그대로다.
- 경로 접근(role 별 허용)은 route-policy 목록에 등재한다.

## 8. 대조 방법

1. 하네스 F03(경쟁사 상위 10 + 추적 브랜드) 대 M-1 brands. C01~C12 조합 × own-mode(account·admin-brand·hq).
2. 하네스에 F08(fetchStandardKpiTypes)·F09(fetchStandardKpiStanceDist)·F10(fetchStandardBrandMentionPrompts·fetchStandardSignalPrompts)을 신설해 현행 값을 캐시한 뒤 대조한다.
3. 내부 불변식(CI):
   - M-1 당사 행(answer_brand) mentions 합 = own.mentions(answer_totals)
   - M-3 brand 모드 전 페이지 count 합 = M-1 해당 브랜드 mentions
   - M-3 signal=positive 합 = 당사 행 s_pos 합
   - M-2 stance.pairs = 4계열 합
   - Overview 경쟁사 줄 = M-1 brands(같은 함수)
4. 정의 변화(A4)로 달라지는 값은 차이 리포트에 사유 코드와 함께 남긴다.
5. known_diff 없음: M-3 `terms`(BG-18) model 표기는 현행 롤업 규칙과 같게 맞췄다(§3.3.1, 1차 수정의 확장안과 R1 요청은 철회).
   signal 의 `terms` 는 현행에 없는 값이라 어댑터가 요청하지 않는 것으로 화면을 유지한다.
6. split_own 행 키 정합(D13): M-1·M-2·M-3·trend 가 같은 `own_brand_code` 를 내는지 회귀 시험으로 고정한다(비트의 부모 브랜드 코드).
   그룹 간 계약 시험(`mentions/brands/tests/test_mentions_brands_fix2.py`): 같은 관점이면 M-1 당사 행과 `/v1/trend?dimension=brand&split_own=true`
   당사 계열의 (own_brand_code, brand_key) 집합이 같다(trend 통합 전에는 건너뛴다).
