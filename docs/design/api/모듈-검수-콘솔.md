# 검수 콘솔(qa) 모듈 설계

작성 2026-09-27 · 기준: 설계 공용 계약 v2(DESIGN-CONTRACT.md), 확정 DDL DB-v2.sql, 결정 G-18(a)·G-24(a) · 현행 근거: hmg-geo 7639b9e `lib/db/repositories/qa-review.ts`

## 1. 개요

Raw Data QA 콘솔은 사람이 Scope job 1건씩 원문과 분석 낱알을 보고 섹션별 ok/issue 를 판정하고 노트를 남기는 운영 화면이다. 지표 API 가 아니므로 표준 모수 규칙(D1·A1·A15·A16·R05 is_rep)은 적용하지 않는다. 모집단은 G-24(a) 에 따라 rd.job 전체(비완료·드롭 포함)다.

단위 구성:

| 단위 | 범위 | 비고 |
| --- | --- | --- |
| QA-1 | 목록·진행률·이웃·필터 옵션 | 읽기 전용 |
| QA-2 | 판정·락·세션·노트·폴링 | 쓰기는 app 스키마만(A17) |
| QA-3 | 상세 낱알 조회 | 설계 리드 신설. 현행 getReviewAnswerDetail(qa-review.ts:652)을 맡은 단위가 없어서 추가했다 |

D8 준수: 새 표·집계·캐시는 없다. 현행 unstable_cache 2곳(qa-review.ts:476-482 진행률 30초, :527-528 필터 옵션 5분)은 없앤다. 대신 인덱스 교정 1건(P-Q1)과 문서형 뷰 확장·신설 3건(P-Q2~P-Q4)을 제안한다. 뷰는 저장이 없으므로 파생 층이 아니다.

## 2. 라우터 구조

```
app/api/v1/qa/
  router.py    APIRouter(prefix="/v1/qa", dependencies=[Depends(require_qa_reviewer)])
  deps.py      require_qa_reviewer, get_ro_conn(api_ro), get_rw_tx(api_rw + set_config)
  filters.py   QaFilter, QaNoteFilter (Pydantic v2 query model)
  coords.py    resolve_filter, enrich_page
  sql.py       qa_job_scope, keyset, lock_upsert, assert_job_exists, assert_session_owner
  locks.py     LOCK_TTL_SECONDS=180, HEARTBEAT_SECONDS=30
  answers.py   QA-1 + QA-3
  reviews.py   QA-2 판정·락·세션·deltas
  notes.py     QA-2 노트
```

정적 경로(/answers/progress, /notes/counts, /notes/export)를 먼저 등록하고, 경로 변수는 uuid 로 타입을 지정한다.

## 3. 엔드포인트 명세

### 3.1 QA-1 목록 계열 (api_ro)

**GET /v1/qa/answers**: 질의 = QaFilter + cursor + limit(기본 50, 최대 200).

- 응답 `data: QaListRow[]`. 한 행 = { job_id, prompt_text, surface(global|website|project), brand[], country, engine, lang, measured_at, job_status(completed|in_progress|failed|other ← rd.job.status_code 0/1/2/3), dropped, mention_count, citation_count, note_count, review_status(unreviewed|ok|issue), reviewer_name, lock }
- `meta.next_cursor` 를 함께 낸다.
- 조회 절차:
  1. resolve_filter 로 코드를 키·project_key 배열로 푼다.
  2. 본 쿼리(qa_job_scope + 2구간 키셋) 로 limit+1 행을 가져온다. surface 가 비었거나 복수면 표면별 분기를 UNION ALL 하고 바깥에서 ORDER BY measured_at DESC NULLS LAST, answer_key DESC LIMIT n+1 로 병합한다.
  3. 페이지 배치 조회 4개(모두 등치 = ANY(페이지)):
     - 락: TTL 안의 것만
     - 노트 수: qa_note_job_idx, GROUP BY job_id
     - 멘션 수: rd.v_answer_mention_raw count
     - 인용 수: rd.v_answer_citation_raw count(P-Q3)
  4. enrich_page 로 좌표를 붙인다.

**GET /v1/qa/answers/progress**: `data: { scoped: {total, reviewed, issues, notes}, total: {...} }`.

- scoped: 공통 빌더로 COUNT(*), COUNT(rv.job_id), COUNT(*) FILTER(WHERE rv.status='issue'), COUNT(*) FILTER(WHERE EXISTS note).
- total: 조인 없이 분해한다.
  - total = count(*) FROM rd.job
  - reviewed = count(*) FROM app.qa_answer_review
  - issues = count(*) WHERE status='issue'(qa_review_status_idx)
  - notes = count(DISTINCT job_id) FROM app.qa_review_note
- 전제: rd.job 에 없는 job_id 를 가진 검수 행(고아)이 0 건이다. 대조로 확인한다.

**GET /v1/qa/answers/{job_id}/neighbors**: `data: { prev, next }`.

- 기준 행의 (measured_at, answer_key) 를 구한다.
- 같은 필터 + 부등호로 LIMIT 1 을 두 번 실행한다. 현행 getNeighbors(qa-review.ts:390-431) 패턴을 rd.job 키로 옮긴 것이다.

**GET /v1/qa/filters**: `data: { brand, country, engine, lang, reviewer }`.

| 필드 | 원천 |
| --- | --- |
| brand | app.brand (sort_order) |
| country | rd.dim_country (kind='iso') + app.website_site/app.project 국가 코드 합집합 |
| engine | rd.dim_engine |
| lang | rd.dim_lang |
| reviewer | DISTINCT app.qa_answer_review.reviewer_name |

현행은 데이터 DISTINCT 스캔이다(qa-review.ts:491-525). 차원표로 바꾸면 '현재 0건' 옵션이 섞인다(열린 질문 1).

### 3.2 QA-2 판정·락·세션 (쓰기 = api_rw, 사전 확인 = api_ro)

- **POST /v1/qa/sessions** → `{session_id}`. user_id = JWT sub, reviewer_name = user_account.display_name, ip_hash = 서버 HMAC.
- **PATCH /v1/qa/sessions/{session_id}** → last_seen_at 갱신(본인만).
- **GET /v1/qa/sessions/current** → `{session_id, reviewer_name, started_at, last_seen_at}`(BG-45 추가 2026-09-28). 부작용 없는 현재 세션 조회:
  쿠키 서명·만료 + 세션 행 존재 확인, last_seen_at 갱신 없음, Cache-Control no-store. 쿠키 없음·만료·행 삭제·게이트 꺼짐은 401(검수 레이아웃 게이트·입장 페이지가 매 렌더에 부른다).
- **POST /v1/qa/answers/{job_id}/lock** → 성공 `{job_id, session_id, reviewer_name, acquired_at, heartbeat_at}`, 실패 409 `{error:'lock-held', held_by}`. 처리 순서:
  1. assert_job_exists(ro)
  2. rw 트랜잭션 안에서 set_config
  3. assert_session_owner
  4. lock_upsert(단일 문, TTL 180초)
  5. 세션 last_seen 갱신(실패해도 무시)
- **PATCH …/lock** → `{held: bool}` (WHERE job_id AND session_id).
- **DELETE …/lock** → 본인 세션만. `?release=1`(sendBeacon) 경로는 폐지한다. 프론트는 fetch keepalive 로 호출한다.
- **GET …/review** → `QaReview`. 행이 없으면 `data: null`.
- **PUT …/review**: 본문 `{session_id, section_flags}`. 한 트랜잭션 안에서 다음 순서로 처리한다.
  1. set_config
  2. assert_session_owner
  3. lock_upsert. 실패하면 롤백 후 409 `lock-lost`
  4. `INSERT INTO app.qa_answer_review(job_id, flag_*, reviewer_id, reviewer_name, session_id) VALUES(..., app.actor(), ...) ON CONFLICT (job_id) DO UPDATE SET flag_*=EXCLUDED.flag_*, reviewer_id=EXCLUDED.reviewer_id, reviewer_name=EXCLUDED.reviewer_name, session_id=EXCLUDED.session_id, updated_at=now() RETURNING status`
  5. COMMIT

  status 는 DB GENERATED 열이다. 현행의 TS 파생 로직(qa-review.ts:876-879)은 없앤다. 미지정 섹션은 NULL 로 덮는다(현행 section_flags 전체 교체와 같다).
- **GET /v1/qa/deltas?job_ids=**(최대 200, 초과분 무시: 현행 answers/route.ts:9-20) → `{locks, reviews}`. 둘 다 PK 등치 조회다.

### 3.3 QA-3 상세 (api_ro, 신설)

**GET /v1/qa/answers/{job_id}** → `data: QaAnswerDetail`. 모든 조회가 answer_key 또는 PK 등치다.

- **answer**: rd.job ⋈ rd.v_answer_body(answer_text, model_slug, status, analysis_status, measured_at) + 좌표. 추가로 job_status, dropped 를 싣는다.
- **prompt**: rd.dim_prompt(text, lang, regions, is_korean, funnel) + 카탈로그 표시(app.prompt WHERE scope_prompt_id = dim_prompt.prompt_id AND 루트 프로젝트 AND deleted_at IS NULL, prompt_scope_idx). depth4·prompt_type·category 는 rd.catalog_entry 에 없어서 app.prompt 에서 읽는다.
- **mentions**: rd.v_answer_mention_raw WHERE answer_key = :k.
  - 정렬: mention_count DESC, display_name NULLS LAST
  - 롤업 부모 이름: 같은 답변의 display_name 이 먼저, 없으면 rd.dim_entity.rep_name(현행 qa-review.ts:689-698 계승)
  - is_own / is_excluded: registry_role 로 판정
  - 감성·유형 카운트: P-Q2 가 필요하다
- **citations**: rd.v_answer_citation_raw(P-Q3) WHERE answer_key = :k, ref_index·ord 순서.
  - 저장 분류 = scope_category
  - 오버라이드 = app.citation_domain_override(domain 정규화 lower, www 제거)
  - effective = 오버라이드 ?? 저장값(현행 qa-review.ts:717-738)
- **acr**: rd.acr_cell_job(answer_key = :k) ⋈ rd.acr_cell ⋈ rd.acr_choice(level IN (1,2,3) AND acr_cell_key = ANY) ⋈ rd.dim_entity/rd.dim_brand_name.
  - appearance_rate, acr, overall_choice_share 는 조회 시 계산한다(P1 예외).
  - 현행은 (run, prompt, target, region) 4축 근사 연결이었다(qa-review.ts:710-719). 이제 source_job_ids 에 근거한 정확 연결이라 값이 달라질 수 있다(의도된 차이).
- **derived**: rd.v_answer_registry(pin_anchor, pin_reason, drop_reason, dropped_at, + P-Q4 의 source_measured_at).

### 3.4 QA-2 노트 (쓰기 = api_rw)

- **GET /v1/qa/answers/{job_id}/notes**: qa_note_job_idx, created_at 순, 해소분 포함.
- **POST /v1/qa/answers/{job_id}/notes**: 본문 `{session_id, target_kind, target_key, target_label, severity, body}`. body 는 비어 있으면 안 되고, target_key 는 인용이면 'job_id:ord'(DDL 주석 :250). reviewer_id = app.actor() 다.
- **GET /v1/qa/notes**: QaNoteFilter + cursor.
  - 드라이버는 app.qa_review_note n(qa_note_cursor_idx)이고, rd.job j 를 job_id UNIQUE 로 조인한다.
  - qa_job_scope 의 술어를 j 에 적용하고 노트 3축을 더한다.
  - 정렬: created_at DESC, note_id DESC. 응답 행 = QaNote + prompt_text + QaCoords.
- **GET /v1/qa/notes/counts**: 같은 술어로 GROUP BY target_kind → `{kind: n}`.
- **GET /v1/qa/notes/export**: 같은 술어로 LIMIT 10000(현행 QA_NOTE_EXPORT_LIMIT, qa-review.ts:1002). text/csv 스트리밍으로 보내고, 헤더 열은 현행 export/route.ts 를 계승한다.
- **PATCH /v1/qa/notes/{note_id}**: 부분 갱신. resolved=true 면 resolved_at=now(), resolved_by=reviewer_name. false 면 둘 다 NULL(CHECK 제약 :253).
- **DELETE /v1/qa/notes/{note_id}**: 하드 삭제(현행 계승, 열린 질문 5).

## 4. 공통 구성요소

- **QaFilter**: surface[] · brand[] · country[] · engine[] · lang[] · from/to(KST, measured_at) · q(≤200, 프롬프트 텍스트) · state[](OR) · reviewer[] · has_notes · no_mentions. QaNoteFilter 는 여기에 target_kind[] · severity[] · include_resolved 를 더한다. 공통 필터 모델의 나머지 축은 ignored_filters 로 보낸다.
- **coords**: 표면별 좌표 규칙.

  | 표면 | 브랜드 | 국가 |
  | --- | --- | --- |
  | 1 global | 카탈로그(rd.catalog_entry ⋈ app.brand) | rd.job.geo_key |
  | 2 website | app.website_site | app.website_site |
  | 3 project | app.project | app.project |

  현행 BRAND_SQL/COUNTRY_SQL(qa-review.ts:206-207) 규칙을 계승한다. 필터는 project_key 배열(표면 2·3)과 카탈로그 semi-join(표면 1)으로 바꾼다.
- **qa_job_scope**: 목록·진행률·이웃·노트 3종이 공유하는 FROM + WHERE 빌더. 한 곳만 고치면 모든 화면에 반영된다(현행 answerPredicates 단일 정본 원칙 유지).
- **keyset**: 2구간(비NULL → NULL). 커서는 base64url('ts|answer_key')다. 표면이 복수면 분기별로 병합한다.
- **locks**: TTL 180초 · heartbeat 30초. 유효 락 = heartbeat_at > now() - TTL.
- **쓰기 트랜잭션 규약**: 모든 쓰기는 다음 순서를 따른다.
  1. api_ro 로 assert_job_exists
  2. api_rw 로 BEGIN
  3. set_config('app.actor_id', uid, true)
  4. assert_session_owner(세션을 쓰는 경우)
  5. DML(reviewer_id = app.actor())
  6. COMMIT

## 5. 읽기 스키마와 제안

사용 표·열은 구조화 출력의 read_schema 를 정본으로 한다. 제안 요약:

| ID | 종류 | 내용 | D8 판정 |
| --- | --- | --- | --- |
| P-Q1 | 인덱스 교정 | job_qa_list_idx → (surface, measured_at DESC NULLS LAST, answer_key DESC) | 해당 없음(인덱스 대체) |
| P-Q2 | 뷰 열 추가 | v_answer_mention_raw 에 sentiment_* 4열, type_* 5열 | 저장 없음, 허용 |
| P-Q3 | 새 뷰 | rd.v_answer_citation_raw(ing.citation 원문, ref_index, scope_category) | 저장 없음, 허용 |
| P-Q4 | 뷰 열 추가 | v_answer_registry 에 pin/drop source_measured_at | 저장 없음, 허용 |

기각: ing.answer.n_mentions/n_citations 투영(현행 수치는 행 count). 채택 안 함: api_rw 의 rd.job SELECT 권한.

## 6. 권한

- 게이트는 JWT(A8) + app.user_account.is_qa_reviewer AND status='active' 다(G-18 a). role 스코프 교집합은 적용하지 않는다(G-24 a). 현행 쿠키 게이트(lib/qa/auth.ts)는 폐지한다.
- 검수자 이름은 클라이언트 입력이 아니라 display_name 스냅샷이다. 신원 위조 방지를 HMAC 쿠키 서명 대신 JWT 서명이 맡는다.
- session_id 는 인증 주체가 아니라 탭 단위 락 소유 식별자다. 모든 쓰기에서 세션이 JWT 사용자 소유인지 검증한다.
- 롤 분리:
  - 읽기: api_ro(읽기 전용, 5초)
  - 쓰기: api_rw(app 만). rd 존재 확인은 api_ro 로 먼저 한다.
- 감사: 행마다 reviewer_id(app.actor())·session_id·시각을 남긴다. 원문 열람 접근 로그는 AU-1 결정을 따른다.

## 7. 성능 (10배 기준, RDS 실측 게이트에서 판정)

| 엔드포인트 | 10배 읽는 행 | 가지치기·인덱스 | 위험 |
| --- | --- | --- | --- |
| 목록 | 기본 limit+1(≤201)행 × 표면 3분기. 선택적 필터면 표면 슬라이스 최대 수십만~200만 행 | job_qa_list_idx(P-Q1 후), semi-join 은 catalog_entry_prompt_idx·qa_note_job_idx, no_mentions 는 뷰 등치 프로브 | medium |
| 진행률 | scoped: 필터 결과 전체 COUNT. total: rd.job 전 행 index-only + app 표 카운트 | job_qa_list_idx index-only, qa_review_status_idx | medium |
| 이웃 | LIMIT 1 × 2 | 목록과 같음 | low |
| 필터 옵션 | 차원표 수백 행 + 검수자 DISTINCT | qa_review_reviewer_idx | low |
| 상세 | 답변 1건의 멘션·인용·ACR 수십~수백 행 | 뷰 PK 경로, acr_cell_job PK, acr_choice PK | low |
| 판정·락·세션·deltas | PK 등치(deltas 최대 200) | PK | low |
| 노트 목록·카운트·내보내기 | 노트 전량(인간 생성, 10배 대상 아님) + rd.job 등치 조인 | qa_note_cursor_idx, rd.job job_id UNIQUE | low |

q(ILIKE)는 dim_prompt 약 12만 행(10배) 순차 비교다. dim_prompt_text_trgm_hint(:397)는 이름과 달리 btree(surface, project_key)라 ILIKE 를 가속하지 않는다. 실측에서 느리면 pg_trgm 을 판단한다(DDL 주석에 v3 후 판단이라고 되어 있다).

## 8. 대조 방법 (신구)

1. **목록**: 같은 필터 조합 12종(무필터, 표면별, 브랜드별, state 조합, has_notes, no_mentions, q)에서 첫 3페이지 job_id 집합과 순서를 현행 listReviewAnswers 와 비교한다. 의도된 차이는 분류해 둔다.
   - 표면 오분류 교정(qa-review.ts:185-191)
   - 날짜 경계 KST
   - 동률 정렬 키(job_id → answer_key)
2. **수치**: 행별 mention_count/citation_count/note_count 가 현행과 일치해야 한다. 드롭·비완료 job 의 인용 수로 P-Q3 필요성을 확인한다.
3. **진행률**: scoped·total 을 현행 countProgress 와 비교한다. 고아 검수 행(rd.job 에 없는 job_id) 0 건을 SQL 로 단언한다.
4. **상세**: 표본 50 job(완료·드롭·비완료·ACR 포함)의 낱알 수와 필드를 현행 getReviewAnswerDetail 과 비교한다. ACR 은 근사 연결에서 정확 연결로 바뀌므로 차이 목록을 따로 낸다.
5. **동시성**: 두 세션 동시 획득 시 한쪽만 성공하는지, TTL 만료 탈취, 판정 저장 중 락 상실 시 409 이면서 판정이 저장되지 않는지, 남의 session_id 사용 시 403 인지 확인한다.
6. **권한**: is_qa_reviewer=false 와 status='suspended' 계정은 403 이어야 한다. 쓰기에서 actor 가 빠지면 예외가 나야 한다.

## 9. 열린 질문

1. 필터 옵션을 차원표로 바꾸면 '현재 0건' 값이 드롭다운에 섞인다. 프로덕트 오너 승인이 필요하다(대안: rd.job DISTINCT 는 10배에서 캐시 없이 비싸다).
2. progress.total 을 정확 COUNT 로 유지할지, pg_class.reltuples 근사(estimate=true)를 허용할지. 현행 주석(qa-review.ts:467-471)은 이 값이 '운용 지표가 아니다'라고 적고 있다.
3. 외부 검수자 계정 규약(role='vendor', menu_groups 비움)과 display_name 필수화. AU-1 과 합의가 필요하다.
4. P-Q2~P-Q4 뷰 변경을 DDL 정본에 반영할지. 미반영이면 상세의 해당 필드는 null 이다.
5. 노트 수정·삭제를 작성자로 제한할지, 삭제를 소프트 삭제로 바꿀지(현행은 무제한 하드 삭제).
6. 브라우저별 keepalive 프리플라이트 지원이 불충분하면, Next.js 같은 출처 릴레이(Supabase SSR 세션에서 토큰을 꺼내 FastAPI DELETE 호출)를 둘지.
7. rd.job.lang_key 가 프롬프트 언어(현행 scope_prompts.lang)와 같은 값인지. 적재 모듈에 확인이 필요하다.
