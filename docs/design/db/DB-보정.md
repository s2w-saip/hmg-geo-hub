# hmg-geo 재설계 통합 DB 설계 v2

작성 2026-09-27. 입력은 설계 공용 계약(D1~D8, A1~A17), 명세서 §2~§10, 영역 설계 8개, 현행 코드 7639b9e, 프로토 v1·v2 실측, 그리고 v1 통합안에 대한 검증 3종(결정 준수, 기능 커버리지, 성능 근거)이다. 읽기 전용으로 작업했다(파일·DB·git 변경 없음). file:line 은 git grep 으로 확인한 것만 적었다.

## 0. 결론

"DB 설계부터 해야 하지 않나"에 대한 답은 **그렇다**이다. 이번 검증으로 한 가지가 더 분명해졌다. DDL 확정은 아래 두 가지에 걸려 있고, 둘 다 아직 없다.

1. **제품 결정 4건**
   - G-01: 언급 그레인. 명세 P2 예외를 둘지.
   - G-03: 답변 행에 당사 측정 열을 둘지.
   - G-23: 엔티티 카탈로그의 엔티티별 수.
   - G-25: 동시성 조건에서의 1초 SLO.
2. **폭 10배 실측(v3 게이트)**: 지금까지의 10배는 과거 회차를 복제해 날짜만 민 "이력 10배"였다. 프롬프트·URL·브랜드 키 카디널리티가 1배에 머물렀으므로, 폭 10배를 뒷받침하는 근거는 0 이다.

v1 대비 구조 변경은 7가지다.
- `rd.job` 신설: 모든 Scope job 의 색인.
- 문서형 뷰 6개: ing 직접 읽기 제거.
- 자식 게이트 전파 함수: 카드와 점유율의 모수 불일치 방지.
- `rd.catalog_entry` 쓰기 주체를 적재기로 변경.
- R08 발행 비율 정정.
- 스탠스·GA4 를 원본 그레인으로 복귀.
- 인용 모수에서 분석 결손 분리(G-21 g).

## 1. 스키마와 쓰기 주체 (A17, 계약 §5)

| 스키마 | 성격 | 쓰는 주체 | 읽는 주체 |
| --- | --- | --- | --- |
| ing | Scope·GA4 원본, 운영자 레지스트리, 회차 원장 | loader 롤만 | loader, rd 뷰(소유자 loader_ro) |
| rd | 읽기 투영(측정·차원·회차·ACR·GA4·키워드·발행값) | loader 롤만(적재 트랜잭션) | 기능 API(api_ro) |
| app | 사용자·권한·프로젝트·카탈로그·규칙·감사·QA·발행 리포트 | api_rw(+judgment_change) | 앱 API, loader(판정 입력) |
| ext | DataForSEO 응답, 컨텍스트 맵, webgeo | loader(외부 적재) | 기능 API |
| mig / archive | 이관·대조 원장 / 백업 | migrator | 하네스 |

- **앱 요청 경로**: 앱은 `app.judgment_change` 에 요청 행만 쓴다. 대상은 카탈로그 편집, 엔티티 역할, 오버라이드, 프로젝트 설정, 회차 숨김·마감, 앵커 고정, 드롭, 발행이다. 적재기가 ing·rd 를 한 트랜잭션에서 반영하고 세대를 올린다. v1 에서는 앱 트리거가 `rd.catalog_entry` 를 직접 썼는데, 이 경로를 없앴다.
- **문서형 조회 경로**: 본문·엔티티 원본·발생·스탠스 근거·고정/드롭 사유는 rd 뷰에서 answer_key 등치로만 조회한다. 뷰에는 `rd.job` 의 스코프 열이 들어 있어 API 가 fail-closed 로 검사한다.

## 2. 그레인

**원칙**: 명세 P2(spec.template.html:146)와 A17 승인 근거(:349)에 따라, **원본과 1:1 인 투영만 승인 범위 안**이다. 원본보다 그레인을 줄인 투영은 결정 대상으로 올린다.

| 읽기 표 | 1행 | 원본 대비 | 비고 |
| --- | --- | --- | --- |
| rd.job | Scope job(모든 status·드롭) | 1:1 | QA·드릴다운 색인, measured_at 보유 |
| rd.answer | 완료·비드롭 job | 1:1(부분 집합) | 당사 측정 열은 G-03 |
| rd.answer_brand | 답변 × 표시 브랜드 × 경쟁 여부 | **축소** | G-01, P2 예외 필요 |
| rd.answer_stance | job × 턴 × 엔티티 | 1:1 | v1 brand_stance 대체 |
| rd.citation | 인용 원소 | 1:1 | 모수 cit_in(결손 무관, G-21 g) |
| rd.acr_cell / acr_choice / acr_cell_job | prompt-run / × 엔티티 × 레벨 / × source job | 1:1 | |
| rd.ga4_row | GA4 보고서 행 | 1:1 | v1 일 합산 표 대체, 사용자 수 합산 금지 |
| rd.cycle, rd.catalog_entry, rd.dim_* | 회차·카탈로그 행·차원 | 1:1 | 쓰기 주체 = 적재기 |
| rd.kw_*, rd.report_unit_value | 공급자 그레인 / 활성 발행 × 유닛 | 1:1 | |

**D8 예외·긴장 전수**
1. rd.answer_brand 그레인(G-01)
2. rd.answer 당사 측정 열(G-03)
3. ing.cycle 의 완료·결손 카운터. R01·R08 게이트 근거로만 쓰고 API 에 노출하지 않는다(G-09).
4. 인용 그레인 예외(G-02, v3 실패 시)

그 밖의 답변 가로지르기 저장은 없다. v1 의 `rd.dim_entity.last_seen` 도 뺐다.

**P1 예외(조회 시 계산)**
- 관점별 톤 비교
- M05 owner_key 허용 배열
- M04 HMG = 3사 순위 중 0 을 뺀 최솟값
- R03 view_date ≤ 오늘
- 프롬프트 수 count(DISTINCT)

## 3. 무결성 장치

- **게이트 전파(B3)**: 게이트 사본은 자식 표(answer_brand·answer_stance·citation·job)에 있다. 이 사본은 `rd.propagate_answer_gates(answer_key[])` 로만 갱신하고, 같은 함수 안에서 동치를 단언한다. run 상태만 바뀐 경우도 `UPDATE … RETURNING answer_key` 로 전파한다. 야간 감사가 leaf 단위로 다시 확인한다.
- **당사 합 불변식**: 같은 답변의 answer_brand 자사 행 합은 rd.answer 당사 열과 같아야 한다. 어기면 롤백하고 경보한다.
- **R08(B5)**: `analysis_done_ratio = (completed − gap) / completed ≥ 0.95` 일 때 발행한다.
- **R05**: 대표는 회차 내부 셀에서 elig 후보 중 measured_at 최신 1건이다. 회차 상태와 무관하므로 숨김 운영 때 재선정하지 않는다.
- **규칙 지문**: app.rule_set 에 13개 지문이 필수다(CHECK). 경쟁사 도메인 토큰을 추가했다(competitor-brand.ts:8).

## 4. 적재 흐름 (A10)

run 1개를 트랜잭션 1개로 처리한다. 순서는 다음과 같다.

1. 스테이지 전량 확인
2. 해시 diff 로 원본 반영
3. 원장·귀속(R02·R01)
4. rd.job·rd.answer 투영
5. 자식 투영
6. 당사 요약
7. 게이트 전파와 불변식 단언
8. 셀 대표 재선정
9. 회차 재평가(R08 정정)
10. 세대 증가 후 커밋, 커밋 뒤 leaf 에 VACUUM (ANALYZE)

재판정 큐는 규칙·프로젝트 설정·rule_param·Scope 프롬프트 변경과 운영자 요청을 모두 적재기가 처리한다. 범위가 크면 leaf 스왑으로 넘긴다. 단계별 상세는 ingestion_flow 에 있다.

## 5. 성능: 정정과 게이트

**정정 사항**
- v1 의 "폭 10배 1초 가능"은 철회한다. 근거는 이력 10배(키 카디널리티 1배)였다.
- 인용 1년 웹사이트 조합은 "경계"가 아니라 **초과 예상**이다. 웹 1.7~2.0초(3 프로세스), 7 프로세스 독점을 가정하면 콜드 약 1.0~1.2초다.
- 처리량 가정(500만 행/초/프로세스)은 실측 근거가 없다.
- 화면 하나가 API 5개 이상을 동시에 부른다. 쿼리 하나가 워커를 독점한다는 전제는 성립하지 않는다.
- v2b 가 느린 원인에 CPU·조인·해시 유출 부류가 있다. 따라서 "배치 결함만 고치면 된다"는 전제도 근거가 없다.

**현재 확실한 근거**
- v1 이력 10배: 최악 p95 601ms, 첫 실행 804ms(파티션 없음, 3 프로세스)
- std_in 판정 열로 추정 붕괴 해소
- v2a 원본 = 읽기는 1배에서 이미 1.25초
- v2b 최악 17,091ms(원인 5부류)

**v3 게이트(DDL 확정 전 필수)**

| 항목 | 내용 |
| --- | --- |
| 폭 10배 합성 | 새 prompt·URL·도메인(롱테일 유지)·브랜드·엔티티 키를 발급하고, 회차당 행 10배. 이력 1년은 별도 축 |
| 배치 | 이 v2 DDL 그대로 |
| 조합 | 14조합 + 택소노미·태그·언어·출처 필터, 상수 배열 1,000 초과 경로 |
| 기능 | F01~F07 + 인용 URL 목록·톤별 URL·SA-06·신호 프롬프트·필터 옵션 전 기간·QA 미검수·AD-01 |
| 동시성 | 화면 단위 동시 호출(1·3·5명) |
| 콜드 | 인스턴스 재부팅 후 첫 호출. OS 캐시가 남은 재시작은 웜으로 구분 |
| 진단 | 300ms 초과 칸은 EXPLAIN (ANALYZE, BUFFERS, SETTINGS) 를 남기고 5부류로 분류. work_mem 64MB·256MB 비교, 계획 시간 측정 |
| 적재 | 6.6만 job run 전체 체인 소요, 적재 직후 추정 오차 |
| 합격 | 명세 그대로: 각 기능 API 콜드 p95 ≤ 1초(동시 조건), heap fetch·temp 0, 카드 = 추이 합 70/70, unexplained 0 |

불합격하면 G-02(인용 예외), G-17(창 상한), G-25(동시성·사양·API 병합) 중에서 제품 책임자가 결정한다.

**사양**
- 작업 집합을 약 12~14GB 로 다시 추정했고, 같은 인스턴스의 ing 핫셋과 경합한다. 시작 후보는 db.r7g.4xlarge(16 vCPU·128GB)다. 2xlarge 는 v3 에서 동시성 합격 시에만 채택한다.
- gp3 처리량을 명시해야 한다(콜드 경로가 여기에 달려 있다).

## 6. 기능 커버리지

§7 의 10개 그룹 모두 rd·app·ext 에서 나온다. 검증에서 지적된 매핑 오류는 모두 고쳤다.

| 기능 | v1 문제 | v2 경로 |
| --- | --- | --- |
| QA | ing 대량 매핑 | rd.job + 뷰 + dim_prompt.text + acr_cell_job |
| WA-23 신호 | rd.answer 만으로 매핑(오류) | rd.answer_brand 자사 행 |
| SA-06 | answer_brand ⋈ citation 조인 누락 | 조인 명시 |
| 경쟁사 인용 점유율 | 규칙이 TS 에만 있음 | dim_source.competitor_brand_key |
| 프로젝트 자사 | 도메인 폴백·카탈로그 합류 누락 | 설정 ∪ 도메인 폴백 ∪ 카탈로그 |
| W-10·11 퍼널 | 루트 카탈로그로만 한정 | dim_prompt.funnel_key |
| PR-01 수집 기간 | round_date 로 조용히 대체 | rd.job.measured_at |

미정·결손으로 남은 것은 셋이다.
- AD-01 엔티티별 수: G-23 결정 대기.
- 가시성 4분면·웹사이트 ACR: 원천 미확인이라 A12 "준비 중".
- 스탠스: 과거 데이터 결손.
