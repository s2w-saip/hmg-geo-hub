# 시나리오 테스트 (2026-11-07)

Next 서비스의 동작을 역할별 시나리오로 실제 브라우저에서 눌러 봤다. 코드는 고치지 않았다. 결함은 심각도 순으로 하나씩 고친다.

## 결론

높음 2건을 찾았다. 둘 다 운영 빌드나 새 회차에서만 드러나서 지금까지의 테스트(개발 서버, 고정 회차)에 안 잡혔다. 나머지 기능은 통과했고 값도 맞았다.

### 결함 1 조사

- 필터 한 번에 `router.replace`는 한 번이고 응답은 끝까지 온다. 콘솔 오류는 없다.
- 멈춘 페이지의 React 루트는 `pendingLanes = suspendedLanes`이고 ping이 없다. 라우터 상태의 페이지 노드는 `rsc = null`, `lazyData` 완료다.
- 응답을 버퍼링해 한 번에 주면 14번 중 0번이다. 응답이 스트리밍으로 나뉘어 오는 것과 관련 있다.
- 관련 없음: 미리 받기(prefetch 0건), 서버 압축(꺼도 18번 중 6번), 다른 세션의 부하(전용 서버에서도 재현), 페이지 로드 직후 클릭(5초 기다려도 15번 중 7번).
- VM은 확인하지 않았다. 운영 빌드라 같을 가능성이 높다.
- React(`front-react`) 운영 빌드는 이미 조회한 조건을 포함해 42번 눌러 0번이다(세션 e6). 다음 조사는 Next 라우터와 `startTransition` 쪽부터 한다.

### 테스트 뒤 고친 것

- `f1b05aa`(세션 e6): 소유 URL 저장 직후의 계산이 이전 입력의 캐시 키로 남던 경합을 데이터 서버에서 막았다. 위 '소유 URL 등록'이 통과한 것은 Next의 읽기가 조금 늦어서였다. 이 테스트는 수정 전 코드에서 돌았고, 공유 :5555는 아직 재시작하지 않았다.

- 레거시 Admin 11개 · `/ko/projects/new`의 '불러오지 못했습니다'는 2026-10-27부터 알고 있던 일이다(`next-service-check.md`).

- 출처 교정이 화면 값을 안 바꾸는 것은 규칙이다. 처음에 기대값을 잘못 적었다.

- 응답 버퍼링 모드에서만 React #418(hydration)이 4번 보였고, 화면에는 영향이 없었다. 버퍼링 없이 8번 열어 0번이다.
