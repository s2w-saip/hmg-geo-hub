1. 의심 결함

ACR 화면의 차종 전환율(구 Q5)은 차종 표시 이름(rd.dim_entity.rep_name) × 소속 브랜드로 묶어 sum(choice) ÷ sum(cells.valid_acr) 로 계산합니다. 분모는 조인된 rd.acr_choice 행마다 그 셀의 valid_acr 를 더합니다.

-- back/app/features/analytics/funnel/acr/queries.py · models_sql (128행 부근)
SELECT de.rep_name AS model, pb.name AS brand,
       sum(ch.choice)::int AS choice, sum(cells.valid_acr)::int AS cell_vacr,
       count(DISTINCT ch.acr_cell_key)::int AS cells
  FROM cells JOIN rd.acr_choice ch ON ch.level = 2 AND ch.acr_cell_key = cells.acr_cell_key
  JOIN rd.dim_entity de ON de.entity_key = ch.entity_key
  LEFT JOIN rd.dim_brand_name pb ON pb.brand_key = ch.parent_brand_key AND ch.parent_brand_key <> 0
 WHERE de.rep_name IS NOT NULL
 GROUP BY de.rep_name, pb.name
  • rd.acr_choice 의 기본 키는 (level, acr_cell_key, entity_key) 라서 한 셀 안에서 엔티티마다 한 행입니다.
  • 그런데 묶음 키는 엔티티가 아니라 이름입니다. rd.dim_entity 는 entity_id(UUID)만 유일하고 rep_name 에는 유일 제약이 없습니다(back/db/DB-v2.32.sql 의 CREATE TABLE rd.dim_entity).
  • 그래서 같은 이름·같은 소속 브랜드의 엔티티 2개가 한 셀에 함께 있으면 그 셀의 valid_acr 가 두 번 더해집니다. 바로 옆 열 cells 는 count(DISTINCT …) 라 중복이 없는데 분모만 중복됩니다.
  • 함수 docstring 의 "행이 셀 × 엔티티 유일이라 합이 곧 그 값"은 엔티티 단위에서는 맞지만 이름 단위 묶음에서는 맞지 않습니다.
예: 셀 valid_acr = 10, 엔티티 E1 "Tucson" choice 3, E2 "Tucson" choice 2(같은 소속 브랜드).
현재 계산 = 5 ÷ 20 = 25.0%. 이름 기준 의도 = 5 ÷ 10 = 50.0%.

legacy 도 같은 결함입니다. front/lib/db/repositories/scope-aggregates.ts 9715행 부근(Q5)이 GROUP BY x.brand, COALESCE(x.parent_brand, pn.brand) 로 묶고 sum(x.valid_acr_iterations) 를 분모로 쓰며, 주석에 같은 가정("행이 (셀×엔티티) 유일이라")이 있습니다. 그래서 고치면 중복이 있는 차종에서는 legacy 와 값이 달라집니다.

2. 이 기기에서 못 한 이유

  • AWS CLI 는 있지만 ~/.aws 에 자격증명이 없었습니다.
  • infra/state.env(EC2 ID 등, 커밋 금지 파일)와 front .env(DB 접속)가 없었습니다.

단계 1 — 중복이 존재하는가

WITH x AS (
  SELECT ch.acr_cell_key, de.rep_name, ch.parent_brand_key, count(*) AS n_ent
    FROM rd.acr_choice ch JOIN rd.dim_entity de ON de.entity_key = ch.entity_key
   WHERE ch.level = 2 AND de.rep_name IS NOT NULL
   GROUP BY 1, 2, 3 HAVING count(*) > 1)
SELECT count(*) AS dup_cells,
       count(DISTINCT (rep_name, parent_brand_key)) AS models,
       max(n_ent) AS max_dup
  FROM x;

같은 쿼리를 최근 90일로 좁혀 한 번 더 돌립니다(JOIN rd.acr_cell c ON c.acr_cell_key = ch.acr_cell_key 후 c.round_date >= current_date - 90 AND c.acr_in). 화면은 acr_in 셀만 읽습니다.

판정: dup_cells = 0(전체·최근 모두) → 단계 4 의 "영향 없음" 경로. 0 보다 크면 단계 2·3 진행.

단계 2 — 어떤 차종이, 왜 겹치는가

WITH x AS (
  SELECT ch.acr_cell_key, de.rep_name, ch.parent_brand_key,
         count(*) AS n_ent, array_agg(DISTINCT de.entity_id::text) AS entity_ids,
         array_agg(DISTINCT de.entity_type) AS entity_types
    FROM rd.acr_choice ch JOIN rd.dim_entity de ON de.entity_key = ch.entity_key
   WHERE ch.level = 2 AND de.rep_name IS NOT NULL
   GROUP BY 1, 2, 3 HAVING count(*) > 1)
SELECT x.rep_name, b.name AS parent_brand, count(*) AS dup_cells, max(x.n_ent) AS max_dup,
       (array_agg(x.entity_ids))[1] AS sample_entity_ids, (array_agg(x.entity_types))[1] AS entity_types
  FROM x LEFT JOIN rd.dim_brand_name b ON b.brand_key = x.parent_brand_key
 GROUP BY 1, 2 ORDER BY dup_cells DESC LIMIT 30;

원인을 둘로 나눠 기록합니다. (가) 같은 차종이 레지스트리에서 다른 엔티티로 중복된 경우(병합 누락), (나) 실제로 다른 엔티티인데 표시 이름이 같은 경우(트림·세대 등). (가)라면 레지스트리 정리도 별도 과제로 보고합니다.

단계 3 — 화면 값이 얼마나 달라지는가

글로벌·최근 90일·acr_in 셀 기준 근사치입니다(화면의 필터 축·창은 cells_cte 가 더 좁힘). 현재식과 고친식(셀마다 valid_acr 한 번)을 나란히 냅니다.

WITH cells AS (
  SELECT c.acr_cell_key, c.valid_acr FROM rd.acr_cell c
   WHERE c.surface = 1 AND c.acr_in AND c.round_date >= current_date - 90),
per AS (
  SELECT ch.acr_cell_key, de.rep_name, ch.parent_brand_key,
         sum(ch.choice) AS choice, count(*) AS n_ent
    FROM cells JOIN rd.acr_choice ch ON ch.level = 2 AND ch.acr_cell_key = cells.acr_cell_key
    JOIN rd.dim_entity de ON de.entity_key = ch.entity_key
   WHERE de.rep_name IS NOT NULL
   GROUP BY 1, 2, 3)
SELECT p.rep_name, b.name AS parent_brand, sum(p.choice) AS choice,
       sum(c.valid_acr * p.n_ent) AS den_current, sum(c.valid_acr) AS den_fixed,
       round(100.0 * sum(p.choice) / nullif(sum(c.valid_acr * p.n_ent), 0), 1) AS rate_current,
       round(100.0 * sum(p.choice) / nullif(sum(c.valid_acr), 0), 1) AS rate_fixed
  FROM per p JOIN cells c USING (acr_cell_key)
  LEFT JOIN rd.dim_brand_name b ON b.brand_key = p.parent_brand_key
 GROUP BY 1, 2
HAVING sum(p.n_ent) > count(*)
 ORDER BY rate_fixed - rate_current DESC LIMIT 50;

보고 형식: 영향 차종 수, 상위 차종별 현재 → 고친 값(%p 차이), 화면 상위 노출 차종(전환율 상위 12) 중 순위가 바뀌는 차종.

7-1. 운영 데이터 대조(원래 화면과 숫자 일치)

리뉴얼 화면은 원래 화면과 같은 읽기를 쓰므로 같은 조건에서 숫자가 모두 같아야 합니다. 다르면 리뉴얼 쪽 결함입니다. stg 또는 미리보기 배포에서, 계정 4종(admin, HQ, 권역 담당, 국가 담당)으로 확인합니다.

단계 1 — Overview

Overview 는 두 화면이 같은 URL 쿼리를 읽습니다. 같은 쿼리로 /ko/dashboard?… 와 /ko/renewal/dashboard?… 를 나란히 엽니다.

조건(쿼리)계정
(필터 없음)admin, HQ, 권역, 국가
brand=Hyundaiadmin
brand=Hyundai&geography=DE~FR (여러 값 구분자는 ~)admin
time=<from>..<to> 월간 프리셋(패널에서 선택)admin, HQ
engine=chatgpt&promptContext=비교/검증국가

비교 항목(2026-10-22 Overview 개편 기준): KPI 5종 값·증감(기간을 고르면 기간 비교 칩)·비교 브랜드 중 순위, 브랜드 비교 표(브랜드 × 5지표 값, 경쟁사는 원래 카드의 경쟁사 4곳), 시장별 현황 표(권역·국가 × 5지표 값, 최대 경쟁사 이름과 그 값 = 값 − 격차, 답변 수).

통과 기준: 모든 숫자가 원래 화면과 같음. 원래 화면에 없는 표시(브랜드 비교의 당사 행 이름 등)는 비교하지 않습니다.

단계 2 — 글로벌 프롬프트

두 화면에서 같은 조건을 고른 뒤 비교합니다. 조건: 없음 / 리스트 유형 하나 / Depth1 하나 / 대상 시장 하나 / 측정 상태 = 미측정 / 검색어 하나.

비교 항목: 전체 건수와 필터 결과 건수, 기본 정렬(Depth1 오름차순) 첫 페이지 행과 순서, 축별 옵션 목록, 엑셀 행 수, 변경 이력 탭 건수.

통과 기준: 모두 같음.

단계 3 — 운영 규모에서의 체감 속도

  • 필터를 하나 눌렀을 때 진행 표시가 사라질 때까지 걸리는 시간(두 화면 모두).
  • 글로벌 프롬프트: 옵션 집계(상위 축을 바꿀 때마다 다시 계산), 검색 응답, 엑셀 다운로드 시간. 프롬프트가 1만 건을 넘는다는 전제로 봅니다.

단계 4 — 보고

단계별 결과를 표로 정리해 사용자에게 보고합니다. 다른 숫자가 있으면 원인을 찾아 수정안을 제시하고, 승인 후 수정합니다.

7-2. 글로벌 프롬프트 1만 건 대응(결정 대기)

지금 화면은 알고 있는 프롬프트를 찾는 데는 충분하지만, 1만 건 전체를 파악하기에는 부족하다는 판단입니다. 막히는 지점은 다섯 가지입니다.

  • 옵션별 건수가 없어 0건 조합에 자주 빠짐.
  • 한 축에서 하나만 고를 수 있음.
  • 전체 요약이 '표시 N / 전체 M' 하나뿐.
  • 같은 원문의 언어·시장 버전이 흩어짐.
  • 검색이 본문 부분 일치뿐.
안내용비용
A옵션별 건수 표시, 0건 옵션은 흐리게서버 집계 쿼리 확장(front/lib/db/repositories/catalog-page.ts scopeMeta, api 경로 포함)
B한 축 안 다중 선택(OR)서버 필터·URL 형식 변경. "원래 화면과 100% 같은 필터" 결정 번복
C상단 요약표(시장·언어·퍼널별 건수, 측정중/미측정), 누르면 필터집계 API 추가
D원문 기준 묶어 보기(언어·시장 버전을 한 행으로)prompts 테이블에 원문을 잇는 키가 없음 → 데이터 모델부터
E촘촘한 보기, 검색어 강조, 분류명 검색프론트만

사용자에게 받아야 할 답: (1) 1만 건의 구성(원문 수백 개의 언어·시장 버전인지, 서로 다른 프롬프트인지 — D 필요 여부), (2) 사용자가 이 화면에서 주로 하는 일(찾기 / 시장·언어별 확인 / 미측정 점검 / 엑셀 추출 — A·B 와 C 의 순서).

A·B 와 분류 트리는 2026-10-20 의 S급 목업 초안(다중 선택·옵션 건수·분류 트리)에 있던 설계입니다. 그 초안은 커밋된 적이 없고 작성 기기 임시 폴더의 백업에만 있습니다. 지금 docs/design/ui/global-prompts-filters.html 은 구현과 같게 다시 쓴 판입니다.

7-3. 화면별 미결 사항

#화면내용출처
1AI 가시성실데이터 대조 — GSC · 크롤 로그 수집기가 연결되기 전에는 모든 환경이 ‘연결된 사이트가 없습니다’(back/analytics/README.md).인계 11절 ② · 검토 메모
2AI 가시성응답 크기 — API 가 페이지 · 기기 · 봇별 일별 행을 모두 보냅니다. 실데이터 규모를 보고 BFF 가 표 행을 잘라 보낼지(예: 상위 N + 검색) 결정.인계 11절 ③ · 검토 메모
3AI 가시성카드 메뉴(CSV · 표/차트 전환)가 아직 없음.인계 11절 ④
4AI 가시성크롤러 · 엔진 · 국가 — 크롤러 목록 · 엔진 연결 원천 analytics.dim_crawl_bot 이 비어 있음, 엔진 필터 옵션은 답변 엔진(ChatGPT · Gemini)뿐, 국가 선택지는 답변 측정 국가라 사이트 없는 국가도 고를 수 있음.검토 메모
5ACR엔진 미선택 시(DC-01) — 신규 API 는 엔진을 고르지 않으면 기본 엔진만 집계해 엔진별 카드가 한 열이 됨. 결정 필요.검토 메모
6ACR추이 단위(U8-N20) — 구 경로는 일별(measured_at), API 는 회차별(최근 12회). 힌트 ‘일별 최종 추천 선택률’ → ‘회차별’.검토 메모
7ACR국가 옵션 — 선택지가 답변 측정 국가(ACR 측정 국가가 아님)라 ACR 없는 국가도 고를 수 있음(그때 ‘결과 없음’). ACR 측정 국가로 좁힐지 결정 필요.검토 메모
8ACR브랜드 전환율(선택 사항) — ‘후보로 오른 셀에서 실제로 선택된 비율’은 API 에 없음. scope_acr_rollups 의 셀별 유효 반복 수로 브랜드별 Σ 집계 하나를 더하면 차종 전환율과 같은 산식으로 낼 수 있음.검토 메모
9언급렌즈의 4개 값 — 타일 4개에 값을 보이려면 히어로 4개를 함께 읽어야 함(각각 스트리밍). 리뉴얼 KPI 탭 구현으로 풀렸는지 확인.검토 메모
10언급브랜드 → 모그룹 매핑 — 앱에 모그룹 정보가 없음(entity_registry = 이름 · 역할뿐). 매핑을 새로 두고(정적 파일 또는 엔티티 카탈로그 관리 화면) 없는 브랜드는 ‘미분류’. 합작 · 소수 지분 규칙도 정해야 함(예: Smart = Mercedes · Geely 50:50, Proton = Geely 49.9%, Mitsubishi = Nissan 34%).검토 메모
11인용legacy 에서 확인된 것 — ① 출처 필터가 걸리면 인용/미인용 프롬프트 수를 계산하지 않아 타일이 꺼지고 잘못된 안내(리뉴얼 구현은 이유를 바르게 표시) ② 하위 프롬프트 페이지의 당사 판정 단위(도메인)가 메인(인용 행)과 달라 수가 어긋날 수 있음 ③ 증감 기준 문구가 화면 리더 전용이라 보이지 않음 ④ 톤 안내 ‘카테고리 필터와 무관’은 새 백엔드 경로에서 틀림.검토 메모
