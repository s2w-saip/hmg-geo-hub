**지금 할 일:** 1단계 GA4 연동. 원본 화면(`ga4-registry-client.tsx`)의 기능 목록을 뽑아 사용자에게 범위를 확인받는다.

## 절대 규칙

1. **순서대로만 한다.** 0 → 1 → 2 → 3 → 4 → 5 → 6. 앞 단계가 완료되기 전에는 다음 단계를 시작하지 않는다. 완료란 공통 완료 기준을 모두 채우고 사용자가 확인한 상태다. 결정 대기로 막히면 사용자에게 묻는다. 단계를 건너뛸지는 사용자만 정한다.
2. **결정 대기(⛔)는 추측으로 정하지 않는다.** 사용자에게 묻고, 답을 아래 '결정 기록'에 날짜와 함께 적은 뒤 진행한다.
3. **세션을 마칠 때 이 파일을 고친다.** 체크 표시, '지금 할 일' 줄, '진행 기록' 한 줄을 갱신한다. 커밋한 항목에는 커밋 해시를 붙인다.
4. **각 단계는 범위 확인부터 시작한다.** 원본 화면(`front/app/[locale]/(dash)/admin/…`)의 기능 목록을 뽑아 사용자에게 보이고, 어디까지 옮길지 확인받은 뒤 설계한다.
5. **데이터 원칙은 어기지 않는다.**
   - Gold에는 쓰지 않는다.
   - BFF가 Gold의 귀속(당사, 부모 브랜드, 출처 카테고리 등)을 읽을 때 덮어쓰거나, 합치거나, 다시 정하지 않는다.
   - HUB가 새 판단을 만들지 않는다. 유의성, '의미 있는 변화', 기준 재정의가 여기에 든다.
   - 외부 API에는 수집·가공 입력만 내보내고 결과는 내보내지 않는다. GA4 속성은 외부 API에 나가지 않는다.
   - 키·토큰·자격 증명은 DB나 git에 두지 않는다. git에서 제외된 `.env.*.local`에만 둔다.
6. **커밋·푸시는 사용자가 요청할 때만 한다.** 작성자 환경변수 등 나머지는 CLAUDE.md 작업 규칙을 따른다. 다른 세션이 같은 작업 트리를 쓰므로 커밋할 때는 그 단계의 파일만 스테이징한다.

### 1. GA4 연동 (`/admin/ga4`)

목표는 속성 목록을 파일(`.local/ga4-properties.json`)에서 HUB 데이터 DB로 옮기는 것이다. 관리자가 화면에서 등록·수정·중지하고, 수집기는 DB에서 목록을 읽는다.

- [ ] 범위를 확인한다. 원본(`ga4-registry-client.tsx`)에는 속성 이벤트 목록, 프로젝트별 덮어쓰기, 레거시 가져오기가 있다. 이 셋을 옮길지 확인한다.
- [ ] 등록부 표를 설계한다. 수집기가 데이터 DB에만 접속하므로 데이터 DB에 둔다.
  - 담을 값: 속성 ID, 브랜드, 국가, 전환 기준(key_events / events와 이벤트 목록), 상태(active / unmapped / 중지).
  - 수집기가 쓰는 `analytics.ga4_property`(pending_grant 등)와의 관계를 정한다.
  - 변경 이력을 어디에 남길지 정한다.
- [ ] 전용 DB 역할을 만든다. 등록부 표만 INSERT·UPDATE하고, 지우기 권한은 없다.
- [ ] 입력 검증은 지금 `load_registry` 규칙과 같게 한다: 숫자 ID, 브랜드 Hyundai·Kia·Genesis, ISO-2 국가, basis가 events면 이벤트가 1개 이상. 같은 규칙을 DB 제약이나 BFF에 둔다.
- [ ] 수집기 `back/analytics/ga4_collect.py` 가 DB 등록부를 읽게 한다. 파일은 처음 한 번 가져오는 데만 쓰거나 없앤다. `test_ga4_collect.py` 를 갱신한다.
- [ ] 화면을 만든다.
  - 목록 열: 브랜드, 국가, 속성 ID, 전환 기준, 상태, 마지막 수집일. 상태와 수집일은 수집기가 남긴 값을 그대로 보인다.
  - 등록·수정 폼.
- [ ] ⛔B 검증 버튼을 만든다. 결정이 난 뒤에 한다.
- [ ] 같은 커밋에서 절차 문서를 새 방식으로 고친다: `scripts/vm.sh` 의 ga4 안내, 인계 문서 `p4-acr-model-denominator.html` 7-3절 13·18번, CLAUDE.md 'GA4 수집 시작' 줄.
- [ ] 공통 완료 기준을 채운다.
