HMG-GEO-HUB 아키텍처

로컬 서비스는 화면 서버(Next.js)와 API 서버(FastAPI BFF) 두 프로세스, 그리고 DB 세 개로 돌아간다. 브라우저는 Next만 부르고, 화면을 위해 DB에 접속하는 것은 BFF뿐이다. GEO 측정값은 외부 Gold DB에서 읽기만 하고, HUB가 직접 가진 데이터는 데이터 DB와 운영 DB 두 곳에 나눠 둔다. 이와 별도로 외부 API(back/ext)가 현재 저장된 프롬프트와 그 수집·가공에 필요한 값을 API 키를 가진 외부 호출자에게 읽기 전용으로 준다(외부 API).

정본(SSOT) · 서비스 구조와 HUB DB ERD는 이 문서 하나에만 둔다. 테이블·컬럼·권한의 최종 근거는 SQL 마이그레이션이고, 이 문서는 그것을 그림으로 옮긴 정본이다. 구조나 스키마를 바꾸는 변경은 같은 커밋에서 이 문서를 고친다. 방법은 이 문서 고치는 법.

요청이 지나가는 길

  • Next는 계산하지 않는다. 페이지는 /v1/screens/{name}에서 완성된 뷰모델을 받아 그리기만 한다. 지표 계산은 BFF의 screens/ 빌더 94개가 맡는다. 페이지를 연 뒤 브라우저가 더 읽는 부분(글로벌 · Website 프롬프트 목록의 검색 · 정렬 · 다음 쪽과 엑셀 행, Website 프롬프트 인사이트, ACR 분포 시트를 탭을 열 때 하나씩)은 /api/standard/* · /api/website/prompts/* 얇은 프록시가 같은 방식으로 화면 빌더에 넘긴다. 로컬 모드는 /api/hub/* 밖의 GET 아닌 요청을 막으므로, 이런 읽기는 서버 액션(POST)이 아니라 GET 프록시로 둔다.
  • 빌더는 HTTP를 다시 타지 않는다. api.get()으로 같은 프로세스 안에서 읽고, 동시에 들어온 같은 읽기는 한 번만 실행한다. Gold 읽기의 답은 아래 Gold 읽기 캐시에 두고, 브라우저로 가는 응답은 모두 no-store다. 한 읽기가 20초를 넘으면 그 구역만 504로 비운다.
  • Gold 읽기 캐시(2026-10-29). 화면 빌더가 읽는 Gold /v1 읽기의 답(JSON)을 BFF 프로세스 메모리에 둔다(gold_reader/cache.py, api.get 안). 키는 경로·쿼리이고, 둔 답은 Gold 상태가 그때와 같을 때만 쓴다. Gold 상태 = 쿼리 하나(약 10ms)로 읽는 지문: active release와 그 항목·빌드 상태, gold.data_version, gold 표마다 relfilenode(통째 재적재는 표를 새로 쓴다 — 10-28 재적재는 data_version을 바꾸지 않았다), dim_cycle 노출 열, gold 표 쓰기 수(pg_stat, 트랜잭션 밖이라 1초쯤 늦다), 그리고 날짜(서울). 읽기 앞뒤 지문이 같을 때만 둔다(그 사이에 쓰기가 없었다는 뜻 — 적재 도중 두 세대가 섞인 답은 답하되 두지 않는다). 최대 10분(HGH_GOLD_CACHE_S, 0이면 끔), 합계 256MB(HGH_GOLD_CACHE_MB)를 넘으면 오래 안 쓴 것부터 버리고, 그 1/10을 넘는 답은 두지 않는다. Gold가 모든 적재에서 버전을 올리고 적재 완료 표시를 두면(개편 Q18) 쓰기 수 대신 그것을 지문에 쓴다.
  • 필터 옵션 캐시. /v1/filters/options는 기간을 읽지 않으므로 그 data를 BFF 프로세스 메모리에 둔다(gold_reader/metrics.py). 키는 release 빌드, gold.data_version 전체, 기간(from·to·cycle_offset)을 뺀 쿼리다. meta는 요청마다 새로 만든다. Gold는 표를 하나씩 다시 적재하므로, 비었거나 차원 행 없는 키가 보이거나 읽는 사이 data_version이 바뀐 결과는 답하되 두지 않는다. 복사본 재적재는 data_version을 바꾸지 않으므로 둔 값도 10분(HGH_FILTER_OPTIONS_CACHE_S, 0이면 끔)이 지나면 다시 읽는다.
  • 읽기 원천은 경로로 갈린다. analytics/conversion·analytics/visibility·analytics/properties(AI Conversion 국가 선택지 = 계정이 읽을 수 있는 GA4 속성, 2026-10-30) 세 경로만 HUB 데이터 DB로 가고, 나머지 /v1/*는 Gold로 간다. Gold는 active_release와 검증된 빌드에 고정해서 읽는다.
  • 읽기는 계정 범위 안에서만 한다(2026-10-29, bff/access.py). 화면과 /v1/* 읽기는 토큰의 계정으로 돌고, 관리자가 아닌 계정(HQ·권역·국가)은 두 곳에서 좁혀진다. 화면 빌더는 그 계정의 범위로 필터를 읽어 원래 화면처럼 브랜드를 잠그고 국가를 좁힌다. 모든 데이터 읽기(api.get과 /v1/* 경로, Gold와 HUB 데이터 DB 모두)는 쿼리의 brand를 범위 안 브랜드로, country를 범위 안 국가(권역이면 그 RHQ 국가 전부)로 바꾼 뒤 읽는다. 원래 API가 토큰으로 하던 일이고, 원래 프런트는 이 값을 쿼리에 넣지 않았다. HMG(전 브랜드)는 범위 계정의 브랜드가 아니다. 국가로 풀리지 않는 권역은 무제한이 아니라 거부다. 범위가 다른 계정은 같은 읽기 키를 쓰지 않으므로 Gold 읽기 캐시와 동시 읽기 공유도 계정 범위를 넘지 않는다. website·project 표면은 아직 이 역할들의 리뉴얼 화면이 없어 범위 계정에게 403으로 닫혀 있다.

BFF의 DB 연결 일곱 개

연결마다 계정이 다르고, 모두 statement_timeout 15초가 걸려 있다. Gold 연결이 없으면 API가 뜨지 않고, 나머지 여섯은 없으면 그 기능만 빠진다. 그래서 HUB 저장소 없이 Gold만으로도 화면 대부분이 돈다.

누가 어디에 쓰는가

  • 카탈로그는 덮어쓰지 않는다. 정의가 바뀔 때마다 *_version 행이 하나 늘고, 보관(archive)과 복원도 버전 하나다. origin=gold 프롬프트는 HUB에서 고쳐도 다음 sync가 Gold 정의로 다시 기록하므로 편집 화면에서 읽기 전용으로 보인다.
  • 두 HUB DB는 느슨하게 묶여 있다. 운영 DB는 project_reference에 같은 UUID만 둔다. 두 DB 사이에 FK도 공동 트랜잭션도 없어서, 데이터 DB 기록 뒤 운영 DB 등록이 실패하면 sync를 다시 돌려 맞춘다.
  • 외부 API는 ext.* 뷰로만 나간다. 호출자에게 허용한 프로젝트 가운데 projects·prompts 승인이 둘 다 있는 것과, 승인한 기준값 종류만 보인다. 범위는 DB가 강제한다(외부 API). published.*와 hmg_data_external은 DB 직접 공개용으로 그대로 두었고 외부에 열지 않았다.
  • 저장한 필터는 계정의 것이다. 리뉴얼 화면 필터 패널의 저장한 필터는 운영 DB system.saved_filter에 계정·화면마다 쌓여 어느 브라우저에서나 같다. BFF는 모든 문장을 로그인한 계정에 묶고, 한 계정의 쓰기는 advisory lock으로 차례대로 해서 순서와 기본 필터 하나를 지킨다. 쓰는 계정은 그 표 하나만 만질 수 있다. 예전 브라우저 저장(localStorage)은 첫 방문 때 한 번 계정으로 옮기고 지운다.
  • 계정은 최상위 관리자가 화면에서 만든다(2026-10-29, 리뉴얼 Admin › User management, hub_stores/accounts.py). 로그인 아이디(만든 뒤 바꿀 수 없음, 대소문자 없이 유일)·이름·메일·역할·범위를 정하고, 사용 중지·다시 사용, 비밀번호 재설정을 한다. 새 계정과 재설정은 임시 비밀번호를 한 번만 보여 주고 must_change를 켠다. 그 계정은 다음 로그인에서 새 비밀번호를 정하기 전에는 /v1/auth/me와 비밀번호 변경 말고는 아무것도 열지 못한다(403 password_change_required, 화면은 /login/password로 보낸다). 계정은 지우지 않는다. 자기보다 낮은 역할의 계정만 바꾸고 그런 역할만 준다. 그래서 관리자는 자기 계정과 다른 관리자 계정을 바꾸지 못하고(403 rank), 관리자 지정·해제는 서버의 manage.py set-admin·revoke-admin으로만 한다. 화면으로는 관리자를 잠글 수 없다. 바꿀 때마다 audit_event(account.*, details.user_id)가 남고 화면의 변경 이력이 된다. 쓰기는 advisory lock 617427416으로 하나씩.

로그인과 관문

middleware 관문 (로컬 모드)

  • localhost·127.0.0.1이 아닌 호스트는 403.
  • GET·HEAD·OPTIONS가 아닌 요청은 405. 예외는 /api/hub/* 하나이고, 거기서도 같은 출처인지 다시 본다.
  • 쿠키가 없으면 페이지는 /login?next=…로, /api/*는 401. /api/hub/session만 열려 있다.
  • middleware는 쿠키가 있는지만 본다. 토큰이 유효한지는 BFF가 판단한다.

로컬 모드가 켜지는 조건

HGH_LOCAL_READ_ONLY=1이고 VERCEL이 없을 때다. 실행 스크립트가 이 값과 HGH_API_BASE_URL=http://127.0.0.1:5555를 넣어 Next를 띄운다. 이 모드가 꺼지면 middleware와 API 클라이언트는 Supabase 로그인을 쓰는 기존 경로로 돌아간다.

첫 관리자 계정은 manage.py set-admin으로 만든다(다른 역할 계정에 쓰면 관리자로 바꾸고, 직접 정한 비밀번호라 변경을 묻지 않는다). 나머지 계정은 그 관리자가 화면에서 만든다. 역할은 관리자·HQ·권역·국가 넷이고, GEO 수행사·웹사이트 열람은 그 메뉴의 리뉴얼 화면이 생기면 더한다.

외부 API

외부 호출자에게 현재 저장된 프롬프트와, 그 수집·가공에 필요한 값을 읽기 전용으로 준다. 가공 결과(지표, 판정, 이전 회차 분석)와 회차·측정 작업 원장, GA4 속성, 답변·인용 원문은 주지 않는다. 별도 프로세스 back/ext/app.py(로컬 :5560)이고, 데이터 DB에 hmg_ext_api로만 접속한다. 운영 DB와 Gold에는 접속하지 않는다. 표 구조는 그림 6.

  • 범위는 DB가 강제한다. 요청마다 읽기 전용 트랜잭션에서 set_config('hgh.key_hash', sha256(키), true)를 먼저 실행한다. ext.* 뷰(소유 hmg_analytics_owner, security_barrier)는 그 해시의 유효한 키·활성 호출자에게 허용된 프로젝트 중 projects·prompts 승인이 있는 것과 승인된 기준값 종류만 보인다. 키가 없거나 틀리면 모든 뷰가 0행이다. hmg_ext_api는 catalog·publication·published를 직접 읽지 못한다.
  • 정의는 Gold 표현 그대로 저장하고 응답에서 푼다. surface 1/2/3과 브랜드 비트마스크는 HUB 코드표로 코드가 되고, 모르는 값은 {"code": null, "raw": n}으로 나간다. Gold 내부 키(scope_project_id·source_project_id·site_id)는 뷰에서 뺀다. 보관·삭제된 항목은 id·상태·순번만 나간다.
  • 변경 감지. 모든 버전 행·기준값 set·승인 변경은 같은 시퀀스 catalog.change_seq에서 순번을 받는다. 기록은 모두 advisory lock 617427413 안에서 하므로 순번 순서가 커밋 순서다. 소비자는 프로젝트마다 after_seq를 들고, 처음 보거나 다시 나타난 프로젝트, reset_seq가 기준점보다 큰 프로젝트는 0부터 다시 읽는다. meta.contract_version(계약 버전 + HUB 코드표 해시)이 바뀌면 전부 다시 읽는다. 기준값은 etag가 바뀐 종류만 다시 읽는다.
  • Gold 가져오기의 안전장치. Gold는 표마다 따로 커밋하며 통째로 다시 적재하므로, 한 번 읽은 것이 섞였는지 먼저 본다(데이터 버전 역행, 코드 없는 키, 빌드 행 수 불일치, 코드표로 풀리지 않는 값, 등록 URL과 짝이 없는 website 대상). 하나라도 걸리면 아무것도 기록하지 않고 catalog.sync_run에 거부 사유를 남긴다. Gold에서 사라진 Gold 출처 항목은 30분 이상 떨어진 두 번의 성공 실행이 모두 못 찾을 때만 removed가 된다. 한 번에 max(20, 1%)를 넘는 삭제나 5%를 넘는 새 버전은 --allow-removals N·--expect-mass-change 없이는 거부한다.
  • 호출 제한과 기록. 키별 분당 120회·동시 4개, 인증 실패는 주소별 분당 20회(넘으면 429와 Retry-After). GET만 받고 문서 경로(/docs·/openapi.json)와 CORS는 없다. 요청마다 한 줄 구조화 로그(요청 id·호출자 id·키 id·경로 템플릿·상태·시간)를 남기고 키 원문은 남기지 않는다.
  • 내부 VM 배치(taeho-dev, 2026-10-28). 컨테이너는 scripts/vm.sh가 만든다. 호출자는 https://10.0.20.132:8087/ext/로 들어온다. nginx hgh-ext-proxy가 VM의 자체 서명 인증서(IP SAN, 2029-01-30 만료)로 TLS를 끝내고, 10.0.0.0/8만 받아 GET /ext/만 넘긴다(infra/vm/ext-proxy/ext.conf). 포트가 8087인 까닭은 사무실과 VM 사이 망이 80xx 포트만 통과시키기 때문이다(8443·9443은 시간 초과). hgh-ext-api는 호스트 포트 없이 hgh-ext-network와 hgh-analytics-network에만 있고, X-Forwarded-For는 프록시 주소(172.30.0.10)에서 온 것만 믿는다. HUB 저장소는 Docker 방식 manage.py init의 hgh-analytics-db·hgh-operations-db(둘 다 127.0.0.1)다. Gold 가져오기는 cron이 매시 정각 vm.sh sync로 돌린다. 가져오기가 BFF 컨테이너 안에서 실행되므로 BFF(hgh-gold-api, 127.0.0.1:18091에만 열림)는 두 HUB 네트워크에 붙어 있다. 모든 화면이 HUB 로그인을 요구하므로 BFF는 Gold 외에 .env.analytics.local·.env.operations.local·.env.hub-edit.local(읽기 연결, 프롬프트 편집·저장한 필터·계정 관리 역할, 로그인 토큰 비밀)도 받는다. 하나라도 없으면 vm.sh bff가 멈추고, 두 HUB 연결이 healthz에서 ok여야 배치가 끝난다. 관리자 계정은 VM에서 manage.py set-admin으로 따로 등록한다. 매시 30분 vm.sh check-sync가 마지막 성공이 3시간을 넘었으면 .local/vm-cron.log에 WARN을 남긴다. 알림 채널은 아직 없다. BFF 이미지로 띄운 일회용 컨테이너가 호스트 네트워크에서 127.0.0.1의 데이터 DB와 인터넷의 GA4에 닿고, 비밀은 .env.analytics-ingest.local·.env.ga4.local env 파일로만 넘긴다. GA4 자격 증명을 인계받기 전이라 cron은 아직 등록하지 않았다.
