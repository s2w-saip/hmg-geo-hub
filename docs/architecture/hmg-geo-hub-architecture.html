GA4 · SEO 화면(AI Conversion · AI Visibility)은 HUB가 날마다 모으는 데이터라 기준 주와 따로 두고 칩 · 지연 안내도 보이지 않는다(2026-11-03, 사용자 결정). gold/*는 Global · Website 회차 달력도 읽지 않아 meta에 회차가 없다(2026-11-03, 리뷰 r2-4). 행에 남기는 Gold 발행본(gold_release)은 기록용이고 읽기를 거기에 고정하지 않으므로, Gold가 지난 주를 다시 발행하면 화면도 따른다. 화면 머리의 기준 주 칩, 끝난 지 10일이 넘으면 보이는 지연 안내, Gold가 발행하지 않았거나 관리자가 숨긴 사이트가 있는 주의 안내는 화면 shared/service-week(Gold 리더 cycles/week-notes)가 준다. 그 리더는 global · website 표면에서만 읽는다(project 표면은 422, 2026-11-03, 리뷰 r2-6). 주 안내는 그 주의 회차 날짜(days: 그 주에 보인 회차와 빠진 사이트의 회차) 가운데 하나가 화면 기간 안에 있을 때만 붙는다. 7일 프리셋처럼 그 주의 다른 날만 걸친 기간에는 붙지 않는다(2026-11-03, 리뷰 r2-10). 그 화면의 rounds는 표면마다 그 주에 회차가 있는지이고, 기간 없이 읽은 화면의 빈 결과는 회차가 없는 표면이면 필터 안내 대신 ‘측정 없음’과 그 주 이름을 보인다(2026-11-03, 리뷰 r1-19). 그 값은 cycles/week-notes가 같이 읽는 Gold 회차 달력이다: Context.create가 회차를 고르는 조건 그대로, 읽기가 고르는 발행본(live · card · grid) 가운데 하나라도 그 주 회차를 가지면 있다. 안내를 못 읽으면 모른다(null). HUB 작업이 기록한 완료 회차(global_cycles · website_cycles)는 쓰지 않는다. 기준 주를 붙잡은 동안 Gold가 그 주 회차를 다시 열어도 기록은 그대로이기 때문이다(2026-11-03, 리뷰 r4-2). 시작이 기준 주 뒤인 기간(위: 아무것도 고르지 않는다)의 빈 결과도 필터 안내나 0 대신 ‘아직 보이지 않는 기간’과 그 주 이름을 보인다(2026-11-03, 리뷰 r3-12). 원본 (dash) 화면은 빈 결과를 원래 빈 문구나 0으로 그리므로(Website 언급 · 인용), 그때 main 맨 위 지연 안내 아래에 같은 줄을 보인다(2026-11-03, 리뷰 r2-12). 기간 없이 모든 회차를 읽는 프롬프트 화면(Global · Website)에는 보이지 않는다(2026-11-03, 리뷰 r3-11). 그 사이트는 그 화면이 읽는 사이트다: 리뉴얼 셸이 Website 화면 URL의 국가(geography) · 언어(language) · 엔진(engine)과 관리자의 브랜드(brand)를 넘기면 화면들과 같은 규칙으로 읽고, 레이아웃의 첫 읽기(고른 값 없음)는 고른 값이 없는 화면에만 쓴다(2026-11-03). 화면 읽기가 사이트의 셀을 고르는 축 그대로다: 기준 주 마지막 날까지 그 사이트의 job(Gold job_index, 어느 회차든) 하나가 고른 국가(프롬프트가 측정된 국가 — 사이트 SA-Dammam인 Genesis 사우디는 Jeddah · Riyadh에서 측정된다) · 언어 · 엔진에 모두 맞으면 그 화면의 사이트이고, job이 아직 없는 사이트는 자기 국가로 고른다(2026-11-03, 리뷰 r5-1).
  • 읽기는 계정 범위 안에서만 한다(2026-10-29, data_server/access.py). 화면과 /v1/* 읽기는 토큰의 계정으로 돌고, 관리자가 아닌 계정(HQ·권역·국가)은 두 곳에서 좁혀진다. 화면 빌더는 그 계정의 범위로 필터를 읽어 원래 화면처럼 브랜드를 잠그고 국가를 좁힌다. 모든 데이터 읽기(api.get과 /v1/* 경로, gold와 GA4 · SEO 모두)는 쿼리의 brand를 범위 안 브랜드로, country를 범위 안 국가(권역이면 그 RHQ 국가 전부)로 바꾼 뒤 읽는다. 원래 API가 토큰으로 하던 일이고, 원래 프런트는 이 값을 쿼리에 넣지 않았다. HMG(전 브랜드)는 범위 계정의 브랜드가 아니다. 국가로 풀리지 않는 권역은 무제한이 아니라 거부다. 범위가 다른 계정은 같은 읽기 키를 쓰지 않으므로 사전 집계 · 캐시 DB와 동시 읽기 공유도 계정 범위를 넘지 않는다. website 표면도 global과 같은 범위로 읽는다(2026-10-31, 리뉴얼 점검 후속 2단계 · ⛔J). 국가는 사이트 국가다. 국가 계정은 자국 사이트, 권역 계정은 권역 국가의 사이트를 읽는다. HQ 계정은 자기 브랜드의 모든 사이트를 읽는다. 브랜드 통합 보기는 관리자만 한다. 국가가 있는 범위는 그 나라의 도시 사이트(SA → SA-Dammam · SA-Jeddah · SA-Riyadh)도 읽는다. 권역 허브 사이트(worldwide · EU · MIDDLEEAST · CPO · CN-BJ)는 국가가 없는 계정만 읽는다. 필터 패널의 국가 · 언어 선택지도 이 범위로 좁힌다(global · website). Gold 선택지 읽기는 국가 축으로 좁히지 않아서 데이터 서버가 범위 밖 국가의 행을 뺀다. Global 프롬프트 카탈로그 읽기(prompts)는 그 국가를 원래 API의 대상 시장 규칙(B1)으로 건다(2026-10-31, 리뉴얼 점검 후속 13단계). 대상 시장이 비었거나, 실국가가 없거나(x:만), 범위 국가를 담은 프롬프트만 읽는다. 브랜드는 범위 브랜드와 공통(HMG)이다. Global 인용의 자사 판정도 그 국가로 좁혀진다(2026-10-31, 9dbd27d). 리더 gold_reader/citations.py owned_bases는 Gold dim_owned_base 설명대로 관점 브랜드의 자사 베이스를 요청 국가의 geo_code → 요청 언어로 좁히고(좁힌 결과가 비면 그 단계는 건너뜀), 범위 계정의 요청 국가는 위에서 바꾼 범위 국가다. project 표면은 범위 계정에게 403으로 닫혀 있다. 프로젝트 목록 · 프롬프트(gold/projects, surface 인자 없이 읽는다)도 project 표면으로 보고 닫는다(2026-11-03, F20). 리뉴얼 Project 목록과 프로젝트 탭(/renewal/projects/{id}/…, 메뉴 D안: 프로젝트는 자기 브라우저 탭에서 열리고 그 탭의 사이드바는 그 프로젝트의 메뉴뿐)도 관리자만 연다(route-policy /renewal/projects). 목록은 데이터 서버 화면 projects/list가 Gold surface 3에서 측정 국가 · 언어 · 엔진 · 회차 · 커스텀 태그 수 · 첫 프롬프트를 더해 준다(Gold에는 프로젝트 이름 · 브랜드 · 국가가 없다). 프로젝트 탭의 화면은 screens/project_dashboard.py의 projects/filters(필터 패널: 기간 · 측정 국가 · AI 엔진 · 커스텀 태그 cf_<fieldId>, 국가가 하나면 잠금)와 Dashboard의 projects/as-of · dash-*(KPI · 엔진 · 출처 · 추이 · 현황)를 읽는다. project 읽기는 live뿐이라 서비스 기준 주 · 기간 비교를 걸지 않고, 당사는 Gold 관점 기본값 HMG다(2026-11-03, P2). 연결마다 계정이 다르고, 모두 statement_timeout 15초가 걸려 있다. Gold 연결이 없으면 API가 뜨지 않고, 나머지는 없으면 그 기능만 빠진다. 그래서 서비스 저장소 없이 Gold만으로도 화면 대부분이 돈다. 입력 DB 조회 연결은 Global · Website Gold 읽기의 상한인 서비스 기준 주(catalog.current_service_week, hub_stores/service_week.py)도 읽는다. 이 연결을 두지 않으면 상한도 빠져 Gold 최신 회차까지 읽는다(화면 칩 ‘기준 주 미정’). 두었는데 기준 주를 아직 한 번도 읽지 못했으면 상한 없이 읽는 대신 그 읽기가 503이다. 기준 주는 처음 한 번만 기다려 읽고(2초까지), 그 뒤에는 들고 있는 값을 바로 쓰면서 60초(HGH_SERVICE_WEEK_CACHE_S)마다 뒤에서 다시 읽는다. 다시 읽기가 실패하면 마지막 주를 그대로 쓴다. 셸의 기준 주 읽기(shared/service-week)만은 Gold 연결을 잡기 전이라 답하기 전에 매번 다시 읽는다(2초까지, 실패한 뒤 5초 동안은 들고 있는 값). 스냅샷 ID는 기준 주를 기다리지 않고 들고 있는 값만 쓴다. 그래서 회차를 읽지 않는 읽기(project 표면 · gold/*)는 입력 DB를 기다리지 않는다(2026-11-03, 리뷰 r2-5). 그래서 기준 주가 바뀌는 순간 열린 화면은 셸의 기준 주 읽기와 본문의 화면 읽기가 서로 다른 주일 수 있다. 셸은 레이아웃이 읽은 주를 한 번 더 읽어 끝이 다르면 본문을 다시 읽고, 데이터 서버가 그 주로 바뀐 지 5초 안이면(shared/service-week의 justMoved) 본문을 한 번 다시 읽는다(2026-11-03, 리뷰 r1-16). 페이지를 옮길 때 셸의 다시 읽기는 새 페이지를 그리는 중에 나가 본문의 화면 읽기보다 먼저 데이터 서버에 닿을 수 있는데, 셸의 읽기가 기준 주를 다시 읽고 답하므로 그 뒤의 화면 읽기는 셸이 받은 주를 받는다(그 사이에 작업이 다음 주를 기록한 때만 빼고, 2026-11-03, 리뷰 r5-2). 기준 주를 쓰는 hmg_service_week_writer는 카탈로그 · 운영 쓰기 계정처럼 manage.py가 실행 중에만 쓰는 계정이라 데이터 서버 연결이 아니다(그림 2).

누가 어디에 쓰는가

  • 카탈로그는 덮어쓰지 않는다. 정의가 바뀔 때마다 *_version 행이 하나 늘고, 보관(archive)과 복원도 버전 하나다. origin=gold 프롬프트는 HUB에서 고쳐도 다음 sync가 Gold 정의로 다시 기록하므로 편집 화면에서 읽기 전용으로 보인다.
  • 두 서비스 DB는 느슨하게 묶여 있다. 운영 DB는 project_reference에 같은 UUID만 둔다. 두 DB 사이에 FK도 공동 트랜잭션도 없어서, 입력 DB 기록 뒤 운영 DB 등록이 실패하면 sync를 다시 돌려 맞춘다.
  • 외부 API는 ext.* 뷰로만 나간다. 호출자에게 허용한 프로젝트 가운데 projects·prompts 승인이 둘 다 있는 것과, 승인한 기준값 종류만 보인다. 범위는 DB가 강제한다(외부 API).
  • 저장한 필터는 계정의 것이다. 리뉴얼 화면 필터 패널의 저장한 필터는 운영 DB system.saved_filter에 계정·화면마다 쌓여 어느 브라우저에서나 같다. 데이터 서버는 모든 문장을 로그인한 계정에 묶고, 한 계정의 쓰기는 advisory lock으로 차례대로 해서 순서와 기본 필터 하나를 지킨다. 쓰는 계정은 그 표 하나만 만질 수 있다. 예전 브라우저 저장(localStorage)은 첫 방문 때 한 번 계정으로 옮기고 지운다.
  • 계정은 최상위 관리자가 화면에서 만든다(2026-10-29, 리뉴얼 Admin › User management, hub_server/accounts.py). 로그인 아이디(만든 뒤 바꿀 수 없음, 대소문자 없이 유일)·이름·메일·역할·범위를 정하고, 사용 중지·다시 사용, 비밀번호 재설정을 한다. 새 계정과 재설정은 임시 비밀번호를 한 번만 보여 주고 must_change를 켠다. 그 계정은 다음 로그인에서 새 비밀번호를 정하기 전에는 /v1/auth/me와 비밀번호 변경 말고는 아무것도 열지 못한다(403 password_change_required, 화면은 /login/password로 보낸다). 계정은 지우지 않는다. 자기보다 낮은 역할의 계정만 바꾸고 그런 역할만 준다. 그래서 관리자는 자기 계정과 다른 관리자 계정을 바꾸지 못하고(403 rank), 관리자 지정·해제는 서버의 manage.py set-admin·revoke-admin으로만 한다. 화면으로는 관리자를 잠글 수 없다. 바꿀 때마다 audit_event(account.*, details.user_id)가 남고 화면의 변경 이력이 된다. 쓰기는 advisory lock 617427416으로 하나씩.

로그인과 관문

middleware 관문 (로컬 모드)

  • localhost·127.0.0.1이 아닌 호스트는 403.
  • GET·HEAD·OPTIONS가 아닌 요청은 405. 예외는 /api/hub/* 하나이고, 거기서도 같은 출처인지 다시 본다.
  • 쿠키가 없으면 페이지는 /login?next=…로, /api/*는 401. /api/hub/session만 열려 있다.
  • middleware는 쿠키가 있는지만 본다. 토큰이 유효한지는 데이터 서버가 판단한다.

로컬 모드가 켜지는 조건

HGH_LOCAL_READ_ONLY=1이고 VERCEL이 없을 때다. 실행 스크립트가 이 값과 HGH_API_BASE_URL=http://127.0.0.1:5555를 넣어 Next를 띄운다. 이 모드가 꺼지면 middleware와 API 클라이언트는 Supabase 로그인을 쓰는 기존 경로로 돌아간다.

첫 관리자 계정은 manage.py set-admin으로 만든다(다른 역할 계정에 쓰면 관리자로 바꾸고, 직접 정한 비밀번호라 변경을 묻지 않는다). 나머지 계정은 그 관리자가 화면에서 만든다. 역할은 관리자·HQ·권역·국가 넷이고, GEO 수행사·웹사이트 열람은 그 메뉴의 리뉴얼 화면이 생기면 더한다.

외부 API (프롬프트·기준정보 API)

수집(앤써)과 분석이 프롬프트 · 측정 설정 · 기준정보를 읽기 전용으로 읽는 API다(SSOT service/prompt-reference-api.md). 지표, 판정, 회차 · 측정 작업 원장, GA4 속성, 답변 · 인용 원문은 주지 않는다. 별도 프로세스 back/ext/app.py(로컬 :5560)이고, 입력 DB에 hmg_ext_api로만 접속한다. 운영 DB · Gold DB · 캐시 DB에는 접속하지 않는다. 표 구조는 그림 6. 호출자는 수집(collect) 또는 분석(analyze)이다. 수집은 허용된 프로젝트와 측정 설정 · 프롬프트 · 수집 기준정보 5종을, 분석은 분석 기준정보 10종을 읽는다. 명세는 GET /ext/openapi.json과 docs/ssot-staging/service/openapi.json(cd back && python -m ext.export_openapi, 코드와 다르면 테스트가 실패한다).
