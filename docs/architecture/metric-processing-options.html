지표 가공 위치 비교

지금처럼 분석팀과 파이프라인이 지표까지 계산할까(현행), 분석팀은 추출만 하고 BFF가 지표를 계산할까(안 B)

초안 · 2026-11-05 · 결정 전 · 읽는 사람: 개발팀 전체 · 안 B는 지금 구현된 코드와 규칙에 얽매이지 않고 설계했고, 근거로는 서비스 중인 데이터 양을 썼다.

그림 읽는 법 데이터가 흐름 지표 변경 요청이 다른 팀으로 감 지표 변경이 같은 담당 안에서 끝남 안마다 달라지는 칸 데이터 파이프라인 영역 Bronze DB · 수집한 그대로 Silver DB · 추출 사실 Gold DB · 지표 · 롤업 다른 팀이 읽는 DB (팀 사이 계약) 같은 팀만 읽는 DB

그림 1 — 현행: 분석팀이 OBT Table에 바로 넣고, 파이프라인이 가공

그림 2 — 안 B: BFF가 가공한다

권고: 안 B. 분석팀은 추출만 하고, 가공(지표 계산)은 BFF가 맡는다.

현행은 지표를 쓰는 쪽(서비스)과 계산하는 쪽(파이프라인)이 달라, 지표 하나를 바꿀 때 팀 사이를 오간다. OBT가 프롬프트 1행이라 답변 단위로 새로 세려면 분석팀까지 움직인다. B에서는 지표를 쓰는 쪽(서비스)이 지표를 정의하고 계산하므로 팀 사이를 오가지 않고, 분석팀은 AI 추출 품질에 집중한다. 성능은 1~4회차 읽기를 요청 때 집계해도 1초 안팎이라 버티고, 무거운 계열만 롤업한다. 단, 5절의 조건 다섯 개를 함께 정해야 한다.

서비스 딜리버리

층마다 저장소는 하나다. 파이프라인이 Silver 저장소에 쓰는 유일한 주체이고, 서비스는 공개된 세대만 읽는다. '임시 저장'은 따로 둔 저장소가 아니라 아직 공개하지 않은 세대이고, '딜리버리'는 데이터를 옮기는 일이 아니라 검사를 통과한 세대를 공개로 바꾸는 일이다. 같은 데이터를 두 곳에 두지 않으므로 어느 쪽이 정본인지, 둘을 어떻게 맞출지 정할 일이 없다.

동작 (회차마다)

  1. 파이프라인이 분석 산출물을 새 세대로 적재한다(loading). 이전 공개 세대는 그대로 보인다.
  2. 행 수 · 필수 열 · 키 중복을 검사하고, 통과하면 ready로 바꾸고 매니페스트에 적는다.
  3. 한 트랜잭션으로 공개 포인터를 새 세대로 바꾼다(public). 이것이 딜리버리다. 이전 세대는 retired가 된다.
  4. 서비스는 매니페스트에서 새 공개 세대를 보고(완료 신호) 롤업을 갱신하고 캐시를 비운다.
  5. 롤업의 세대가 공개 세대와 다르면(롤업 실패 · 지연) BFF는 요청 때 Silver에서 계산한다. 느려도 틀리지 않는다.
  6. 되돌릴 때는 포인터를 retired 세대로 돌린다. 오래된 세대는 정리한다.

답변 1건당 언급 브랜드 · 인용 수(3.2 · 11.5)와 최근 답변 수로 셌다. 한 번에 수만 행(그 안의 항목은 100만 개 미만)이라 적재 · 검사는 몇 초 수준으로 본다. 이 적재가 서비스가 읽는 저장소에 걸리는 것이 이 구성이 감수하는 점이다.

뺀 방식

  • 임시 저장 + 서비스 쪽 사본(복사): 같은 Silver가 두 곳에 생겨 정본 · 동기화 · 보존 규칙이 둘이 된다.
  • 파이프라인 전용 저장소를 서비스가 색인 권한 없이 읽음: 색인을 바꿀 때마다 파이프라인에 요청해야 한다.
  • 서비스가 당겨 감: 적재기가 서비스 담당 한 명의 일로 늘어난다.

책임. 세대가 다 왔는지는 파이프라인, 내용이 맞는지는 분석, 지표는 서비스가 진다. 숫자가 틀리면 매니페스트와 롤업에 남은 세대 · 정의 버전으로 어느 단계 문제인지 가린다.

확인하지 못한 것: Silver 저장소를 어느 DB에 두고 누가 운영할지, 서비스에 색인 권한을 줄 수 있는지, 파이프라인 팀이 '임시 저장'을 별도 저장소로 생각하고 있는지.

3. 기준별 비교

현행은 지금 모습 그대로, 안 B는 아래 4절의 계산 방식으로 비교한다.

기준현행 · 파이프라인 가공안 B · BFF 가공우세
개발 효율성
  • + BFF는 읽기만 하므로 단순하다.
  • − 새 지표 · 필터 축 · 분모 조건이 바뀌면 서비스가 파이프라인에 요청하고, 파이프라인이 가공을 고쳐 다시 계산한 뒤에야 화면에 반영된다(그림 1의 빨간 점선).
  • − 파이프라인이 데이터 이동 · 저장에 더해 지표 규칙까지 맡아, 지표 요구가 몰리면 파이프라인 일이 밀린다.
  • − OBT가 프롬프트 1행이라, 답변 단위로 새로 세려면 분석팀이 OBT의 열을 바꿔야 한다.
  • + 화면 요구와 지표 계산을 같은 담당이 고쳐 한 번에 끝난다(그림 2의 초록 점선).
  • + 분석팀은 추출 품질(모델 · 프롬프트 · 분류)에 집중한다.
  • − 서비스 담당 한 명의 일이 늘어난다.
  • − 추출 사실의 열 · 뜻이 바뀌면 BFF도 함께 고쳐야 한다.
 B
책임 · 소유
  • + 지표가 미리 계산돼 있어 서비스는 값을 그대로 보인다.
  • − 숫자가 틀리면 추출(분석팀) 문제인지 가공(파이프라인) 문제인지 두 팀 사이에서 가려야 한다.
  • − 지표가 어떻게 쓰이는지 아는 쪽(화면)과 지표를 정의하는 쪽이 달라 해석 차이가 생기기 쉽다.
  • + 경계가 '사실과 규칙'으로 분명하다. 추출이 맞는지는 분석팀이, 세는 규칙은 서비스가 책임진다.
  • + 각 팀의 전문성(AI 모델 / 서비스 · 쿼리)과 맡은 일이 맞는다.
  • − 숫자가 틀리면 추출 문제인지 가공 문제인지를 두 팀 사이에서 가려야 한다. 추출 사실 검수 기준이 필요하다.
 B
정확성 · 일관성
  • + 회차를 마감할 때 한 번 계산해 저장하므로, 모든 소비자가 같은 값을 본다.
  • − 지표 셀에 없는 조합을 BFF가 따로 계산하기 시작하면 정의가 두 곳으로 갈라진다.
  • + 지표 정의가 BFF 한 곳에 모인다. 화면과 외부 API가 모두 BFF를 거친다.
  • − 요청 때 계산하므로, 추출 사실이 다시 분석되면 값이 바로 바뀐다. 세대 번호를 고정하는 계약이 꼭 있어야 한다.
  • − BFF를 거치지 않고 추출 사실을 직접 세는 소비자가 생기면 값이 갈라진다.

성능 · 비용
  • + 미리 계산해 두므로 화면이 빠르다.
  • − 모든 조합을 미리 계산해, 지표 셀이 답변 단위 사실의 약 4.2배(5,420만 행)이고 회차마다 다시 만든다.
  • + 1~4회차 읽기는 요청 때 집계해도 1초 안팎이다(4절 측정). 저장은 추출 사실과 작은 롤업뿐이다.

5. 권고와 조건

안 B를 권고한다. 성능은 현행이 더 빠르지만 B도 1~4회차 읽기가 1초 안팎이라 버티고, 저장 · 재계산 비용은 B가 작다. 개발 효율성과 책임에서 B가 낫다. B의 약점은 넓어진 계약, 값의 고정, 한 명에게 쏠리는 일이고, 아래 조건으로 막는다.

  1. 추출 계약을 문서로 고정한다. 추출 사실 OBT Table의 열 · 뜻 · 세대 번호를 적고, 바꿀 때는 미리 알린다. 분석팀과 서비스가 함께 갖는다.
  2. 지표는 BFF로만 내보낸다. 외부 API와 다른 소비자도 BFF를 거친다. 추출 사실을 직접 세어 지표를 내는 곳을 두지 않는다.
  3. 세대를 고정한다. BFF는 공개된 세대의 추출 사실만 읽는다. 다시 분석한 결과는 새 세대로 들어오고, 공개 전환 때만 화면 값이 바뀐다.
  4. 지표 정의를 코드와 시험으로 남긴다. 정의 변경은 분석팀도 리뷰해 한 사람에게만 기대지 않게 한다.
  5. 롤업은 서비스가 갖고 돌린다. 파이프라인이 새 세대를 공개하면(매니페스트) 그것을 신호로 갱신하고, 실패하거나 늦으면 BFF가 요청 때 계산한다.

현행을 유지하는 편이 나은 경우

  • 지표 정의가 거의 바뀌지 않을 때
  • BFF 말고도 지표를 직접 읽는 소비자가 많을 때
  • 서비스 쪽 인력을 늘리거나 나눌 수 없을 때

확인하지 못한 것

  • 동시 사용자가 많을 때의 집계 시간
  • website · project 질의 시간 (global만 쟀다)
  • 서비스 담당의 실제 여력과 분석팀의 의견
  • Silver 저장소를 어느 DB에 두고 누가 운영하는지, 서비스에 색인 권한을 줄 수 있는지
  • 현행 그림: 지금 Gold DB에는 지표 셀 말고도 답변 1건 = 1행인 사실 표(answer_fact 74만 행, answer_brand_fact · citation_fact)가 있고 BFF가 이것도 읽는다(BFF 코드에서 확인). Silver가 프롬프트 단위라면 이 표를 어느 단계에서 누가 만드는지
