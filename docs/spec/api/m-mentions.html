언급

FastAPI APIRouter(prefix="/v1/mentions", tags=["mentions"]) 1개. 파일 구성: app/modules/mentions/router.py(엔드포인트 3개: GET /brands, GET /types, GET /prompts), schemas.py(공유·단위별 Pydantic v2 모델), repo.py(SQLAlchemy 2 Core 텍스트 SQL, 공통 WHERE 빌더와 3개 단위 쿼리, 다른 모듈에 내보내는 brand_rows 함수), service.py(관점 브랜드 → 열 선택, 비율 조립, 커서 인코딩). 모든 핸들러는 Depends(get_principal)(auth 모듈: Supabase JWT JWKS 검증) → Depends(resolve_read_context)(filters 모듈: 공통 필터 모델 + 권한 교집합 + 회차 창 + 카탈로그 prompt_key 해석) 두 의존성을 거쳐 ResolvedContext 하나만 받는다. DB 롤은 api_ro(statement_timeout 5s, plan_cache_mode=force_custom_plan: DB-v2-roles.sql:40-42), asyncpg + PgBouncer transaction 모드(prepared statement 캐시 끔). 한 요청 안의 독립 문장(M-1 의 분모 문장과 브랜드 행 문장, M-2 의 유형 문장과 스탠스 문장)은 asyncio.gather 로 커넥션 2개에 병렬 실행.

언급 모듈은 GET /v1/mentions/brands(M-1), /types(M-2), /prompts(M-3) 3개 엔드포인트다. 단위 설계를 대조한 결과, 공통 필터를 적용하는 방식에서 계약 위반과 회귀가 여럿 나왔다. (1) brand[] 를 표시 브랜드 필터로 오해했다(M-1·M-2). 실제로는 카탈로그 모수 필터(bgrp)다. (2) 당사 판정을 관점과 무관하게 own_bit=0/>0/=1 로 적었다. 이러면 Kia 관점에서 Hyundai 가 경쟁 행에서 빠지는 회귀가 난다(현행 trackedRollupIn scope-aggregates.ts:195 = 관점 ∩ 3사). M-2 는 WHERE 에 비트 등식 bgrp=:own_brand 까지 썼다. (3) 세 단위 모두 회차 게이트(R03 view_date, hidden_scope), 엔진 미지정 = dflt, 스냅샷(A1) 처리를 빠뜨렸다. (4) M-3 은 catalog_entry 를 LEFT JOIN 해 언급 합이 부풀려지는 버그가 있다. (5) M-2 는 답변 수를 행 수로 세어 과대 집계한다. (6) M-1 은 include_trend 가 /v1/trend 와 중복된다. (7) M-1 의 own 감성 형태는 rd.answer 로는 낼 수 없다(neutral·mixed 없음). 해소안으로 관점 비트 목록 vp 와 공통 WHERE 빌더 하나를 세 단위가 공유하게 한다. 당사 = own_bit = ANY(:vp), 경쟁 = competitive AND NOT 당사로 통일한다. 브랜드 행 리더(brand_rows)는 Overview 경쟁사 줄과 값이 같아야 하므로(server.ts:3813 제품 결정) KPI·trend 모듈에 내보낸다. DDL 에 없는 이름은 M-1 의 rd.dim_project→bgrp 하나다. 제안 인덱스 1개와 조건부 제안 컬럼 1묶음은 D8 저촉이 없고, RDS 실측 게이트 뒤에 판단한다. 위험은 셋 모두 medium 이고, 1년 누적과 화면당 동시 호출에서 high 로 오를 수 있다.

쿼리 설계
읽기 스키마(rd)만, 조인 없이 파티션 가지치기로 두 갈래를 병렬 실행.

1) 당사 행(rd.answer, G-03 판정 열만):
```sql
SELECT count(*) FILTER (WHERE std_in) AS answers_total,
       sum(ment_total) FILTER (WHERE std_in) AS mentions_total,
       count(*) FILTER (WHERE std_in AND own_mask <> 0) AS own_exposure,
       sum(ment_h) FILTER (WHERE std_in) AS own_mentions,      -- h/k/g 중 own_brand 에 맞는 열을 서버가 선택
       sum(own_rk_h) FILTER (WHERE std_in AND own_rk_h > 0) AS own_rank_sum,
       count(*) FILTER (WHERE std_in AND own_rk_h > 0) AS own_ranked_answers,
       sum(sent_pos_h) FILTER (WHERE std_in) AS own_pos, sum(sent_neg_h) FILTER (WHERE std_in) AS own_neg,
       sum(sent_all_h) FILTER (WHERE std_in) AS own_scored
FROM rd.answer
WHERE surface = :surface AND round_date BETWEEN :from AND :to
  AND project_key = ANY(:project_keys) AND engine_key = ANY(:engine_keys)
  AND geo_key = ANY(:geo_keys) AND lang_key = ANY(:lang_keys)
  AND (:catalog_filtered = false OR prompt_key IN (SELECT prompt_key FROM rd.catalog_entry WHERE ...funnel/presence/list_type/depth...));
```

2) 경쟁사 행(rd.answer_brand, competitive=true, own_bit=0):
```sql
SELECT brand_key,
       count(DISTINCT answer_key) AS exposure_answers,
       sum(mention_count) AS mentions,
       sum(rk) FILTER (WHERE rk > 0) AS rank_sum,
       count(*) FILTER (WHERE rk > 0) AS ranked_rows,
       sum(s_pos) AS s_pos, sum(s_neu) AS s_neu, sum(s_neg) AS s_neg, sum(s_mix) AS s_mix
FROM rd.answer_brand
WHERE surface = :surface AND round_date BETWEEN :from AND :to AND std_in
  AND competitive AND own_bit = 0
  AND project_key = ANY(:project_keys) AND engine_key = ANY(:engine_keys)
  AND geo_key = ANY(:geo_keys) AND lang_key = ANY(:lang_keys)
  AND (:brand_filter IS NULL OR brand_key = ANY(:brand_filter))
  AND (:catalog_filtered = false OR prompt_key IN (SELECT prompt_key FROM rd.catalog_entry WHERE ...))
GROUP BY brand_key
ORDER BY :sort_column DESC
LIMIT :top_n;
```
brand_key → rd.dim_brand_name.name 은 점 조회(수십 행, 캐시 가능 차원)로 해석. exposure_rate = exposure_answers/answers_total(공유 분모), share = mentions/mentions_total. avg_rank = rank_sum/ranked_rows(조회 시 계산, P1 예외).

3) include_trend=true 면 위 두 쿼리를 round_date 를 주 단위로 GROUP BY 해 반복(같은 WHERE, GROUP BY brand_key, date_trunc('week', round_date) 또는 rd.cycle.view_date 기준 버킷 — 버킷 키 산식은 계약 §2 공용 규약을 따름), trend_weeks 로 기간 상한.
