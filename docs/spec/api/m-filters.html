필터

APIRouter(prefix="/v1/filters", tags=["filters"]) 하나에 GET /options(F-1)·GET /dates(F-2) 두 경로. 파일 구성(제안): modules/filters/router.py(경로·의존성 주입), modules/filters/schemas.py(Pydantic 입출력), modules/filters/repo.py(SQLAlchemy Core text SQL, 읽기 전용 커넥션), modules/filters/presets.py(presetRange 순수함수 이식). 공통 의존성은 core 패키지(core.auth.get_principal, core.scope.get_scope, core.filters.CommonFilterQuery, core.meta.build_meta, core.window.resolve_window)에서 주입받고, filters 모듈은 core.window 의 최초 소비자로서 그 구현을 소유한다. 계약서 §8 초안의 단일 경로 GET /v1/filters?surface= 와 다르다(consistency_fixes 1번, 통합자가 명세 §8 갱신).

필터 모듈은 F-2(선택 가능 날짜, GET /v1/filters/dates, low)와 F-1(옵션 매트릭스, GET /v1/filters/options, 스냅샷 low·기간 medium·1년 high)을 한 라우터로 묶는다. 핵심 해소는 여섯이다. (1) 창 해석을 공유 함수 resolve_window 하나로 통일한다. F-1 이 쓰던 "표면별 ORDER BY LIMIT 1" 스냅샷을 버리고, 현행 pickWebsiteCycles(summary-cycles.ts:207)의 함대 규칙(허용 프로젝트들의 최신 노출 round_date 하나, 그 날 회차가 없는 프로젝트는 결손)과 F-2 latest_round_date 를 같은 값으로 만든다. (2) F-1 이 빠뜨린 R04 숨김 게이트를 넣는다. 옵션은 현행 OPTION_HIDDEN_FAMILY='mentions'(scope-aggregates.ts:2038, 가장 느슨한 계열로 옵션 ⊇ 데이터)의 취지를 이어 hidden_scope=1(all)만 뺀다. 달력은 family 별 배제(mentions {1,3}·citations {1,2}·all {1,2,3})로 둔다. (3) F-1 사실 표 질의에 round_date 범위가 없어 파티션 가지치기가 안 되고, WHERE 안에 비트 식(cat_mask & mask)과 CROSS JOIN LATERAL 전개가 있어 계약서 §3 술어 규약을 어긴다. 창 해석 결과(cyc_key 배열·round_date 범위)를 상수로 넘기고, (geo_key, lang_key, cat_mask) GROUP BY 뒤 바깥 소집합에서 비트를 전개하도록 고친다. (4) 스코프 계산은 effectiveScopeCountries(lib/rhq/index.ts:87)의 우선순위(countries 가 있으면 그것만, 없으면 regions 확장)를 따른다. F-1 의 "국가 비면 403" 규칙은 국가 제한이 없는 브랜드 스코프 고객을 막으므로 폐기한다. (5) 응답 형태를 맞춘다. 내부 정수 키(brand_bit·region_key·geo_key)를 노출하지 않고 코드로 내며, meta.suppressed 는 명세 §8 대로 객체 {} 로 통일한다. (6) 빈틈 셋을 메운다. 프로젝트 표면 택소노미는 rd.catalog_entry(루트 전용)가 아니라 app.prompt 에서 읽고(현행 listCatalogTaxonomy(id), standards.ts:394), 웹사이트 브랜드 가상 지오(website-virtual-geo.ts:57)를 매트릭스에 싣고, 프로젝트 커스텀 필드 옵션을 추가한다. DB-v2 에 없는 이름을 확정처럼 쓴 단위는 없다(대조 결과 0건). 새 컬럼·인덱스 제안도 없다.

성능(10배)
rd.cycle은 답변 그레인이 아니라 회차 그레인 — surface=global: project_keys 보통 단원(루트) → cycle_project_idx로 수백 행. surface=website: 스코프 내 사이트(project_key) 수 × 회차 수, 10배 폭에서도 수만 행 이하로 추정(회차 주기가 3일~1주이고 역사 길이가 폭과 무관, §3 성능 근거 한계 문단과 일치 — '이력 10배'가 아니라 '폭 10배' 전제이므로 사이트 수는 늘어도 회차 캐던스는 불변). surface=project: 단일 project_key → 매우 작음.
인덱스: cycle_pick_idx (surface, round_date DESC) INCLUDE (cyc_key, project_key, servable, view_date, hidden_scope, generation), cycle_project_idx (project_key, round_date DESC)
cycle_pick_idx는 (surface, round_date DESC)에 필요한 열을 전부 INCLUDE해 Index Only Scan 가능(project_key/hidden_scope/servable/view_date 필터는 인덱스 안에서 Filter로 처리, 힙 접근 없음). project_keys 배열이 작을 때(전형: 루트 1건, 웹사이트 수십 건)는 플래너가 cycle_project_idx로 각 project_key를 개별 스캔해 병합할 수도 있음 — 둘 다 저비용. 쿼리 설계
입력(상위 인가 계층이 미리 계산): :surface(int2), :project_keys(int4[] — global/website는 서버가 계산한 스코프 내 project_key 목록, project는 project_id→rd.dim_project.project_key 단일 해소), :excluded_hidden(int2[] — family로 결정), :limit.

WITH picked AS (
  SELECT DISTINCT round_date
  FROM rd.cycle
  WHERE surface = :surface
    AND project_key = ANY(:project_keys)
    AND servable
    AND view_date IS NOT NULL AND view_date <= rd.today_kst()
    AND hidden_scope <> ALL(:excluded_hidden)
),
agg AS (SELECT min(round_date) AS first_round, max(round_date) AS latest_round, count(*) AS n FROM picked)
SELECT p.round_date, a.first_round, a.latest_round, a.n
FROM picked p CROSS JOIN agg a
ORDER BY p.round_date DESC
LIMIT :limit;
