적재 파이프라인

HTTP 표면은 운영 조회 라우터 하나뿐: `ingest_admin_router = APIRouter(prefix="/v1/admin/ingest", tags=["ingest-admin"], dependencies=[Depends(require_role("admin"))])` (신규 코드, 인증 의존성은 AU-1 소유, 기준 = 현행 /admin ADMIN_ONLY lib/auth/route-policy.ts:236-239). api_ro 커넥션으로 loader_ro 소유 rd 뷰 3개(제안)만 읽는다. 적재·판정·회차 처리는 HTTP 가 아니라 같은 코드베이스의 별도 프로세스 `hmg.ingest.worker`(loader 롤, 직접 DB 연결)가 수행: 루프 pull(20분, IG-1 오케스트레이터) · queue(60초, app.judgment_change 소비 디스패처) · cycles_tick(20분, 시간 기반 종결·발행 / 일 1회 파티션 선생성) + 별도 스케줄 태스크 `hmg.ingest.watch`(6시간, 경보 전용). 수동 실행은 CLI `python -m hmg.ingest.cli sync --project <uuid> [--force] [--max-runs N]`(HTTP 트리거·크론 비밀 폐기). 회차 운영·발행값 적재 HTTP(/v1/admin/cycles, 리포트 발행)는 AD-4 소관이며 이 모듈은 그 요청 큐의 소비자다.

Scope API 를 20분마다 당겨 ing(넓은 원본)에 해시 diff 로 반영하고, 같은 트랜잭션에서 rd(좁은 투영)의 판정 열·자식 표·회차·세대를 갱신하는 적재 모듈이다(A10·A17·G-16). 단위 경계를 DB-보정 §4 10단계에 맞춰 재정의했다: IG-1 = 스테이지·diff·ing 반영·트랜잭션 오케스트레이션·마무리, IG-2 = rd.job/rd.answer/자식/당사 요약/게이트 전파/is_rep 전부와 판정 입력 재판정, IG-3 = 회차 원장(개설·좌석·귀속·카운터·종결·발행·노출일·숨김)과 운영 요청(cycle_admin·report_publication·anchor_pin·answer_drop) 처리. 단위 설계의 주요 모순 27건을 해소했다: IG-3 HTTP 는 AD-4 로 이관, IG-1 ing 직조회 API 는 A17 위반이라 rd 뷰(제안) 경유로 전환, HTTP 수동 트리거 폐기(CLI), D8 예외 ③ 카운터 비노출 유지, R13 접기 키를 run-셀로 정정(IG-2 는 회차-셀·오름차순이라 D1·A15 위반), R01 술어를 현행 started_at 기준으로 정정, 세대 증가 1회로 일원화, 루프백 큐 INSERT 권한 결함 우회. 조회 API 위험은 low, 적재 트랜잭션은 폭 10배에서 미측정이라 high(6.6만 job run 기준 전체 체인 소요 미측정, 10배면 run 당 최대 수십만 job).

공통 구성요소
  • [프로세스 구성] API(api_ro/api_rw) 와 적재 워커(loader)를 같은 Python 패키지의 다른 프로세스로 둔다. 워커는 ECS 서비스 1개(서울, CDK, A14)에서 pull·queue·cycles_tick 루프를 돌리고, watch 는 EventBridge 스케줄 태스크로 분리한다. 분리 근거: 현행은 동기화가 16틱 연속 300s 타임아웃일 때 뒷단 관제가 0회 실행됐다(app/api/cron/cycle-chain-watch/route.ts:21-27).
  • [DB 연결] 워커는 loader 롤 직접 연결(asyncpg, statement 캐시 끔)로 PgBouncer transaction 모드를 거치지 않는다. 트랜잭션 모드에서는 세션 advisory lock 이 깨지므로 모든 잠금은 xact 형태만 쓴다. 롤 기본값 lock_timeout 5s·statement_timeout 180s(DB-v2.sql:864-865)는 유지하되 적재 트랜잭션은 SET LOCAL 로 문장 상한만 조정(열린 질문).
  • [잠금 규약] 네임스페이스 상수 NS_SURFACE=1, NS_PROJECT=2, NS_DIM=3. 적재·프로젝트 한정 재판정: pg_advisory_xact_lock_shared(NS_SURFACE, surface) 후 pg_try_advisory_xact_lock(NS_PROJECT, hashtext(scope_project_id)) (실패 시 그 프로젝트는 이번 패스 건너뜀). 전역 규칙 재판정: pg_advisory_xact_lock(NS_SURFACE, surface) 배타. 순서는 항상 surface → project → dim 으로 교착 방지. 패스 중복 실행 방지는 세션 잠금 대신 ing.sync_cursor 행을 FOR UPDATE SKIP LOCKED 로 집어 last_attempt_at 을 선기록하는 임대(현행 markSyncAttemptStarted lib/db/repositories/scope-mirror.ts:420 의미 계승: 에러는 지우지 않음).
  • [LoadContext] 모든 쓰기 트랜잭션이 공유하는 객체: load_id, kind, surface, scope_project_id, rule_ver(app.rule_set 의 applied 최신), touched_answer_keys, touched_cycle_ids, 카운터(jobs_fetched·jobs_changed·jobs_removed·rd_answers_upserted·rd_gate_propagated·rd_rep_flips·rd_children_rows). 생명주기: open_load = 짧은 별도 트랜잭션으로 ing.load 1행(status='running') 생성(스테이지 태깅용 load_id 선발급) → 적재 트랜잭션 → finalize = 같은 트랜잭션 끝에서 rd.surface_generation 1회 증가(rd 행이 바뀐 경우만), ing.run.sync_state='loaded'·last_load_id, ing.load committed·카운터, 해당 load_id 의 stage_* 삭제 → 실패 시 롤백 후 새 트랜잭션에서 ing.load failed·ing.run attempts+1·next_attempt_at 지수 백오프(5회 연속이면 blocked + 경보).

  • [2 계약 위반 A17] IG-1 GET status/backlog/load-log 가 ing 를 직접 읽는데 api_ro 는 ing 권한이 없다(DB-v2.sql:829-831). 해소: loader_ro 소유 rd 뷰 3개(제안 1) 경유.
  • [3 계약 위반: 경로 접두] /internal/v1/ingest/* 는 계약 §5 접두 /v1 과 명세 §8 admin 그룹에 맞지 않는다. 해소: /v1/admin/ingest/{status,backlog,loads}.
  • [4 HTTP 수동 트리거 폐기] IG-1 POST /sync(X-Cron-Secret). 사실 정정: 현행 인증은 Authorization: Bearer(lib/cron-auth.ts:8-16), force 파라미터는 app/api/cron/sync-mirror/route.ts:326(주석 :34)이지 route.ts:31 이 아니다. 패스가 수 분 걸려 동기 HTTP 에 맞지 않고 API 프로세스는 ing 쓰기 권한이 없다. 해소: 워커 CLI sync --project [--force] [--max-runs], 크론 비밀 폐기(fail-closed 인증 수단 축소).
  • [5 권한 기준 불일치] IG-3 은 operator IN (assigned, global) 로 운영 화면을 게이트했지만 operator 는 비용 액션 축이다(lib/db/schema.ts:35-41, lib/auth/operator-policy.ts:21-37). /admin 경로는 ADMIN_ONLY(lib/auth/route-policy.ts:236-239). 해소: 적재 운영 조회는 role='admin' 하나. AD-4 에도 같은 기준 권고.
  • [6 D8 예외 ③ 노출 위반] IG-3 가 completed_units·gap_answers·completion_ratio·analysis_done_ratio 를 응답에 넣고 perf 에서 'rd.cycle 자체 컬럼'이라 적었으나 rd.cycle 에는 없다(DB-v2.sql:426-430). 카운터는 ing.cycle 에만 있고 기능 API 비노출(DB-v2.sql:335, 계약 §3). 해소: 응답 제외, 운영자는 status·closed_by·경보로 본다. 노출 허용은 제품 결정(열린 질문).

쓰기
쓰기 스키마는 항상 앱(api_rw)이 아니라 로더(loader 롤)가 최종 반영한다(A17·B4). API 표면에서의 쓰기 경계는 두 개뿐: (1) PATCH /v1/admin/cycles/{cyc_key} — 트랜잭션 경계: app.judgment_change 1행 INSERT + app.access_audit_log 1행, 같은 트랜잭션. ing.cycle·rd.cycle 은 이 트랜잭션에서 건드리지 않는다(비동기 적용, GRANT 상 api_rw 는 ing/rd 에 쓰기 권한 자체가 없음 — REVOKE UPDATE,DELETE ON app.judgment_change FROM api_rw 로 상태 전이도 로더 전용). (2) POST /v1/admin/report-publications — 트랜잭션 경계: 이전 active 행 supersede UPDATE 1건 + report_publication INSERT 1건 + report_site_fact/engine_fact 배치 INSERT + judgment_change INSERT + access_audit_log INSERT, 전부 한 트랜잭션(report_publications_active_uq 제약이 동시성 가드). 로더 쪽 실제 rd 반영(ing.cycle UPSERT→rd.cycle, rd.report_unit_value 교체, rd.surface_generation 증가)은 GRANT UPDATE(status,claimed_at,applied_at,applied_load_id,error) ON app.judgment_change TO loader 로 loader 롤이 change 를 claim→apply 하는 별도 트랜잭션이며 감사 대상은 app.access_audit_log(kind='data_access') 로 남긴다.

인덱스: cycle_pick_idx ON rd.cycle (surface, round_date DESC) INCLUDE (cyc_key, project_key, servable, view_date, hidden_scope, generation) — GET /v1/admin/cycles 의 surface+round_date 범위 스캔을 인덱스만으로 커버, cycle_project_idx ON rd.cycle (project_key, round_date DESC) — project_key 필터(operator=assigned 교집합) 경로, report_publications_active_uq ON app.report_publication (surface, round_date, brand_scope) WHERE status='active' — R09 조회의 유일 인덱스, rd.report_unit_value PRIMARY KEY (round_date, file_seq) — cyc_key 로 찾는 경로는 인덱스 없음(제안: cyc_key 보조 인덱스, 목록 API 가 round_date 만으로 부족할 때)
회차 원장(rd.cycle)의 그레인은 '프로젝트 × 회차'다. 폭 10배는 프로젝트 수(현재 규모 기준 수십~수백)가 10배가 되는 것이지 회차당 행이 늘어나는 구조가 아니라 — 목록 API 는 cycle_pick_idx 로 100건 내외 range scan, 상세는 PK 단건 조회다. D8 예외 ③ 카운터(completed_units 등)는 rd.cycle 자체 컬럼이라 자식 표 스캔이 없다(집계 아님, 로더가 채워 넣은 값). PATCH(cycle_admin)·POST(report_publication) 는 app.judgment_change 1행 INSERT + 감사 로그뿐이라 폭과 무관하게 상수 비용. 위험은 로더 쪽(ing.cycle_run 귀속 스캔)에 있지 이 API 표면에는 없다.
신구 대조
현행 신구 대조 하네스(mig.parity_run/parity_result)의 feature 키는 F01~F07(값 비교)이며 회차 관제 자체는 값 산출 기능이 아니라 "어느 회차가 서빙 가능한가"라는 전제 조건이라 F01~F07 어디에도 직접 대응하지 않는다. 제안하는 별도 대조 항목: (1) ing.cycle vs 구 summary_cycles — cycle_id·status·view_anchor_at·hidden_scope 행 단위 diff(mig.row_oracle_diff 오라클 목록에 'summary_cycles' 자체가 없어 oracle CHECK 확장 필요, 제안), (2) rd.surface_generation.generation 단조 증가 검증(신 로더가 구 시스템과 같은 적재 이벤트에서 세대를 증가시키는지), (3) app.report_publication ingest 후 rd.report_unit_value 재계산값과 구 report_site_facts 값의 완전 일치(A5 는 발행값 고정이므로 diff=0 이 계약, 다르면 로더 버그). mig.parity_run.cycle_id 컬럼이 이미 있어 회차별 parity_run 을 이 단위로 스코프할 수 있음.
열린 질문

  • cyc_key 목록 API 의 pagination 방식(계약서는 커서 기반을 요구하나, rd.cycle 은 (surface, round_date) 자연키라 프로젝트당 행 수가 작아 단순 range 응답으로 충분할 수 있음) 미확정
  • app.judgment_change 의 cycle_admin/report_publication 처리 SLA(운영자가 PATCH 후 몇 분 내 rd 반영을 기대하는지) — 로더 폴링 주기(20분 pull 과 별도 루프인지) 미확인
  • GET /v1/admin/cycles 응답에 D8 예외③ 카운터(completed_units·gap_answers 등)를 항상 포함할지, 아니면 상세(GET /{cyc_key})에서만 줄지 — 목록이 프로젝트×회차 다건이라 폭 넓히면 응답 크기 증가

응답 형태
GET /v1/admin/cycles → `{ data: [{ cyc_key, cycle_id, surface, project_key, round_date, anchor_date, status, servable, view_date, hidden_scope, generation, completed_units?, expected_units?, gap_answers?, completion_ratio?, analysis_done_ratio? }], meta: { surface, mode:"admin", as_of, generation, ignored_filters, dropped_filters, suppressed:false } }` — 카운터 필드(?)는 D8 예외③으로 운영자 role 에서만 채움. GET /{cyc_key} 는 같은 셰이프의 단건 + 항상 카운터 포함. PATCH 응답은 `{ data: { change_id, status:"pending" }, meta:{...} }`(202). POST /v1/admin/report-publications 응답은 `{ data: { publication_id, status:"active", superseded: uuid|null }, meta:{...} }`(201). 페이지네이션은 목록이 소규모(perf 참고)라 커서 없이 `round_date` 범위 + LIMIT.
쿼리 설계
[배치] ingest.cycles.tick 절차(현행 4단계를 유지, DB 는 v2 표로 교체):
1. 오픈: `SELECT DISTINCT scope_project_id, cycle_anchor_at FROM ing.cycle_round cr LEFT JOIN ing.cycle c USING (scope_project_id, anchor_date) WHERE c.cycle_id IS NULL` 형태로 신규 anchor 탐지 → `INSERT INTO ing.cycle(...) ON CONFLICT (scope_project_id, cycle_anchor_at) DO NOTHING`.
2. 귀속: 미귀속 run 을 `ing.cycle_run(run_id, cycle_id, attributed_by)` 로 배치 INSERT, `cycle_open_idx`(WHERE status='open')로 열린 회차만 대상.
3. 카운터: 열린 회차별 `UPDATE ing.cycle SET expected_units=..., completed_units=..., completed_answers=..., gap_answers=(분석 없는 완료 답변 수, R12) WHERE cycle_id = $1` — completion_ratio·analysis_done_ratio 는 GENERATED STORED 라 재계산 불요.
4. 종결: `UPDATE ing.cycle SET status='closed', closed_by=..., closed_at=now() WHERE status='open' AND (다음 anchor 존재 OR (completion_ratio=1 AND updated_at < now()-interval '36 hours') OR now() > cycle_anchor_at + interval '3 days')`.
5. 같은 트랜잭션에서 rd.cycle 을 ing.cycle 의 투영으로 UPSERT(A17), rd.surface_generation.generation 을 1 증가 + last_load_id 갱신.

[API] GET /v1/admin/cycles:
```sql
SELECT cyc_key, cycle_id, surface, project_key, round_date, anchor_date, status, servable, view_date, hidden_scope, generation
FROM rd.cycle
WHERE surface = ANY($1::int2[])
  AND round_date BETWEEN $2 AND $3
  AND ($4::int2 IS NULL OR project_key = $4)
ORDER BY round_date DESC
LIMIT $5;
```
(cycle_pick_idx 로 커버, LIMIT 은 커서 없이 range 로 충분 — open_questions 참고)

[API] PATCH /v1/admin/cycles/{cyc_key} 처리 절차:
1. `SELECT cycle_id FROM rd.cycle WHERE cyc_key = $1` 로 uuid 해소(FastAPI 경로는 정수 cyc_key, 원장 키는 uuid cycle_id).
2. `INSERT INTO app.judgment_change (kind, subject_uuids, payload, requested_by) VALUES ('cycle_admin', ARRAY[$cycle_id], $payload, app.actor())`.
3. `INSERT INTO app.access_audit_log (actor_id, actor_role, kind, action, target) VALUES (app.actor(), $role, 'data_access', 'cycle_admin:'||$op, $cycle_id)`.
4. 응답은 202(비동기 적용) + change_id, 트랜잭션 커밋 시점엔 아직 rd 미반영(로더 폴링 대상).

[API] POST /v1/admin/report-publications 처리 절차:
1. `INSERT INTO app.report_publication (...) RETURNING id`.
2. `INSERT INTO app.report_site_fact (...)` · `INSERT INTO app.report_site_engine_fact (...)` 배치(파일 seq × 브랜드 × 엔진 행 수만큼).
3. 같은 트랜잭션에서 `UPDATE app.report_publication SET status='active' WHERE surface=$s AND round_date=$r AND brand_scope=$b` 의 이전 active 행을 `status='superseded', superseded_by=$new_id` 로 먼저 닫음(report_publications_active_uq 유니크 제약 준수).
4. `INSERT INTO app.judgment_change (kind, subject_uuids, payload) VALUES ('report_publication', ARRAY[$publication_id], NULL)`.
5. 로더가 이 change 를 집어 `rd.report_unit_value` 를 `(round_date, file_seq)` 키로 교체(DELETE+INSERT 또는 UPSERT), rd.surface_generation 갱신.
