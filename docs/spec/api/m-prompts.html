프롬프트

app/modules/prompts/router.py (설계안, 미구현): APIRouter(prefix="/v1/prompts", tags=["prompts"]). 경로 2개: GET "" (P-1 카탈로그, surface 로 global·website 분기, format=json|csv) · GET "/history" (P-2 변경 이력, format=json|csv). 경로 파라미터 라우트가 없어 순서 충돌 없음. 의존성 체인: get_principal(JWT·JWKS 검증 후 app.user_account 로드, A8) → require_surface_route(surface 별 역할 집합 + 메뉴 그룹 AND 판정) → resolve_scope(ScopeContext: all, brands, countries_catalog, countries_site) → 파라미터 모델(PromptCatalogParams / PromptHistoryParams, CommonFilters 상속) → 리포지토리(SQLAlchemy Core text SQL, asyncpg, api_ro 커넥션, prepared statement 캐시 끔). 응답은 공통 Envelope[T] = { data, meta }, data = Page[Row] = { rows, next_cursor, total }. CSV 는 같은 리포지토리 함수의 상한 모드 결과를 StreamingResponse(text/csv, Content-Disposition attachment, 상한 도달 시 X-Export-Truncated: true, Cache-Control: no-store) 로 직렬화.

프롬프트 모듈은 읽기 전용 2개 엔드포인트다. GET /v1/prompts(P-1)는 글로벌 표준 카탈로그(app.prompt 루트 프로젝트, 전량 응답 현행 패리티)와 웹사이트 카탈로그(app.website_prompt ⋈ app.website_site, 키셋 페이지 + rd.answer_w 측정 메타)를 surface 로 나눠 내고, GET /v1/prompts/history(P-2)는 app.prompt_audit_log 를 스코프 교집합·키셋으로 낸다. 단위 대조에서 26건을 해소했다. 핵심은 (1) P-2 가 dead code 라 한 listForPrompt 가 실제로 뷰어·관리자 타임라인 두 화면에서 호출됨(prompt-audit-timeline.tsx:44) → prompt_id 모드를 1급 기능으로 확정하고 스코프를 새로 강제, (2) 라우트 역할이 NON_VENDOR 가 아니라 STANDARD_VIEWERS(hq·region·country·admin, route-policy.ts:28)이고 website 표면은 WEBSITE_VIEWERS + 메뉴 그룹 게이트가 필요, (3) P-1 웹사이트 측정 렌즈에 round_date 범위와 R03 노출 게이트가 빠져 계약 §3 술어 규약 위반 → rd.cycle 가시 회차 집합(semi-join)과 그 min/max round_date 로 가지치기, (4) 스코프 국가 함수가 표면마다 다름(effectiveScopeCountries vs effectiveCountries)과 요청 국가 필터(정확 포함)와 스코프 술어(3분기)의 의미 차이를 분리, (5) 페이지네이션·meta·필드 표기(snake_case) 통일, (6) 현행 화면 필터 11종 중 P-1 에 빠진 depth4·kind·측정 여부·brand_presence 파생을 추가. DB-v2 신규 컬럼 제안은 없고 인덱스 제안 2건(app 표 pg_trgm, rd.answer INCLUDE engine_key)은 RDS 실측 게이트까지 보류다. 10배 최대 위험은 웹사이트 기본 정렬(마지막 측정일 내림차순)이 전 기간 rd.answer_w 집계를 매 페이지 요구한다는 점(high)이며, 글로벌 전량 응답 페이로드(약 2.4만 행)는 medium 이다. 빈틈 하나(페이지 머리 수집 기간 standardCollectionDates)는 공통 메타 소관으로 넘긴다.

권한
스코프 적용: FastAPI 의존성이 JWT(JWKS) 검증 후 `AllowedScope`(all/brands[]/regions[]/countries[])를 세션에서 파생(A8). 공통 필터 모델 규약대로 서버가 brand[]·country[] 쿼리 파라미터와 스코프를 default-deny 교집합한다(스코프 밖 값은 meta.dropped_filters). 라우트 게이트는 현행과 동일하게 NON_VENDOR(모든 role 허용, vendor 제외) — canAccessRoute("/standard/prompts") 상당. 운영자 게이트 없음(열람 전용, admin 전용 아님 — _actions.ts:14 주석 "편집과 달리 admin 전용이 아니다"). prompt_id 단일 조회(구 listForPrompt)도 같은 라우트 게이트 하나로 통합하고 스코프 교집합을 동일 적용 — 구 listForPrompt 는 스코프 미적용이었던 결함을 이 설계에서 닫는다(open_questions 참고).

성능(10배)
10배에서도 app.prompt_audit_log 는 관리자 저빈도 편집 이벤트 원장 — dim_prompt 12만 행(전체 프롬프트 카탈로그, DB-v2.sql:397 주석) 대비 편집 이벤트는 그 몇 % 수준으로 훨씬 작다(추정치, 볼륨 실측 없음). prompt_audit_project_idx(project_id, created_at DESC) 가 project_id=상수 + created_at 범위를 커버해 인덱스 레인지 스캔 후 LIMIT 조기 종료 — leaf 재구성 없이 100~500건만 페치.
인덱스: app.prompt_audit_project_idx (project_id, created_at DESC) — 주 필터·정렬 커버, app.prompt_audit_prompt_idx (prompt_id, created_at DESC) — prompt_id 지정 시 사용, app.prompt PK(project_id, prompt_id) — LEFT JOIN 룩업
브랜드·국가 스코프 필터는 JOIN 후 WHERE 라 인덱스 미지원이지만, project_id+created_at 로 이미 좁혀진 소량 행에 적용되므로 순차 필터 비용 낮음. event_type 전용 인덱스 없음 — 카디널리티 7종뿐이라 불필요(select성 낮아 인덱스 이득 적음). LIMIT+키셋이라 OFFSET 페이지네이션의 후반 페이지 비용 폭증 없음.
신구 대조
신구 대조: 구 listGlobalScoped(project_id=STANDARD_ROOT_PROJECT_ID, from=90일 전, brand/country 스코프)와 새 GET /v1/prompts/history?from=<90일전> 이 같은 행 집합·같은 순서(created_at DESC)를 반환하는지 대조. 하네스 F01~F07 키에 이 기능이 없으면(현재 기능은 프롬프트 카탈로그 화면 보조 탭이라 핵심 지표 F01~F07 범위 밖으로 추정) 별도 대조 항목 신설 필요: "PA-01 감사 이력 건수·필드 일치"(같은 브랜드·기간 스코프에서 count(*) 와 최근 20건 audit_id·event_type·changes JSON 대조). CSV export 는 클라이언트 측 filtered 배열을 그대로 직렬화하던 것을 API 응답 페이지들을 합쳐 동일 CSV 를 만드는 방식으로 전환(서버 export 엔드포인트 신설은 하지 않음, open_questions 참고).
열린 질문
  • 구 listForPrompt(스코프 미적용, UI 미호출 dead code)를 prompt_id 파라미터로 흡수하며 스코프를 새로 강제하는 것이 맞는지: 관리자 화면(P-1, admin/standards)에서 향후 이 파라미터로 전체 이력(스코프 무관)을 보고 싶을 수 있음 — admin 전용 우회가 필요하면 별도 role 게이트(operator=global) 추가 여부는 P-1/AU-1 담당과 조율 필요.
  • listDailyCounts(90일 일별 카운트, 차트 마커용)는 현재 UI 어디서도 호출되지 않는 dead code로 확인됨(grep 0건) — 이 설계에서 드롭. 부활이 필요하면 별도 엔드포인트로 재제안.
  • CSV 전체 내보내기가 500건(limit 상한)을 넘는 스코프(대형 브랜드·90일 전체)일 때 클라이언트가 여러 페이지를 순회해 합쳐야 하는데, 이 반복 호출이 사용자 대기 시간에 문제없는지 — 아니면 limit 상한을 CSV 전용으로 더 높게(예: 5,000) 허용할지 P-1 설계 리드 결정 필요.
  • meta.generation·meta.cycles 필드가 계약서 공통 응답 형태에 포함되는데, 이 API 는 rd(회차 파티션 사실표)를 전혀 읽지 않아 실질적 의미가 없음 — 공통 형태를 유지하되 빈 값/고정값으로 채우는 것이 맞는지, 아니면 비-회차형 API 는 meta 축소 변형을 쓰는지 계약서에 명시 필요.
  • app.prompt LEFT JOIN 에서 이론상 prompt_id 가 app.prompt 에 없는 감사 행이 있을 수 있는지(하드 삭제 이력·데이터 정합 예외) — 현재 soft-delete(deleted_at) 만 존재해 발생 안 할 것으로 보이나 FK 제약이 없어(현행 스키마도 FK 없음) 확정은 미확인.

쿼리 설계
쓰기 없음(읽기 전용). SQL 스케치:\n```sql\nSELECT pal.audit_id, pal.prompt_id, pal.actor_id, pal.actor_type, pal.event_type,\n       pal.changes, pal.batch_id, pal.created_at,\n       ua.email AS actor_email, p.text AS prompt_text, p.brand_code AS prompt_brand\nFROM app.prompt_audit_log pal\nLEFT JOIN app.prompt p ON p.prompt_id = pal.prompt_id\nLEFT JOIN app.user_account ua ON ua.user_id = pal.actor_id\nWHERE pal.project_id = :standard_root_project_id   -- app.project WHERE kind='standard_root' (project_one_root 유일 인덱스로 1행 상수화)\n  AND pal.created_at >= :from\n  AND (:to IS NULL OR pal.created_at < :to)\n  AND (:prompt_id IS NULL OR pal.prompt_id = :prompt_id)\n  AND (:event_types IS NULL OR pal.event_type = ANY(:event_types))\n  -- 스코프 교집합(브랜드): scope.all 이면 생략\n  AND (p.brand_code IS NULL OR p.brand_code = ANY(:scope_brands) OR p.brand_code = 'HMG')\n  -- 스코프 교집합(국가/시장): effectiveScopeCountries 상당, catalogMarketScopeCondition 동치\n  AND (p.regions IS NULL OR NOT EXISTS (SELECT 1 FROM unnest(p.regions) r WHERE btrim(r)<>'' AND lower(btrim(r)) NOT LIKE 'x:%')\n       OR EXISTS (SELECT 1 FROM unnest(p.regions) r WHERE lower(btrim(r)) NOT LIKE 'x:%' AND upper(btrim(r)) = ANY(:scope_countries)))\n  -- 키셋 페이지네이션(다음 페이지)\n  AND (pal.created_at, pal.audit_id) < (:cursor_created_at, :cursor_audit_id)\nORDER BY pal.created_at DESC, pal.audit_id DESC\nLIMIT :limit;\n```\n:standard_root_project_id 는 app.project 에서 `WHERE kind='standard_root'`로 요청마다 조회하거나 기동 시 1회 캐시(변경 없음, project_one_root 유일 인덱스가 보증).
