프로젝트

/v1/projects (APIRouter 1개에 하위 라우터 4개 결합: projects.py(PJ-1), members.py(PJ-2), prompts.py(PJ-3), settings.py(PJ-4)) + /v1/me/project-invites (PJ-2 소유, me 라우터)

프로젝트 모듈은 집계 지표가 없는 app 스키마 CRUD 모듈이다(rd 읽기는 프롬프트 영향 미리보기와 Scope 연결 진단 2곳뿐). 단위 설계 4개 중 PJ-4 는 산출물이 비어 있어("test", /v1/x) 현행 setting/_actions.ts 기준으로 설계 리드가 보충 초안을 썼다(단위 재설계 필요). 핵심 해소: (1) ai_engines 는 PJ-1 PATCH 에서 빼 PJ-4 PUT /settings/engines 로 옮기고 Owner+운영자 이중 게이트를 복원(현행 setting/_actions.ts:255), (2) domain 은 owned base 파생값이라 PATCH 에서 제외(setting/_actions.ts:144, general-form.tsx:57), (3) Scope 전파는 전부 app.scope_outbox 비동기(계약 §5, DB-앱-도메인.md:42)로 확정해 PJ-3 open ① 을 닫음, (4) PJ-1 의 scope-link 제안 인덱스는 사실 오류(rd.job 은 비파티션 DB-v2.sql:441, INCLUDE(served) 는 HOT 규율 위반)로 기각하고 최신 회차 한정 쿼리로 대체해 PJ-4(admin 전용)로 이동. DB 선행 과제 3건을 발견: DB-v2.sql 의 app.project·app.prompt 트리거는 주석(:120·:156)만 있고 CREATE TRIGGER 가 없다, outbox 워커가 쓸 롤 권한이 없다(loader 는 app SELECT 만, :860-861), api_rw 는 rd 를 못 읽는다(:839-843). 10배 성능 위험은 전 엔드포인트 low(최대 medium 1건: 프롬프트 영향 미리보기)이며, 실제 위험은 성능보다 비동기 전환에 따른 UX·워커 계약과 병행 운영 중 쓰기 이원화다.

모듈 공통

공통 구성요소
  • 라우터 구조: app/modules/projects/{router.py, deps.py, schemas.py, errors.py, sql/*.sql, repo/{projects,members,prompts,fields,settings,outbox,judgment,audit}.py, xlsx.py}. router.py 가 APIRouter(prefix='/v1') 에 projects·members·prompts·settings 하위 라우터와 me 라우터(/v1/me/project-invites)를 include. 정적 세그먼트 경로(member-audit, prompts:export 등)는 {id} 경로보다 먼저 선언.
  • DB 연결 2종(A17·권한 §10): ro_conn = api_ro 풀(rd·app·ext SELECT, default_transaction_read_only, statement_timeout 5s: DB-v2.sql:830-836), rw_tx = api_rw 풀 트랜잭션(app 쓰기만, rd USAGE 없음: DB-v2.sql:839-843). rd 를 읽는 엔드포인트(lifecycle-impact, scope-link)는 ro_conn 만 쓰고, 쓰기 트랜잭션 안에서 rd 를 조회하지 않는다.
  • rw_tx 의존성: BEGIN 직후 SET LOCAL app.actor_id = principal.user_id(app.actor() 가 없으면 예외, DB-v2.sql:96-98), SET LOCAL statement_timeout='5s', SET LOCAL app.request_id. PgBouncer transaction 모드이므로 세션 SET 금지(SET LOCAL 만), prepared statement 캐시 끔(계약 §5). 모든 쓰기 액션 = 단일 트랜잭션(원본 변경 + 감사 + outbox + judgment_change).
  • 권한 의존성 require_project(level): level ∈ member | owner | operate | owner_and_operate. 판정: ① JWT(JWKS) → app.user_account(인증 모듈 get_principal) ② role='admin' 이면 통과(현행 member/_actions.ts:41-43 등 계승) ③ app.project 행이 없거나 kind='standard_root' 이거나 비멤버면 404(member/page.tsx:38-40 계승) ④ 멤버지만 수준 미달이면 403. operate = canOperateProject(operator-policy.ts:30) 포팅 + global 분기에도 프로젝트 brand_code·country_code 가 세션 스코프 안인지 대조(DB-앱-도메인.md:42 결정). 반환 ProjectCtx(project, membership, principal).
  • IDOR 구조적 차단: 하위 리소스(prompt_id·field_id·candidate_id·user_id) 를 다루는 모든 SQL 에 WHERE project_id = :project_id 를 함께 둔다(현행 assertFieldInProject/assertPromptInProject prompt/_actions.ts:694-712 의 대체). DDL 복합 FK(app.prompt_custom_field_value → (project_id, prompt_id)/(project_id, field_id), DB-v2.sql:166-170)가 이중 방어.
  • 공유 Pydantic 모델: CrudMeta(계약 meta 형태 그대로, surface·mode·as_of·cycles·generation·suppressed = null, ignored_filters·dropped_filters = []), Envelope[T]{data, meta}, Page[T]{items, next_cursor}, ErrorBody{error:{code, message}}, Project, ProjectCreate, ProjectPatch(extra='forbid' 로 domain·ai_engines·country_code 거부), Member, MemberAuditEntry, Invite, Prompt(프로젝트용: 은퇴 축 제외), PromptCreate, PromptPatch, PromptCandidate, CustomField, LifecycleImpact, ExecuteResult, ImportResult, SettingsBundle, EngineHistoryEntry, OwnedBase, TrackedUrl, Competitor, Vehicle, ScopeLink.

  • 에러 코드 표(HTTP status + code): not_found 404, forbidden 403, validation 422, conflict 계열 409(already_member, last_owner_cannot_demote, cannot_remove_owner, not_active, already_that_role, prompt_not_draft, shared_prompt, name_mismatch, duplicate), bad_request 400(self_invite, cannot_remove_self, country_immutable, invalid_engine, reserved_label). 현행 ActionResult 한국어 문자열은 프론트 i18n 이 code 로 매핑.
