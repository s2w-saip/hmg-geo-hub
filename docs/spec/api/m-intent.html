고객 관심

app/modules/intent/ 패키지 하나, APIRouter(prefix="/v1/intent", tags=["intent"]) 아래 하위 라우터 3개: (1) keywords.py (IN-1: /keywords, /insight, /related, /lookup, /fetches, /serp-drafts) (2) social.py (IN-2: APIRouter(prefix="/social"), /context-map/*, /prompts) (3) candidates.py (IN-1·IN-2 공용: POST /candidates). 공용 파일: deps.py(인증·프로젝트 스코프·운영자 게이트·api_ro/api_rw 세션·actor GUC), schemas.py(IntentMeta·Envelope·Page·SentimentBreakdown·CandidateIn 등), repo_kw.py(rd.kw_* 읽기 SQL), repo_ctx.py(ext.ctx_* 읽기 SQL), repo_app.py(app.* 쓰기 SQL: tracked_keyword·prompt_candidate·kw_prompt_draft·ctx_generated_prompt·judgment_change), presets.py(location_presets 이식 + term_norm), llm.py(OpenRouter 호출 래퍼, 트랜잭션 밖 실행 강제), xlsx.py(export 스트리밍). 읽기 핸들러는 api_ro 풀만, 쓰기 핸들러는 '읽기(api_ro) → 외부 호출(무 트랜잭션) → 쓰기(api_rw 단일 짧은 트랜잭션)' 3단 구조. api_rw 는 app 스키마 USAGE 만 있으므로(DB-v2.sql:839-843) rd·ext 를 같은 트랜잭션에서 읽지 않는다.

IN-1(키워드)과 IN-2(소셜 스크레이핑)를 /v1/intent 한 라우터로 묶었다. 핵심 해소 5가지: (1) IN-1 의 동기 DataForSEO 재조회는 api_rw 가 ext·rd 를 쓸 수 없다는 계약 §3 과 충돌하므로, app.judgment_change 에 kind 'dfs_fetch'(DDL 변경 제안)를 넣어 적재기(loader)가 수집하는 비동기 큐 방식(202 + 상태 폴링)으로 확정했다(DB-ACR-외부-데이터.md:70 의 '수집 중' 응답 설계와 일치). GET 에서 유료 호출을 일으키는 fresh 파라미터는 제거했다. (2) 키워드 데이터 읽기를 keyword_id 기반에서 term+country 기반(/v1/intent/insight·related·lookup)으로 바꿔, 프로젝트 없는 표준 화면(/customer-interest/google-keywords, 현행도 insight 를 실호출함)까지 같은 엔드포인트로 덮는다. (3) 후보 풀 쓰기를 POST /v1/intent/candidates(source=google_keyword|social_scraping, 다건, 앱 단 dedup) 하나로 합쳤다. (4) 응답 봉투를 IntentMeta(공통 meta 필드 유지, surface·mode·cycles·generation=null, as_of=관측시각 또는 스냅샷 시각, page 확장)로 통일하고, 삭제는 두 단위 모두 DELETE ?ids= 로 맞췄다. (5) DB-v2 에서 빠진 ext.ctx_drive(snapshot_id, requirement_id) 인덱스(초안 DB-ACR-외부-데이터.sql 에는 있었음)와 app.ctx_generated_prompt 의 layer·funnel_stage·priority·origin·seed_key 컬럼, app.prompt_candidate(project_id) 인덱스를 제안으로 올렸다. 두 단위 모두 측정 지표 M01~M12 를 소비하지 않고, 요청당 읽는 행이 10배에서도 수십~수백 행이라 성능 위험은 낮다. 예외는 export(전량)와 LLM·외부 호출 지연이다.

모듈 공통

공통 구성요소
  • 라우터: /v1/intent 루트 APIRouter + keywords·social·candidates 하위 라우터(router 필드 참조). 모든 project 종속 엔드포인트는 project_id 를 query parameter 로 받는다(IN-1 이 'path' 라고 적었지만 경로에 자리가 없던 모순 해소).
  • 의존성 get_principal: Supabase JWT(JWKS) 검증 → app.user_account(role, operator, scope_all, scope_countries …) 로드. 인증 모듈(AU) 소유, intent 는 소비만.
  • 의존성 require_project_member(project_id): app.project 존재 + app.project_member(project_id, user_id).status='active' 또는 admin 또는 operator='global'. 읽기용.
  • 의존성 require_operate(project_id?): 현행 canOperateProject(lib/auth/operator-policy.ts, operator-policy.test.ts:45-65 로 검증된 규칙) 이식. admin 통과, operator='none' 거부, 'global' 통과, 'assigned' 는 active 멤버만. project_id 가 없으면(표준 화면) admin 또는 operator='global' 만. 모든 쓰기·유료 호출(추가·삭제·fetches·serp-drafts·candidates·social prompts 생성·삭제)에 적용.
  • 의존성 require_standard_viewer: project_id 없는 키워드 읽기(표준 화면)용. role IN (hq, region, country, admin)(현행 STANDARD_VIEWERS, lib/auth/route-policy.ts:28) + country 가 사용자 국가 스코프 안(scope_all 이면 통과). 단일값 파라미터라 스코프 밖이면 403.
  • DB 세션 의존성 두 개: ro_conn(api_ro 풀, default_transaction_read_only=on, statement_timeout 5s) 과 rw_tx(api_rw 풀, 트랜잭션 시작 시 SELECT set_config('app.actor_id', :uid, true) 로 행위자 GUC 설정, app.actor() 호환 DB-v2.sql:96-98). PgBouncer transaction 모드라 SET 이 아닌 set_config(..., is_local=true) 만 쓴다.
  • Pydantic 모델 IntentMeta: 공통 meta 모양 유지 {surface: null, mode: null, as_of, cycles: null, generation: null, ignored_filters, dropped_filters: [], suppressed: []} + 확장 page{total, page, size}·snapshot_id·freshness. 클라이언트가 공통 필터 축(brand[], engine[] 등)을 보내면 ignored_filters 에 이름을 적는다(계약 §2 규약 준수, 단위들이 surface 생략·고정값 'intent' 로 갈렸던 것 통일).
  • Pydantic 모델 Envelope[T] = {data: T, meta: IntentMeta}, Page[T] = Envelope[list[T]] + meta.page. IN-2 의 'Paged' 와 IN-1 의 {data, meta} 를 이 둘로 통일.
  • Pydantic 모델 SentimentBreakdown {positive, negative, neutral(정수 개수), total, positive_pct, negative_pct, neutral_pct}: 현행 sentimentPerspective(lib/db/repositories/scope-context-map.ts:87-100) 규칙 그대로(분모 = 세 감성 합, utterance_count 아님, 각 비율 Math.round 와 같은 반올림, total=0 이면 neutral_pct=100). 필드명 perspective(buyer/seller) 는 폐기(IN-2 open 2 확정).
  • Pydantic 모델 CandidateIn {source: Literal['google_keyword','social_scraping'], items: list[{text, source_keyword?}] (1~200)}, CandidateOut {added_count, skipped_count, candidate_ids}.
  • 공유 함수 presets.py: LOCATION_LANGUAGE_PRESETS 를 lib/keyword/location-presets.ts 정적 배열(getPresetById :72) 에서 파이썬 상수로 이식, country(ISO2, 소문자 id) → (location_code, language_code). 알 수 없는 country 는 400(현행은 'kr' 폴백, insight/route.ts:24-26: 조용한 폴백은 오답을 숨기므로 400 으로 바꾼다). DB 테이블 승격은 하지 않는다(IN-1 open 7 확정).
  • 공유 함수 term_norm(term) = unicodedata.normalize('NFC', term).strip().lower(): 현행 cacheKey 의 trim().toLowerCase()(lib/keyword/insight.ts:54-55) 와 같고 NFC 만 추가. rd.dim_keyword.term_norm 을 쓰는 적재기와 같은 함수를 공유 패키지로 둔다(불일치 시 조회 전부 missing).
  • 공유 상수 FRESHNESS = {insight: 24h, related: 7d, search: 7d}: 현행 TTL(lib/keyword/cache.ts:41-44) 이식. API 가 fetches 수락 시 '신선하면 skip' 판단과 GET 응답 freshness 계산에만 쓴다. app.rule_param 편입은 하지 않는다(rule_param 은 rule_set 지문에 들어가 재판정을 일으키는 판정 입력이라 성격이 다름, IN-1 open 6 확정).
  • 공유 SQL repo_kw: resolve_kw_keys(term_norms[]) (rd.dim_keyword UNIQUE(term_norm)), latest_volume(kw_keys, loc, lang), trend_12m(kw_key, loc, lang), latest_serp_call(kw_key, loc, lang), serp_rows_with_latest_draft(call_id), latest_suggestion_call(seed_kw_key, loc, lang), suggestion_rows(call_id, include_seed).
  • 공유 SQL repo_ctx: active_snapshot(industry_entity_id) (ext.ctx_snapshot 부분 유니크), list_entities(snapshot, type, search, sort, dir, page, size), count_entities, list_combinations, combo_max, entity_detail 4조회, stats, seed_pool(snapshot, n_ctx=150, n_cond=200, n_combo=500).
  • 공유 SQL repo_app: insert_candidates(project_id, source, rows) (기존 텍스트 SELECT 후 신규만 INSERT, 한 트랜잭션), tracked_keyword CRUD, insert_kw_drafts, insert_ctx_prompts ON CONFLICT DO NOTHING, soft_remove_ctx_prompts, enqueue_dfs_fetch, find_open_dfs_fetch.
  • 공유 llm.py: OpenRouter 호출 래퍼. DB 커넥션을 쥔 채 호출하지 못하게 시그니처에서 커넥션을 받지 않는다. 모델명은 응답 행에 기록(kw_prompt_draft.model, ctx_generated_prompt.model).
  • 정렬·방향 화이트리스트: sort·dir 은 SQL 파라미터로 바인딩할 수 없으므로 {('name','asc'): 'canonical_name ASC', …} 고정 매핑에서만 SQL 조각을 고른다. search 는 ILIKE 이스케이프(%, _, \) 공용 함수.
  • 서버 설정 CONTEXT_MAP_INDUSTRY_ENTITY_ID(+ LLM 라벨 CONTEXT_MAP_KEYWORD='자동차'): 현행 코퍼스가 단일 자동차 산업(_actions.ts:141-147 주석) 이므로 활성 스냅샷은 이 설정값으로 고른다. 활성 스냅샷이 없으면 A12 '준비 중' 응답(data=null, meta.suppressed=['no_active_snapshot']).
단위 간 정리
  • [계약 위반] IN-1 이 ext.dfs_call·rd.kw_volume_monthly·rd.kw_serp·rd.kw_suggestion 을 API 가 쓰는 동기 refresh 로 설계했다. 계약 §3 은 api_rw = app + judgment_change INSERT, rd·ext 는 loader(DB-v2.sql:9-10, 839-858) 이므로 불가. IN-1 권장안 (a)'collector 전용 DB 역할'과 (c)'api_rw 에 권한 부여'는 모두 역할 경계 변경이라 기각. 확정: (b) 변형 = POST /v1/intent/fetches 가 app.judgment_change('dfs_fetch', 제안 P1) 를 넣고 202, DataForSEO 적재자가 처리, 클라이언트는 GET /v1/intent/fetches/{id} 폴링 후 GET insight 재조회. DB-ACR-외부-데이터.md:70('첫 조회는 수집 중 상태로 응답') 과 일치.
  • [계약 위반] IN-1 의 GET insight 에 fresh=true 로 유료 재조회를 승격하는 안: GET 은 api_ro(읽기 전용) 이고 부수효과가 없어야 하므로 제거. 재조회는 fetches(force=true) 로만.
  • [빈틈] IN-1 refresh 흐름에서 SERP 초안(app.kw_prompt_draft) 은 loader 가 쓸 수 없다(loader 는 app SELECT 만, DB-v2.sql:860). 현행은 insight 계산 안에서 전 행 초안을 한 번에 만든다(lib/keyword/insight.ts:98-114). 확정: 적재 완료 후 클라이언트가 POST /v1/intent/serp-drafts(ranks 생략 = 초안 없는 전 행, LLM 1회) 를 부르고, IN-1 의 행 단위 /serp/{rank}/prompt 는 같은 엔드포인트의 ranks=[n](재생성) 으로 흡수. 초안이 없는 행은 suggested_prompt=null(현행은 term 폴백, :86·:112): 화면 폴백은 FE 가 한다.
  • [빈틈] 표준 화면 /customer-interest/google-keywords 는 project_id 없이 GoogleKeywordView 를 렌더하고 /api/keyword/insight·related 를 실호출한다(google-keywords/page.tsx, google-keyword-view.tsx:212·241). 성능(10배)
10배에서도 요청당 O(수십) 행 — 트렌드 ≤12, SERP ≤depth(기본 10), 연관어 ≤30, 목록 ≤수백(project_tracked_keyword 전체, 프로젝트당). 전용 leaf/파티션 없음(kw_* 는 파티션 표가 아님) — 가지치기 조건은 WHERE kw_key/location_code/language_code = 상수뿐.

-- GET contexts/conditions (동일 쿼리, type 만 다름)
WITH active AS (SELECT snapshot_id FROM ext.ctx_snapshot WHERE industry_entity_id = $industry_id AND is_active)
SELECT e.id, e.canonical_name, e.dimension, e.mention_count, e.utterance_count,
       e.sentiment_positive, e.sentiment_negative, e.sentiment_neutral,
       (SELECT count(*) FROM ext.ctx_drive d WHERE d.snapshot_id = e.snapshot_id
          AND (CASE WHEN $type='ConsumerContext' THEN d.context_id ELSE d.requirement_id END) = e.id) AS linked_count
FROM ext.ctx_entity e, active
WHERE e.snapshot_id = active.snapshot_id AND e.type = $type
  AND ($search IS NULL OR e.canonical_name ILIKE '%'||$search_escaped||'%')
ORDER BY (CASE WHEN $sort='name' THEN e.canonical_name END) $dir,
         (CASE WHEN $sort='mentions' THEN e.mention_count END) $dir
LIMIT $size OFFSET $page*$size;
-- + 별도 COUNT(*) 쿼리(total)

-- GET combinations
SELECT c.cond_a, c.cond_b, c.co_count, a.canonical_name AS a_name, b.canonical_name AS b_name
FROM ext.ctx_combination c
JOIN ext.ctx_entity a ON a.snapshot_id = c.snapshot_id AND a.id = c.cond_a
JOIN ext.ctx_entity b ON b.snapshot_id = c.snapshot_id AND b.id = c.cond_b
WHERE c.snapshot_id = $active_snapshot
  AND ($search IS NULL OR a.canonical_name ILIKE ... OR b.canonical_name ILIKE ...)
