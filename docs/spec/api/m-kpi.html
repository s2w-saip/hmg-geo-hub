KPI

app/modules/kpi/router.py: APIRouter(prefix="/v1/kpi", tags=["kpi"]). 핸들러 3개(GET /summary, GET /compare, GET /engines)는 얇게 두고, 공통 의존성 Depends(kpi_request) 가 (1) JWT 검증된 ScopeContext (2) 공통 필터 모델 FilterParams + KpiSurfaceParams(surface, project_id) (3) resolve_scope 결과(ResolvedScope) (4) CycleSet 을 만들어 넘긴다. 파일 구성: router.py · deps.py(kpi_request) · schemas.py(공유 Pydantic) · sql/own_cols.py(관점 브랜드 열 선택기) · sql/answer_counts.py(rd.answer 단일 스캔 빌더, group_by = none|engine|window) · sql/citation_counts.py(rd.citation M05 빌더) · sql/url_rates.py(M06·M07·인용 정확도 + R09 발행값 접기, citations 모듈 /v1/citations/targets 와 공유) · sql/prompt_counts.py(M12 적용 프롬프트) · logic/compare.py(lib/kpi/period-compare.ts 순수 로직 이식) · logic/consistency.py(엔진 일관성). 분석 쿼리는 SQLAlchemy 2 Core text() + asyncpg, api_ro 롤(statement_timeout 5s, force_custom_plan, 읽기 전용), PgBouncer transaction 모드라 prepared statement 캐시 끔.

KPI 모듈은 카드(K-1 /v1/kpi/summary), 기간 비교 Δ(K-2 /v1/kpi/compare), 엔진별 서브 지표(K-3 /v1/kpi/engines) 세 엔드포인트를 하나의 rd.answer 스캔 빌더와 하나의 rd.citation 스캔 빌더 위에 올린다(group_by 만 다름: 없음 / engine_key / 창 라벨). 세 단위 설계를 대조해 모순 22건을 해소했다. 핵심은 다섯 가지다. (1) 시간 술어를 round_date 로 통일(K-1 의 anchor_date 누적 스캔은 G-04 위반). (2) 회차 게이트(servable, view_date <= rd.today_kst(), 계열별 hidden_scope)를 공용 CycleSet 으로 세 단위에 똑같이 건다(K-1 누적 모드와 K-2 는 게이트가 없었고, K-3 는 current_date 로 조인했다). (3) M02·M03 은 G-03 에 따라 rd.answer 당사 열로만 계산한다(K-2 의 rd.answer_brand 합산은 필터 미적용 버그이자 카드 값과 불일치). (4) M05 자사 판정을 표면별로 확정했다(global = owner_key 허용 배열(G-21), website = loc_owned OR tgt_hit(scope-aggregates.ts:8655), project = loc_owned). (5) 관점 브랜드 모집단(bgrp = ANY)·기본 엔진(dflt)·택소노미(prompt_key 집합)를 세 단위에 같은 규칙으로 적용한다. 단위들의 DDL 밖 제안 3건은 전부 기각했다: rd.cycle.expected_units(계약 D8 예외 ③ 'API 비노출' 과 충돌, 회차 수 기반 대안으로 대체하고 제품 결정으로 올림), rd.citation 부분 인덱스(HOT 규율 위반), rd.cycle ASC 인덱스(불필요). 성능 위험은 K-2(365일 창 = 730일 스캔, 웹사이트 인용) high, K-1·K-3 medium 이며, 판정은 RDS 실데이터 실측 게이트에서 한다.

단위 간 정리
  • F1 시간 축: K-1 기간 누적이 rd.answer.anchor_date BETWEEN 으로 스캔하고 round_date 를 '근사 힌트' 로만 썼다. G-04 확정(round_date = 필터·추이·파티션 키)과 계약 §3 술어 규약 위반이라 세 단위 모두 round_date BETWEEN :from AND :to 로 통일(K-3 metrics_rules 의 anchor_date 문구도 정정).
  • F2 회차 게이트 누락: K-1 누적 모드는 회차 게이트 없이 답변을 직접 스캔(미발행·노출 전·숨김 회차 누출), K-2 는 mention_agg·brand_agg·citation_agg 어디에도 servable·view_date·hidden_scope 가 없음, K-3 는 rd.answer 만 rd.cycle 과 조인하고 rd.citation 에는 게이트가 없으며 current_date(UTC 세션 기준)를 썼다. 공용 CycleSet(servable ∧ view_date <= rd.today_kst() ∧ 계열별 hidden_scope)으로 세 단위의 답변·인용 스캔 모두에 같은 규칙을 FILTER 제외 목록으로 건다.
  • F3 hidden_scope 계열 규칙 통일: 언급 계열 제외 = (1,3), 인용 계열 제외 = (1,2). K-1 은 맞았고 K-2 는 인용 계열만 '별도' 로 미뤘으며 K-3 는 meta.suppressed 를 불리언 하나로 뭉갰다. 지표별 meta.suppressed 맵으로 통일.
  • F4 M02·M03 원천: K-2 가 share·favorability 를 rd.answer_brand 합으로 계산했다. G-03(a) 와 계약 §3('카드·추이의 당사 수치는 rd.answer 당사 열로 자식 스캔 없이')에 어긋나고, brand_agg 에 엔진·국가·dflt·bgrp 필터가 전혀 없어 필터를 걸면 카드(K-1)와 Δ(K-2)의 같은 지표가 다른 모수를 쓰는 버그다(또 PK 에 competitive 가 있어 mention_count 합이 ment_total 과 다를 수 있다). K-2 도 rd.answer 의 ment_*/ment_total/sent_* 로 바꾸고 brand_agg 문장을 없앤다(문장 5개 → 원장 1 + 답변 1 + 인용 1).
  • F5 M05 자사 판정: K-1·K-2 는 모든 표면에 loc_owned, K-3 는 global = owner_key·website/project = loc_owned(+tgt_hit 추정)로 서로 달랐다. 확정: global = owner_key = ANY(허용 배열)(G-21, DB-인용-도메인-웹사이트.md:59), website = loc_owned OR tgt_hit(타겟 ⊂ 자사, websiteTargetOwnedClause scope-aggregates.ts:8655), project = loc_owned(설정 베이스 ∪ 카탈로그 루트, ownedBasePrefixesForProject server.ts:866, 추적 URL 은 자사 아님). citation_counts 한 곳에서만 정의.
  • F6 관점 브랜드 모집단: K-1·K-3 는 own_brand 모집단 술어(카탈로그 brand X ∪ 공통, 계약 §2·standard-filters.ts:60-64)를 쿼리에 넣지 않았고 K-2 는 brand[] 가 있을 때만 bgrp 를 걸었다. 세 단위 모두 항상 bgrp = ANY(:pop_bgrps)(서버가 own_bits·스코프·brand[] 교차로 계산)를 WHERE 에 건다.
  • F7 brand[] 처리 불일치: K-1 지원(쿼리 반영 없음), K-2 supported 는 'rd.catalog_entry 경유 prompt_key' 인데 쿼리는 bgrp 사용, K-3 ignored. 통일: brand[] 는 bgrp 교차 마스크로 모집단을 좁히는 축(DB-측정-코어 §5 매핑)으로 세 단위 모두 지원. K-3 는 own_brand 관점 열만 읽지만 모수 자체가 brand[] 로 바뀌므로 ignored 가 아니다.
  • F8 기본 엔진: K-2 citation_agg 만 dflt 를 걸고 나머지는 없었다. engine[] 가 비면 dflt, 있으면 engine_key = ANY 를 rd.answer·rd.citation 양쪽에 똑같이 건다.
