답변 드릴다운

APIRouter(prefix="/v1/answers", tags=["answers"]) 1개. 파일 구성: app/modules/answers/router.py(핸들러 2개: GET "" = AN-1, GET "/{job_id}" = AN-2), schemas.py(Pydantic v2 요청·응답 모델), repo.py(SQLAlchemy Core 텍스트 SQL: 회차 게이트·헤더 로더·목록·상세 json_agg 단일문), gates.py(R03·R04 계열 게이트 순수 함수), render.py(현행 TS 포팅: verify_stance_evidence·build_sentiment_spans·own 판정). 공통 의존성은 filters·auth 모듈 것을 Depends 로 주입: get_principal(JWT JWKS, A8), resolve_scope(surface, 공통 필터 → ScopeKeys), get_ro_conn(api_ro, asyncpg, PgBouncer transaction 모드 호환 statement_cache_size=0), build_meta(공통 meta 봉투). 경로 파라미터 job_id 는 UUID 타입으로 받아 형식 오류는 422, 존재·권한·노출 실패는 전부 404 로 통일한다.

답변 드릴다운 모듈은 목록(AN-1 GET /v1/answers)과 상세(AN-2 GET /v1/answers/{job_id}) 두 엔드포인트로 확정한다. 단위 사이 핵심 모순 6가지를 해소했다: (1) 공개 id 를 job_id(uuid)로 통일(현행 /api/scope/answer?jobId= 와 QA 키 계승, answer_key 는 내부 커서 전용), (2) 권한 게이트를 표면별로 분리(AN-2 의 j.geo_key 일괄 게이트는 웹사이트 가상 지역에서 2026-09-04 사고와 같은 전면 차단을 재현하므로 website·project 는 project_key 소속, global 은 project_key + bgrp + geo_key), (3) 브랜드 스코프 누락(AN-2)과 catalog_entry 선계산(AN-1)을 DB 설계의 bgrp = ANY(마스크 목록)로 대체, (4) R04 숨김을 현행 계열 규칙(scope-aggregates.ts:3790-3793)으로 통일하고 R03 은 rd.today_kst()·servable 로 통일, (5) 상세의 언급 브랜드 원천을 원본 뷰 재판정에서 rd.answer_brand(카드와 같은 규칙 버전)로 바꾸고 현행이 서버에서 하던 감성 스팬·스탠스 근거 대조(verifyStanceEvidence)를 포팅 대상으로 추가, (6) source_category[] 를 공통 필터 source[] 로 승격하고 카탈로그 축(funnel 등)을 global 에서 지원으로 승격. DB-v2 에 없는 이름을 확정처럼 쓴 단위는 없었고, 신규 스키마 제안은 rd.dim_source(domain) 인덱스 1건뿐이다(D8 무관). 위험은 상세 low, 목록은 스냅샷 medium이고 기간 1년 + 선택도 낮은 domain/source/mention_brand 조합은 high 라서 페이지당 조회 창 상한(92일)과 RDS 실측 게이트를 둔다.

단위 간 정리
  • [공개 id] AN-1 은 answer_key(int4)를 공개 id 로, AN-2 는 경로 {answer_key} 를 가정했으나 현행 모달·QA 는 전부 job_id 로 라우팅한다(app/api/scope/answer/route.ts:24 jobId 파라미터, app/[locale]/raw-data-qa/answers/[jobId]/page.tsx, app.qa_answer_review PK job_id DB-v2.sql:238). 확정: 경로 GET /v1/answers/{job_id}(UUID), 목록 행의 id = job_id. answer_key 는 순차 정수라 열거 가능하므로 응답에 노출하지 않고 커서 내부에만 쓴다. rd.job.job_id UNIQUE(DB-v2.sql:441)로 점 조회 비용은 같다.
  • [surface 코드] AN-1 은 1·2·3 매핑을 미확정으로 두고 응답에 정수를, AN-2 는 문자열을 냈다. DDL 이 1 global 2 website 3 project 로 확정(DB-v2.sql:12). API 입출력은 문자열 enum 으로 통일, 정수는 SQL 바인드 전용.
  • [R03 노출 게이트] AN-2 가 c.view_date <= current_date 를 썼다(DB 세션 시간대가 UTC 면 KST 자정~09시 사이 하루 어긋남). rd.today_kst()(DB-v2.sql:377, api_ro EXECUTE 허가 :832)로 통일하고 AN-1 처럼 servable 도 포함한다. view_date NULL 은 비노출.
  • [R04 숨김 매핑] AN-1 인용 술어 hidden_scope NOT IN (1,2), AN-2 'citations 이면 인용 섹션만 비움'은 현행과 다르다. 현행은 인용 계열 = 숨긴 회차 전부 제외, 언급 계열 = 'all' 만 제외(lib/db/repositories/scope-aggregates.ts:3790-3793, DB-측정-코어.md §5 회차 게이트 행). 확정: 행 노출 = hidden_scope <> 1, 언급 필드·술어 = hidden_scope NOT IN (1,3), 인용 필드·술어 = hidden_scope = 0. 'mentions'(3) 값은 현행 코드에 대응 분기가 없어 언급 계열 제외로 해석했다(열린 질문으로 확인).
  • [권한 게이트 표면별 분리] AN-2 헤더 게이트가 표면 무관하게 j.geo_key = ANY(scoped_geo_keys)를 걸었다. 웹사이트의 지오 축은 사이트 국가(가상 코드 worldwide·EU 등)인데 답변 geo 는 측정 로케일이라 이 게이트는 웹사이트 답변을 전부 차단한다(현행 route.ts:41-56 주석의 2026-09-04 고객 리포트와 같은 결함). 프로젝트 표면도 계정 region 락을 걸지 않는다(route.ts:36-40). 확정: global = project_key(root) + bgrp = ANY + geo_key = ANY, website = project_key = ANY(스코프 사이트 집합, site_brand_bit·site_geo_key 로 계산), project = project_key = ANY(활성 멤버 프로젝트, scope_all 이면 전체). 계산은 공통 resolve_scope 가 한다.
  • [브랜드 스코프] AN-2 는 브랜드 게이트가 없었고(Kia 전용 계정이 Hyundai 카탈로그 답변을 job_id 로 열 수 있음, 현행 scope-aggregates.ts:7896-7904 는 prompt brand 로 막는다), AN-1 은 catalog_entry 로 brand_prompt_keys 를 선계산했다. DB 설계는 brand[]·own_brand 를 bgrp = ANY(교차 마스크 목록)로 건다(DB-측정-코어.md §5). 확정: 두 단위 모두 bgrp = ANY(:bgrp_values), 스코프 브랜드 ∪ HMG 공통(components/dash/standard-filters.ts:62-64 계승).
  • [country[] 해석] AN-1 은 웹사이트 가상 지역 코드를 geo_key 와 site_geo_key 중 무엇으로 맞출지 미정이었다. 확정: global 은 geo_key = ANY, website 는 dim_project.site_geo_key 로 project_key 집합을 좁히고 가상 브랜드 코드(HYUNDAI-N, lib/scope/website-virtual-geo.ts:23)는 site_brand_bit(bgrp)로 변환. 해석은 filters 모듈 몫.
  • [필터 지원 차이] AN-1 이 funnel·brand_presence·list_type·depth1~3 을 ignored 로 뒀지만, 카드·표에서 드릴다운하면 그 화면 필터가 그대로 넘어와야 목록 모집단이 클릭한 숫자와 맞는다(현행 모달은 URL 필터 전체를 전달, answer-modal.tsx:137-141). 확정: global 에서 지원(filters 모듈이 카탈로그 축 → prompt_key 집합), website·project 에서는 ignored_filters.
  • [source 축 중복] AN-1 extra_params 의 source_category[] 는 공통 필터 source[](URL 키 source, standard-filters.ts:116, spec §4 '인용 계열 기능만')와 같은 축이다. 확정: source[] 를 AN-1 지원 축으로 올리고 source_category[] 는 삭제. AN-2 는 source[] 를 ignored_filters.
  • [project 표면 컨텍스트] AN-1 에 프로젝트 지정 파라미터가 없었다. 확정: surface=project 이면 project_id 필수(없으면 422), 서버가 멤버십 검증 후 project_key 로 변환.
  • [mention_brand 값 공간] AN-1 은 '브랜드 카탈로그 코드'라 했으나 경쟁사는 app.brand 코드가 없다. 현행 드릴다운도 표시명 문자열로 넘긴다(mentions-drilldown.tsx brand prop). 확정: mention_brand = rd.dim_brand_name.name(UNIQUE, DB-v2.sql:403), 서버가 brand_key 로 변환. brand[](관점·모집단)와는 다른 축으로 유지.
  • [signal 당사 판정] AN-1 이 ab.own_bit > 0(전 HMG)을 썼는데 현행 판정 단위는 화면 카드와 같은 당사(관점 브랜드)다(scope-aggregates.ts:7248 주석). 또 계약은 WHERE 비트 식을 금한다. 확정: ab.own_bit = ANY(:own_bits)(own_bit CHECK IN (0,1,2,4), DB-v2.sql:404), own_bits 는 resolve_scope 가 계산. signal 은 언급 계열 게이트를 따른다.
  • [domain 술어 경로] AN-1 은 rd.dim_url.domain 으로 url_key 를 먼저 뽑는다고 했으나 dim_url 에 domain 인덱스가 없다(DB-v2.sql:420-421 은 host·source_key 만). 확정: rd.dim_source.domain → source_key 집합 → c.source_key = ANY(...) 로 cit_source_idx 사용, rd.dim_source(domain) 인덱스를 제안으로 올린다. dim_url.domain 과 dim_source.domain 정규화가 같은지는 열린 질문.

쿼리 설계
2단 조회(파티션 가지치기 확보):
1) 헤더+스코프 게이트(단일 rd.job/rd.cycle, 파티션 없음, PK 조회):
```sql
SELECT j.answer_key, j.job_id, j.surface, j.project_key, j.cyc_key, j.round_date, j.measured_at,
       j.engine_key, j.geo_key, j.lang_key, j.prompt_key, j.status_code, j.analysis_code, j.dropped,
       c.anchor_date, c.view_date, c.hidden_scope
  FROM rd.job j JOIN rd.cycle c ON c.cyc_key = j.cyc_key
 WHERE j.answer_key = :answer_key
   AND j.project_key = ANY(:scoped_project_keys)   -- 권한 교집합(default-deny)
   AND j.geo_key = ANY(:scoped_geo_keys)
   AND c.view_date <= current_date;                 -- R03, 404 로 처리
```
없으면 404(스코프 밖이든 존재하지 않든 동일 응답 — IDOR 방어, 존재 자체를 노출하지 않음).
2) 헤더에서 얻은 (surface, round_date, answer_key) 로 파티션 프루닝된 본표 3종 + 뷰 4종을 병렬 조회:
```sql
-- 프롬프트/카탈로그
SELECT p.text, p.funnel_key, p.kind, ce.brand_bit, ce.presence_key, ce.list_type_key, ce.depth1_key, ce.depth2_key, ce.depth3_key
  FROM rd.dim_prompt p LEFT JOIN rd.catalog_entry ce ON ce.prompt_key = p.prompt_key AND ce.brand_bit = :own_brand_bit
 WHERE p.prompt_key = :prompt_key;

-- 답변 메타(있으면: completed 이고 안 드롭됐을 때만 rd.answer 존재)
SELECT acr_iter_rank, analysis_state, cat_mask
  FROM rd.answer WHERE surface = :surface AND round_date = :round_date AND answer_key = :answer_key;

-- 원문
SELECT answer_text, model_slug, measured_at, analysis_status, status FROM rd.v_answer_body WHERE answer_key = :answer_key;

-- 언급(브랜드·모델)
SELECT ord, entity_id, entity_key, display_name, entity_type, mention_count, avg_position, brand_rollup_entity_id
  FROM rd.v_answer_mention_raw WHERE answer_key = :answer_key ORDER BY mention_count DESC;

-- 문장 단위 감성 발생
SELECT ord, entity_id, turn_index, source_start, source_end, surface_text, sentiment, mention_role, assertion, context_snippet, descriptors, criteria
  FROM rd.v_answer_occurrence WHERE answer_key = :answer_key ORDER BY turn_index, source_start;

-- 스탠스
SELECT turn_index, entity_id, brand_label, stance, confidence, evidence_text, evidence_start, evidence_end, reason
  FROM rd.v_answer_stance_raw WHERE answer_key = :answer_key ORDER BY turn_index;

-- 인용(파티션 프루닝: surface+round_date+answer_key = PK 프리픽스)
SELECT c.ord, u.url, u.title, u.domain, s.category_key, cc.name AS category_name, c.owner_key
  FROM rd.citation c
  LEFT JOIN rd.dim_url u ON u.url_key = c.url_key
  LEFT JOIN rd.dim_source s ON s.source_key = c.source_key
  LEFT JOIN app.citation_category cc ON cc.category_key = s.category_key
 WHERE c.surface = :surface AND c.round_date = :round_date AND c.answer_key = :answer_key
```
