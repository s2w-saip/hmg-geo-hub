AI 퍼널

app/modules/funnel/router.py (제안 경로): APIRouter(prefix="/v1/funnel", tags=["funnel"]). 하위: acr.py(FU-1 핸들러), conversion.py(FU-2 핸들러), schemas.py(Pydantic 응답 모델), repo_acr.py·repo_ga4.py(텍스트 SQL, SQLAlchemy Core + asyncpg), deps.py(모듈 전용 의존성: AcrParams·ConversionParams). 공용 필터·권한·회차 게이트·meta 조립은 공통 모듈 의존성을 주입받아 쓰고 이 모듈에서 다시 만들지 않는다.

AI 퍼널 모듈은 엔드포인트 2개로 확정한다: GET /v1/funnel/acr(FU-1, 위험 medium)과 GET /v1/funnel/conversion(FU-2, 위험 low). FU-2 가 제안한 /v1/funnel/conversion/coverage 는 본 응답의 data.coverage 로 흡수해 없앤다(P4, G-25). 단위 사이 주요 정정은 다섯 갈래다. (1) 비율 표현: FU-2 의 서버 계산 퍼센트를 P3 에 맞춰 {num, den} 정수 쌍으로 바꾸고 FU-1 과 같은 공유 Ratio 모델을 쓴다. (2) FU-1 회차 게이트 오류: hidden_scope<>3 은 all(1) 숨김을 통과시키므로 언급 계열 게이트(NOT IN (1,3), servable, view_date <= rd.today_kst())를 스냅샷·기간 모두에 공용 헬퍼로 적용한다. (3) FU-1 브랜드 좁힘: 카탈로그 비트 세미조인 대신 DB-측정-코어.md:65-66 규칙대로 bgrp = ANY(펼친 마스크 목록)으로 커버링 인덱스 둘째 키를 태운다. 당사 판정은 관점 무시(own_bit<>0)에서 관점 비트 투영((own_bit & :own_bits)<>0)으로 고친다. 현행이 적용 중인 funnel[]·lang[](표준 지면)을 FU-1 이 무시·제한한 것도 지원으로 바로잡는다. (4) FU-2 전환 분자 모순: metrics_rules(is_conv)와 query_design(report 1/2 key_events)이 달라, 분모 = 세션(AI 코호트는 report 2, 비AI 는 report 1), 분자 = report 3 의 is_conv 행으로 통일하고, 속성별 전환 기준(key event 폴백 대 추적 이벤트)을 적재 판정 열로 굳히는 rd.ga4_dim_property.conv_basis 를 제안한다. FU-2 의 성능 전제(ga4_row PK 선두가 prop_key 가 아님)는 DDL 과 달라 기각한다. (5) 빈틈: ACR 측정 대기 문구(countStandardAcrPrompts)와 대시보드 KPI 7번(GA4 전환)이 단위 설계에 없어서, 전자는 totals.catalog_acr_prompts 로, 후자는 대시보드 모듈이 이 모듈 리포지토리 함수를 재사용하도록 넣었다. GA4 시장 카탈로그(속성 없는 시장)와 전환 이벤트 변경 후 is_conv 재투영 경로는 DB-v2 에 없어 제안으로 올린다. D8 위반 제안(캐시·사전 집계)은 두 단위 모두 없었다.

모듈 공통

공통 구성요소
  • 라우터 골격: app/modules/funnel/router.py 에 APIRouter(prefix='/v1/funnel'). 핸들러는 공통 모듈의 CommonFilters(쿼리 파라미터 모델)·AuthScope(서버 계산 스코프, default-deny)·MetaBuilder 를 Depends 로 받는다. 모듈은 필터 파싱·권한 교집합을 다시 구현하지 않는다.
  • 공유 Pydantic 모델 Ratio {num: int, den: int}: 두 단위의 모든 비율(ACR choiceShare·coverage·conversionRate, GA4 ai_conv·human_conv·engine conv·page conv)에 쓴다. 퍼센트·lift(pp)·Δ 는 프론트 계산(P3). den=0 이면 그대로 0 을 보내고 프론트가 '없음' 처리.
  • 공유 응답 봉투 FunnelResponse[T] = {data: T, meta: Meta}. Meta 는 계약 §2 공통 형태(surface, mode, as_of, cycles, generation, ignored_filters, dropped_filters, suppressed). A12 '준비 중' 표현을 모듈 전체에서 하나로 고정: data 는 빈 구조(배열 [], 총량 0), meta.suppressed = [{scope: 'all', reason: 'source_pending'}]. 사용처: website·project 표면 ACR 원천 없음, GA4 활성 속성 0.
  • 공용 헬퍼 brand_masks(bits: int) -> list[int] (Python 순수 함수, 공통 모듈에 없으면 이 모듈이 공통으로 올려 보낸다): 브랜드 비트(1 H, 2 K, 4 G, 8 HMG, 16 N; DB-v2.sql:12)의 모든 조합 1..31 중 (m & bits) <> 0 인 값을 펼쳐 `bgrp = ANY(:masks)` 상수 배열로 쓴다(WHERE 비트식 금지 규약 준수, DB-측정-코어.md:65-66). own_brand X 의 모수 마스크 = brand_masks(X | 8).
  • 공용 회차 게이트(공통 모듈 소유, 이 모듈은 series='mentions' 로 호출): rd.cycle 에서 surface, project_key(global = dim_project.is_root 인 루트), servable, view_date <= rd.today_kst(), hidden_scope NOT IN (1,3) 을 만족하는 cyc_key 목록. 스냅샷 = round_date 최대 1개, 기간 = round_date BETWEEN from AND to 전부. 인덱스 cycle_pick_idx(DB-v2.sql:431) 인덱스 전용 스캔.
  • 카탈로그 축 해석(공통 모듈 소유): funnel·brand_presence·list_type·depth1~3 를 rd.catalog_entry 에서 '한 행이 모든 선택 축 만족' prompt_key 집합으로 먼저 풀고, 1,000 이하면 prompt_key = ANY(:keys), 초과면 semi-join(DB-측정-코어.md:68). ACR 은 이 결과를 acr_cell.prompt_key 에 건다. GA4 는 이 축들을 ignored_filters 로.
  • 일관 읽기 헬퍼 read_tx(): 한 요청의 여러 문장(ACR 6문장, GA4 4~5문장)을 한 커넥션의 READ ONLY REPEATABLE READ 트랜잭션 안에서 순차 실행해 적재 중간 상태가 섞이지 않게 한다. PgBouncer transaction 모드와 호환(트랜잭션 단위 고정), prepared statement 캐시 끔(계약 §5). 병렬 커넥션 분할은 쓰지 않는다(스냅샷 불일치 위험).
  • ACR 공용 셀 선택 SQL 조각 acr_cells_cte(params): WITH cells AS MATERIALIZED (SELECT acr_cell_key, round_date, cyc_key, prompt_key, engine_key, geo_key, valid_acr FROM rd.acr_cell WHERE surface = :s AND bgrp = ANY(:masks) AND cyc_key = ANY(:cyc_keys) [AND round_date BETWEEN :lo AND :hi] AND acr_in AND engine_key = ANY(:engine_keys) [AND geo_key = ANY(:geo_keys)] [AND lang_key = ANY(:lang_keys)] [AND prompt_key = ANY(:catalog_keys)]). 모든 ACR 문장이 이 조각을 머리에 둔다(중복 SQL 금지). 스냅샷은 acr_cell_cyc_cov, 기간은 acr_cell_round_cov 를 탄다.
  • ACR 브랜드 레벨 조인 규약: rd.acr_choice 를 부모로 두고 level = 1(브랜드)·2(차종) 조건으로 파티션 가지치기, PK (level, acr_cell_key, entity_key) INCLUDE 로 인덱스 전용 스캔. 브랜드 계열 전 구획에 keep 을 건다. 당사 판정은 SELECT 투영 bool_or((own_bit & :own_bits) <> 0) (WHERE 아님). 표시명은 rd.dim_brand_name.name(브랜드), rd.dim_entity.rep_name(차종).
  • GA4 공용 속성 해석 resolve_ga4_props(scope, filters): rd.ga4_dim_property(수십 행)에서 brand_bit = ANY(:bits) AND geo_key = ANY(:geos) 로 시장을 고르고 status 별로 분류. active 만 prop_key 배열로 쿼리에 넘기고, 나머지는 coverage 에만. app.ga4_property 는 읽지 않는다(A17: 기능 API 는 rd 투영).
  • GA4 행 역할 규칙(모듈 내 단일 정의, 적재 설계 확인 필요): 세션 분모 = event_key = 0 인 traffic 행. AI 코호트 세션 = report 2(traffic_ai, engine_key 보유), 비AI 세션 = report 1(traffic_total) 의 NOT is_ai 행. 전환 분자 = report 3(events) 의 is_conv 행에서 conv_basis(제안 열)에 따라 key_events 또는 event_count 합. 페이지 = report 4(landing). 이 규칙은 conversion_summary()·conversion_detail() 두 리포지토리 함수가 공유한다.
  • 리포지토리 함수 conversion_summary(props, from, to, filters) 공개: 대시보드 모듈의 KPI 7번(현행 live.ts:397-417 getAiTrafficConversionKpi·Rollup·getAiVisitsKpi)이 같은 SQL 을 재사용한다. 대시보드는 자기 기간(현행 28일)을 from/to 로 명시해 넘긴다.
  • extra_params 상한 검증(Pydantic Field): top_brands 기본 12(1..50), trend_series 기본 5(1..10), battle_limit 기본 200(1..500), territory_limit 기본 12(1..24), model_limit 기본 12(1..50), trend_cycles 기본 null(전 게이트 회차, 1..104), page_limit 기본 15(1..50), device[] (mobile|desktop|tablet), visitor_type[] (new|returning). 현행 상수 근거: scope-aggregates.ts:9373·9393·9503·9523·9584, conversion.ts:381·725.
단위 간 정리
  • [P3 위반] FU-2 응답이 ai_conv_rate(%)·human_conv_rate(%)·lift(pp)·conv_rate 를 서버에서 나눈 값으로 준다. FU-1 과 같은 공유 Ratio {num, den} 로 바꾸고 lift 는 프론트가 두 비율 차로 계산한다.
  • [중복 제거] FU-2 의 visits 블록은 summary·trend·pages 와 같은 값을 다시 싣는다. 제거하고 AI 방문수 = summary.ai.sessions, 추이 = trend[].ai_sessions, 페이지 방문 = pages[].ai_sessions 로 흡수한다(현행 getAiVisitsLive conversion.ts:766-792 의 totals·pages·trend 대응). ai_users_window_sum_disclaimer 문자열 필드는 데이터가 아니라서 삭제(G-12 로 사용자 수 자체를 안 준다). 현행 visits 의 screenPageViews 는 summary.ai.page_views 로 보존.
  • [엔드포인트 축소] FU-2 의 /v1/funnel/conversion/coverage 는 같은 화면·같은 속성 해석을 쓰므로 data.coverage 로 흡수하고 삭제(P4, G-25 화면당 호출 수).
  • [형태 분기 정리] 현행은 country-leaf(1국)이면 getAiConversionLive, 다국가면 getAiTrafficConversionRollup 로 갈렸다(conversion/page.tsx:53, conversion.ts:507·628). 신: 단일 엔드포인트가 항상 active 속성 집합을 SQL 하나로 합산하고, 매칭 속성이 2개 이상이면 by_country 를 채우며 1개면 null. 추이·엔진·페이지는 다국가에서도 합산해 준다(현행 대비 기능 확장, 명시).
  • [분자 정의 모순] FU-2 metrics_rules 는 is_conv 로, query_design 은 report 1/2 의 SUM(key_events) 로 전환을 센다. 모듈 규칙: 분자 = report 3 is_conv 행의 conv_basis 별 합(제안 1), 분모 = 세션(AI 는 report 2, 비AI 는 report 1 NOT is_ai). report 1 의 AI 행에는 source 가 없어 engine 필터를 걸 수 없으므로 AI 세션은 항상 report 2 에서 읽는다(적재 불변식 Σreport2 = report1 AI 행, DB-v2.sql:693).
  • [SQL 오류] FU-2 page_split 는 GROUP BY page_key, is_ai 뒤 ORDER BY SUM(sessions) FILTER (WHERE is_ai) 로 잘라 비AI 행이 다른 순위로 잘린다. GROUP BY page_key 하나에 FILTER 집계(ai_sessions, human_sessions, ai_conv, human_conv)로 고치고 AI 세션 내림차순 page_limit 절단.
  • [성능 전제 오류] FU-2 는 rd.ga4_row PK 선두가 prop_key 가 아니라고 했으나 DDL 은 PRIMARY KEY (prop_key, report, date, ...)(DB-v2.sql:691). PK 순서 변경·(prop_key, date) 보조 인덱스 제안을 기각한다.
  • [engine 축] FU-2 는 engine 을 별도 extra_param 으로 두자고 했으나 현행 parseConversionFilters 가 공용 URL 파라미터 engine 을 그대로 쓴다(conversion.ts:196-202). 공용 engine[] 로 지원하고 의미를 'AI 유입 sessionSource 엔진'으로 문서화한다. engine_key 는 rd.dim_engine.code 로 해석하고 GA4 매핑 없는 코드는 meta.ignored_filters 에 값 단위로 적는다. 빈 값 = 전 AI 엔진(측정 엔진이 아니므로 dflt 규칙 미적용). device·visitor_type 만 extra_params(DB-ACR-외부-데이터.md:50).
  • [속성 해석 경로] FU-2 는 brand[]·country[] 를 app.ga4_property.brand_code·country_code 로 대조한다. rd.ga4_dim_property(brand_bit, geo_key, status) 로 바꾼다(A17).
  • [기본 기간 누락] FU-2 는 from/to 미지정 동작이 없다. 미지정 = 최근 90일(G-12, conversion-window.ts:7). 현행 dateNDaysAgo 는 '{N}daysAgo'~'today'(client.ts:70-73: N+1일, 당일 부분 포함)이므로 신은 to = 선택 속성 최신 적재일, from = to - 89 로 정하고 parity 노트에 차이를 적는다. mode 는 항상 'cumulative', cycles = [], generation = null(GA4 는 Scope 세대와 무관), as_of = 최신 적재일.
  • [회차 게이트 오류] FU-1 스냅샷 서브쿼리의 hidden_scope<>3 은 1(all) 숨김 회차를 통과시킨다(rd.cycle 코드 0 없음 1 all 2 citations 3 mentions, DB-v2.sql:429). G-11 'mentions 숨김' = hidden_scope NOT IN (1,3). view_date 비교는 current_date 가 아니라 rd.today_kst()(DB-v2.sql:377). FU-1 기간 모드에는 게이트가 아예 없어 같은 게이트를 cyc_key = ANY(:allowed) 로 건다. 공용 회차 게이트 헬퍼로 일원화.
  • [브랜드 좁힘 방식] FU-1 은 own_brand 를 catalog_entry 세미조인 안의 brand_bit & :own_mask 로 걸어 규약 위반 소지를 스스로 적었다. DB-측정-코어.md:65-66 규칙대로 bgrp = ANY(brand_masks(X | 8)) 로 바꾼다(global 에서 bgrp = cat_mask). brand[] 도 같은 방식(교차 마스크). 커버링 인덱스 둘째 키를 타므로 FU-1 의 열린 질문 1 과 성능 저하 우려가 함께 해소된다.
  • [당사 판정] FU-1 은 is_ours = own_bit<>0 으로 관점을 무시한다. 현행 acrIsOurs 는 관점별 tracked 집합으로 판정한다(scope-aggregates.ts:9323-9325). SELECT 투영 bool_or((own_bit & :own_bits) <> 0) 로 바꾼다(HMG 관점 own_bits = 7, dim_brand_name.own_bit 는 0·1·2·4, DB-v2.sql:404).

  • 결정 G-12(a) 채택 반영: 분모가 activeUsers(현행) → sessions(신규) 로 바뀐다. 이유: users_day 는 행(채널·기기·신규재방문·페이지·이벤트 조합) 사이에서 합산 불가(GA4 사용자 중복 계산 위험, DDL 주석 'users_day 는 행 사이로 합하지 않는다 — API 규약, lens1 m9') 인 반면 sessions 는 가산 가능. 이것은 A13 의 5단계 변경 게이트 대상 정의 변경이다 — 신구 대조 하네스는 이 차이를 '결정된 정의 변경'으로 설명해야 통과(계약 §2 정합성 기준).
  • AI 코호트 판정: rd.ga4_row.is_ai (channel_group='AI Assistant', ingest 시점 판정 — P1 준수, 조회 시 문자열 비교 없음).
  • 전환 판정: rd.ga4_row.is_conv (추적 이벤트 지정 시 그 이벤트, 아니면 GA4 key events 폴백 — 이 선택도 적재 시점에 결정. 현행 resolveConvSpec 의 '속성별 등록 이벤트 있으면 그것, 없으면 key events' 로직이 ingest 로 이동). API 는 is_conv=true 행만 분자에 합산하면 된다 — 속성별 분기(ConvSpec 유무) 를 쿼리에서 다시 판단하지 않는다.
  • human 코호트 = total(report=1, is_ai 무관 전체) − ai(is_ai=true) — 현재도 같은 차분 방식(lift=aiRate−humanRate, pp).
  • engine 별 분해는 report=2(traffic_ai) 사용(1:1 그레인이면서 이미 AI 코호트로 좁혀진 표, engine_key 보유) — report=1 을 engine 으로 다시 나누지 않는다(적재 불변식: Σreport2.sessions(date,device,nvr)=report1 AI행.sessions).
  • AI 유입 방문수(volume) 는 별도 지표 렌즈(RATE 아님) — sessions 합계 그대로(현행 getAiVisitsLive 와 동일 정의, D8 예외 아님, 원본 그레인 합산일 뿐).

성능(10배)
현재 1개 속성 기준 파티션(≤90일) 내 수천~수만 행. 41개 속성 전체 active 매핑 시나리오에서도 GROUP BY 단일 쿼리라 수십만 행 이내로 추정(실측 없음, '제안' 수준 추정치).
인덱스: rd.ga4_row PK (prop_key, report, date, channel_key, source_key, device_key, nvr_key, page_key, event_key) — RANGE(date) 파티션과 결합해 date 범위 가지치기 필요, but 리프 스캔 시 prop_key 가 PK 선두가 아니라 파티션 내부에서 (report,date) 순 정렬만 보장 — property 단위 필터는 리프 내 인덱스 스캔이 아니라 prop_key 조건의 selectivity 에 의존. 제안: PK 순서를 (date, prop_key, report, ...) 로 바꾸거나 (prop_key, date) 부분 인덱스 추가 — 현재 PK 만으로는 '특정 속성 90일' 질의가 파티션 리프 전체를 스캔할 위험(로더 설계자·통합자 확인 필요, 이 설계 문서에서 인덱스 추가를 제안만 해둔다), app.ga4_property (brand_code, country_code) — PK 는 property_id 단독이라 브랜드×국가 역방향 조회(scope→property 목록)에 인덱스 없음. 제안: UNIQUE(brand_code, country_code) 또는 covering index — 시장 수가 41개(현행 실측) 규모라 low 리스크지만 향후 브랜드 확장 시 문제될 수 있어 표시만 해둔다.
폭 10배 기준이 이 도메인엔 원천적으로 안 맞는다 — GA4 데이터는 Scope 측정과 무관하게 구글이 발생시키는 실제 트래픽이므로 '프롬프트·URL·브랜드 키 10배'가 아니라 '속성 수(현재 1개 Kia/IT, 카탈로그 시장 41개) × 90일 범위의 세션 볼륨'이 규모 변수. 현재 관측 규모(Kia/IT 실측 수치는 코드 주석 근거)로는 하루 세션 두 자릿수~세 자릿수라 rd.ga4_row 행수는 파티션당(90일×5 report×수십 차원조합) 최대 수만 행 추정 — 현재 스케일에서는 low. 다만 41개 시장 전부가 active 매핑되면(현재 1개→41개, 41배) 단일 쿼리가 41개 속성을 GROUP BY 하는 형태(신 설계는 SQL 하나로 전 시장 SUM 이라 41개 병렬 API 호출이던 현행보다 오히려 유리) — 이 경우도 인덱스 문제(위 제안)가 없으면 low~medium.
신구 대조
"신구 대조 하네스 F01~F07 키에 GA4 전용 항목이 없어(현재 하네스는 Scope 측정 계열 위주로 보임 — 확인 필요) 이 단위는 새 항목을 제안한다: F-GA4-1(KPI aiConvRate/humanConvRate/lift, 분자·분모 포함), F-GA4-2(추이 일별 시계열), F-GA4-3(엔진별 breakdown), F-GA4-4(페이지별 표), F-GA4-5(국가별 rollup, 다국가 선택 시). 다만 metrics_rules 의 분모 변경(activeUsers→sessions)으로 신구 값이 정의상 다르게 나오는 게 정상이므로, 하네스는 '차이가 결정된 정의 변경(G-12a)으로 설명됨'을 확인하는 쪽으로 판정 기준을 잡아야 한다(단순 수치 일치 비교 불가). 페이지별·엔진별 표는 목록 자체(URL 집합, 엔진 집합)의 일치만 먼저 확인하고 rate 값은 재계산."
열린 질문
  • is_conv 판정 매커니즘이 report=3(events)·report=4(landing) 중 어디에 실리는지, 그리고 report=1/2(traffic)의 key_events 컬럼과의 관계가 DDL 주석만으로는 확정 안 됨. 현행 코드(resolveConvSpec)는 '속성별 등록 이벤트 있으면 eventName 매치, 없으면 keyEvents 폴백'인데 이걸 ingest 가 어느 report 행에 반영하는지(report=1의 key_events 를 그대로 쓰는지, report=3/4 의 is_conv 플래그된 행만 쓰는지) 로더 설계 문서가 없어 미확인. 쿼리 스케치는 최선 추정이며 로더 담당 설계자 확인 필요.
  • engine_key 가 rd.dim_engine(FK 미선언, DDL:688-689)과 같은 코드 공간을 공유하는지, 아니면 rd.ga4_dim_value(kind='source')로 별도 관리되는지 불명확. 공용 필터 engine[] 재사용 여부가 여기 달려 있음(제안: 공유 안 함 — GA4 sessionSource 값(chatgpt.com 등)과 LLM engine 코드(chatgpt 등)는 이름은 겹쳐도 서로 다른 분류축).
  • rollup(다국가 합산, 현행 getAiTrafficConversionRollup)을 메인 엔드포인트 응답에 흡수할지, 별도 엔드포인트로 뺄지 — 공용 계약에 이 축을 위한 명시 규칙이 없다. 제안: brand[]/country[] 가 복수 매치되면 응답이 자동으로 byCountry 배열을 채우는 방식(엔드포인트 분리 없이 필터 결과에 따라 형태가 달라짐) — API 설계 단순화와 P4('기능=엔드포인트=쿼리 하나') 사이 긴장, 통합자 판단 필요.
  • coverage(측정대기 시장 수) 를 별도 엔드포인트로 뺄지 meta 로 흡수할지 — /v1/funnel/conversion/coverage 는 제안일 뿐, 다른 필터 모듈(GET /v1/filters/options)이 이미 비슷한 정보를 낼 수도 있어 중복 우려.
  • GA4 pull 주기(A10 의 'Scope API 20분 pull'이 GA4 에도 적용되는지, 별도 주기인지)가 계약서에 명시 안 됨 — API 응답의 meta.as_of(신선도 표시) 값을 이 주기에 맞춰야 하는데 근거 문서가 없음. GA4 는 계약상 'Scope 와 무관한 별도 계열'이라 적재 트랜잭션 경계(A10)가 그대로 적용되는지 불확실.
  • device/visitor_type/engine 세 축을 공용 필터 모델 밖 extra_params 로 둔 것이 맞는지 — 계약 §2 공용 필터 모델에 없는 축이라 P5('지원 축 외엔 조용히 무시 금지')를 지키려면 meta.ignored_filters 대신 정식 문서화된 extra_params 로 취급해야 하는데, 이 처리 방식 자체가 계약에 선례가 없어 통합자 확인 필요.

쿼리 설계
"CTE ai_total AS (SELECT date, SUM(sessions) sess, SUM(key_events) conv FROM rd.ga4_row WHERE prop_key = ANY($props) AND report=1 AND date BETWEEN $from AND $to AND is_ai GROUP BY date), human_total AS (같은 조건 NOT is_ai), engine_split AS (SELECT engine_key, SUM(sessions) sess, SUM(key_events) conv FROM rd.ga4_row WHERE prop_key=ANY($props) AND report=2 AND date BETWEEN $from AND $to [AND engine_key = ANY($engineKeys)] GROUP BY engine_key), page_split AS (SELECT page_key, is_ai, SUM(sessions) sess, SUM(key_events) conv FROM rd.ga4_row WHERE prop_key=ANY($props) AND report=4 AND date BETWEEN $from AND $to GROUP BY page_key, is_ai ORDER BY SUM(sessions) FILTER (WHERE is_ai) DESC LIMIT $limit_pages), by_country AS (다국가 선택 시: 위 ai_total/human_total 을 prop_key 대신 (brand_bit, geo_key) 로 GROUP BY, rd.ga4_dim_property 조인). 모든 CTE 는 WHERE report=N·date 범위·prop_key IN(스코프 교집합에서 미리 resolve) 조건으로 파티션 가지치기(RANGE date)+리프 내 조건. device/visitor_type/engine 필터는 각각 device_key/nvr_key/(engine_key 또는 source_key) 조건 추가. is_conv 정의가 확정되면(open_questions) key_events 를 일반화된 conv_count 로 교체."
