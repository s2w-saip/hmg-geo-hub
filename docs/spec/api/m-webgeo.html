웹 크롤·SEO(제거)

단위 상세

WG-1 웹 크롤·SEO (webgeo/crawl) — 소비자 없음, 신규 API 설계 대상 아님 n/a

crawl_pages·crawl_links·webgeo_*(webgeo_sites, webgeo_pages, webgeo_page_seo, webgeo_raw_html_objects 등) 테이블을 읽는 화면이나 배치가 현재 앱에 없다. 10-feature-trace.tsv 전행에 webgeo/crawl 관련 행이 0건이고, 리서치 프리뷰 리포 전체 git grep(webgeo, crawl_pages, crawl_links)에서 실제 소비(라우트·쿼리·컴포넌트)는 0건 — 나온 것은 drizzle 드리프트 감시 스크립트의 제외 주석과 무관한 정적 카탈로그(webgeo_final_list.xlsx, lib/geo-catalog/)뿐이다. drift-sql.ts 자체가 "이 앱의 읽기 경로가 쓰지 않고 별도 파이프라인이 소유한다"고 명시하고, DB 설계 v2 결정 G-13 은 "crawl_* 참조가 0건" 임을 확인한 뒤 폐기는 보류(용도 미확인)하고 crawl 은 S3 보관·webgeo 는 ext 스키마로 정적 이관만 하기로 했다(DECISIONS.md:228-240). 계약서 §3 도 이 방향과 일치한다: rd 스키마(기능 API 읽기 대상)에 webgeo_*·crawl_* 표가 아예 없고 ext 절 주석에 "정적 이관"으로만 적혀 있다(DB-v2.sql:741). 결론: WG-1 은 현재 범위에서 API 로 노출할 기능이 없다 — "쓰는 곳이 없으면 그렇게 보고한다"는 지시에 따라 엔드포인트를 설계하지 않는다.

해당없음 (엔드포인트 없음)
인덱스:
설계 대상 API 가 없어 성능 산정 불필요. 다만 해당 표들이 라이브 DB 에서 이미 대형(crawl_links 는 인덱스 crawl_links_src_link_unique 982MB 가 4/5 미사용 상태로 관찰됨, 03-db-live-catalog.md:100,112)이라, 훗날 실제 소비자가 나타나 API 를 신설할 경우 이 부채(미사용 인덱스·라지 테이블)부터 별도로 정리해야 한다는 점만 기록해 둔다.
신구 대조
해당없음 — 신규 API 가 없으므로 하네스 기능 F01~F07 어디에도 이 단위에 대응하는 항목이 없다(F01~F07 자체가 webgeo/crawl 을 다루지 않음, 10-feature-trace.tsv 근거). 새 대조 항목도 추가하지 않는다 — 대조할 신구 화면 쌍이 없다.
열린 질문
  • WG-1 을 아예 이관 단위로 유지할 필요가 있는가: 확인된 소비자가 0건이므로 이 API 설계 단위 자체를 취소하고 모듈 지도에서 제거하는 편이 맞는지 설계 리드 확인 필요.
  • webgeo_*·crawl_* 를 실제로 쓰는 '별도 파이프라인'(drift-sql.ts:44 가 언급)이 무엇인지 리포 밖(다른 서비스·배치)에 있는지 확인이 안 됐다 — 확인되면 그 파이프라인 쪽 이관 계획(스키마·인증)이 별도로 필요할 수 있다.
  • G-13 은 '용도 미확인이라 폐기 금지'로 crawl_* 를 S3 로만 보관하기로 했는데, 이관 후에도 아무도 안 쓰면 그 데이터를 다시 조회할 계획이 있는지(있다면 그게 WG-1 의 진짜 범위가 될 수 있음) 사용자 확인이 필요하다.
  • webgeo_pages 의 raw_html_path FK 가 인덱스 없음으로 관찰됐다(03-db-live-catalog.md:163) — 이관·아카이브 작업(적재 모듈 소관) 시점에만 문제이며 이 API 설계 범위 밖이지만, 적재 모듈 담당자에게 전달이 필요한지 확인.
