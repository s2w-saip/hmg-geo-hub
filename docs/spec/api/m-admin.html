관리자

/v1/admin (APIRouter, 모듈 공통 의존성 require_admin; 하위 라우터 catalog·interest·entities·citation-overrides·cycles·jobs·users·changes)

관리자 모듈 결론: 단위 5개를 /v1/admin 라우터 하나로 묶고, 모든 쓰기를 "app 원본 쓰기 + 명시적 감사 + app.judgment_change 요청(비동기 반영)" 한 패턴으로 통일했다. 단위 설계에서 계약·결정 위반 4건을 고쳤다. (1) AD-1 의 Scope 동기 PATCH 는 계약 §5 위반이라 app.scope_outbox 적재로 바꿨다. (2) AD-1 이 judgment_change('catalog'/'prompt_kind')를 선택사항으로 둔 빈틈을 필수로 바꿨다. DB-v2.sql 에는 tg_catalog_change 트리거 본문이 없고(주석뿐, DB-v2.sql:155-156) rd.catalog_entry 는 적재기만 쓰기 때문이다(B4). (3) AD-2 의 엔티티별 전 기간 rd.answer_stance 집계와 새 인덱스 제안은 G-23 (a)·G-18 (a) 위반이라, 기간을 필수로 하고 수치를 표시 브랜드 단위(rd.answer_brand)로 재정의했다. (4) AD-2·AD-3 의 access_audit_log 'data_access' 쓰기는 AU-1 미결 표를 선점하는 것이라 뺐고, judgment_change(append-only, api_rw UPDATE·DELETE 회수)를 변경 원장으로 쓴다. AD-4 는 단위 설계가 비어 있어("test") 여기서 새로 설계했다. 현행에는 화면이 없고 운영자 스크립트(scripts/summary/hide-cycle.ts)와 0054 드롭 SQL 만 있으므로, judgment_change 의 cycle_admin·anchor_pin·answer_drop 요청 API 로 설계했다. 공통 구성요소는 require_admin(활성 admin 만 통과), rw_tx(set_config 로 app.actor_id 설정), enqueue_change, 관리 창 해석기(기본 = 최신 노출 회차, 1회차 초과는 admin_long, 366일 초과는 422), 통일 봉투(meta.next_cursor), 변경 큐 조회 API 다. 위험 high 는 AD-2 목록의 1년 창 한 곳이다. medium 은 AD-3 후보, AD-4 회차 상세, AD-1 드리프트 카운트 세 곳이다. 이 밖에 두 가지를 발견했다. 현행 /admin/ga4 와 /admin/keyword-tools 가 어느 단위에도 배정되지 않았다. DB-v2 에 없는 투영 열 2개(rd.dim_project.regions, rd.cycle.hidden_reason)와 적재 롤 GRANT 부족(scope_outbox 처리 주체 없음)도 확인했다.

모듈 공통

공통 구성요소
  • 라우터 구조: app/modules/admin/__init__.py 에 router = APIRouter(prefix="/v1/admin", tags=["admin"], dependencies=[Depends(require_admin)]). 하위 모듈 catalog.py(AD-1), interest.py(AD-1b), entities.py(AD-2), citation_overrides.py(AD-3), cycles.py·jobs.py(AD-4), users.py(AD-5), changes.py(공통). 정적 경로(/prompts/export, /prompts/bulk/*, /prompts/import/preview)는 파라미터 경로보다 먼저 선언하고 prompt_id 는 UUID 타입으로 받아 충돌을 막는다. 경로 스타일은 하위 리소스형으로 통일한다(단위 설계의 ':bulk-apply'·':export' 콜론형 폐기).
  • 의존성 require_admin(): Supabase JWT 를 JWKS 로 검증(A8)한 뒤 app.user_account 를 user_id 로 조회해 role='admin' AND status='active' 가 아니면 403. 현행 canAccessAdmin(lib/auth/scope-policy.ts:48)은 role 만 보지만 DB-v2 에 status(suspended)가 생겨 정지 계정 차단을 추가한다. 반환 AdminPrincipal{user_id, email, role}.
  • 의존성 rw_tx(principal): api_rw 풀에서 커넥션을 받아 BEGIN 후 SELECT set_config('app.actor_id', :uid, true) 와 SET LOCAL statement_timeout='30s' 를 실행한다. SET LOCAL 은 바인드 파라미터를 못 받으므로 set_config 를 쓴다. PgBouncer transaction 모드에서도 트랜잭션 범위라 안전하다. asyncpg statement_cache_size=0.
  • 의존성 ro_conn / admin_window(surface, from, to, family): 관리 창 해석기. from/to 생략 시 rd.cycle(cycle_pick_idx)에서 surface 의 최신 노출 회차(servable AND view_date <= rd.today_kst() AND hidden_scope 가 해당 계열을 가리지 않음) round_date 1개로 채운다(G-18 a). 창이 회차 1개를 넘으면 admin_long 풀(statement_timeout 30s)로 바꾸고, to-from > 366일이면 422 window_too_large. 결과 AdminWindow{surface_key, from, to, pool, default_applied}. AD-2·AD-3 이 공유한다.
  • 공유 리포지토리 enqueue_change(tx, kind, subject_uuids, subject_texts, payload) → change_id: app.judgment_change INSERT(requested_by = app.actor()). payload 에 항상 {op, old, new} 를 담아 judgment_change 를 변경 원장으로 쓴다(api_rw 는 UPDATE·DELETE 회수, DB-v2.sql 롤 절 4). 같은 subject 에 대기 중(pending·running) 요청이 있으면 409 duplicate_pending 을 낸다(judgment_change_open_idx 부분 인덱스 범위 안 조회).
  • 공유 리포지토리 audited_catalog_write(tx, prompt_id, event_type, patch, changes, batch_id): 현행 applyAuditedCatalogChange(lib/db/repositories/prompt-audit-logs.ts:198)의 가드 규칙(restore 는 deleted_at IS NOT NULL, 그 외 IS NULL, 0행이면 롤백)을 그대로 옮긴다. 그리고 ① prompt_audit_log INSERT ② 판정 입력 변경(brand_code·funnel_stage·taxonomy·kind·deleted_at·scope_prompt_id) 시 enqueue_change('catalog' 또는 'prompt_kind') ③ Scope 노출 필드 변경 시 app.scope_outbox INSERT 를 한 트랜잭션에서 한다. DB-v2 에는 트리거가 없으므로 앱이 명시적으로 쓴다(consistency_fixes 참고).
  • 공유 리포지토리 audited_user_write(tx, op, before, after): app.user_account 쓰기와 app.permission_audit_log(before/after to_jsonb 스냅샷) INSERT 를 같은 트랜잭션에서 하고, row_version + 1 과 updated_at 을 앱이 설정한다. 스코프 값 검증(scope_brands ⊂ app.brand, scope_regions ⊂ app.rhq_region)도 앱이 SELECT 로 한다. DB-v2 에는 tg_user_scope_validate·tg_user_permission_audit 가 없다.
  • 쓰기 전 rd 검증 규약: api_rw 는 rd USAGE 가 없다(DB-v2-roles.sql:45-50). 그래서 rd 참조가 필요한 쓰기(AD-2 엔티티 존재·rep_name, AD-4 cyc_key→cycle_id·job_id 존재)는 ro_conn 으로 먼저 읽고 api_rw 트랜잭션에서 app 만 쓴다. 최종 정합성은 적재기가 claim 시 다시 검증한다.
  • Pydantic 공통 모델: AdminEnvelope[T]{data: T, meta: AdminMeta}. AdminMeta{next_cursor: str|None, ignored_filters: list[str], dropped_filters: dict, surface: str|None, as_of: {from,to}|None, generation: int|None, default_window: bool|None}. 단위별 meta.cursor(AD-1)·meta.next_cursor(AD-2·AD-5)·next_cursor(AD-3)를 meta.next_cursor 하나로 통일한다. 계약 공통 meta 중 mode·cycles·suppressed 는 관리 API 에서 생략한다. generation 은 rd.surface_generation.generation 이라, 비동기 반영이 끝났는지 화면이 판별하는 신호로 쓴다.
  • Pydantic 쓰기 응답: WriteAccepted{change_id: int|None, propagation: 'pending'|'none', subject}. 동기 app 쓰기만 있는 경우(AD-5, AD-1b)는 propagation='none'. 오류 바디 ErrorBody{error:{code, message, details}}. 코드: forbidden(403), not_found(404), conflict(409: last_admin·self_demote·row_version·duplicate_pending·state_mismatch), unprocessable(422: CHECK 위반은 제약명 매핑, window_too_large, out_of_vocabulary), upstream_auth(502: Supabase Admin API 실패).
  • 키셋 커서 코덱: base64url(JSON 정렬키 튜플). 서버가 limit+1 을 조회해 다음 페이지 존재를 판정한다. 정렬 키는 엔드포인트별로 고정하고 커서에 정렬 키 이름을 담아, 정렬이 바뀐 커서 재사용을 422 로 막는다.
  • 공통 필터 처리: 관리 API 는 공통 필터 모델을 쓰되 권한 교집합을 적용하지 않는다(관리자는 전량, 현행 listStandardCatalog 주석과 동일). 지원하지 않는 축은 meta.ignored_filters 로 돌려준다. surface·from/to 는 AD-2·AD-3·AD-4 에서 지원한다. brand[]·funnel[]·brand_presence[]·list_type[]·depth1~3[] 는 AD-1 목록에서 app.prompt 열 = ANY(:arr) 로 지원한다.
단위 간 정리

AD-3 인용 출처 오버라이드 medium

인덱스: app.user_account 는 PRIMARY KEY(user_id) 뿐 별도 인덱스 DDL에 없음 — 목록 검색(email ILIKE)·필터(role/operator/status)용 인덱스가 DDL 에 없다. 제안: idx_user_account_role(role), idx_user_account_status(status), 필요 시 email 은 citext UNIQUE 라 이미 등가검색은 빠름(ILIKE prefix 검색용 pg_trgm GIN 은 규모가 작아 불필요할 수 있음)., app.permission_audit_log 는 PRIMARY KEY(audit_id) 뿐, target_user_id 조회 인덱스 없음 — GET /users/{id}/audit 용 idx_permission_audit_target(target_user_id, created_at DESC) 제안.
이 API 군은 rd 스키마(측정 사실 표)를 전혀 읽지 않는다 — 파티션·round_date·surface 가지치기 대상이 아니다. app.user_account 는 회사 전체 계정 수 규모(수백~수천 행 추정, 폭 10배를 적용할 대상이 아니다 — 계정 수는 프롬프트·URL·브랜드 키처럼 수집 규모에 비례하지 않는다). 목록 조회는 풀스캔~인덱스 스캔 수준이라 규모와 무관하게 저위험.
신구 대조
"하네스 F01~F07 키에 AD-5 상당 기능이 없다(계정 관리는 화면 측정값이 아니라 CRUD라 F-key 대상 밖). 신규 대조 항목 제안: PA-1(목록 총 계정 수·role별 분포 신구 일치), PA-2(임의 계정 10건 role/scope/operator 값 바이트 단위 일치), PA-3(마지막 admin 보호·자기삭제 금지·vendor operator 금지 3개 가드 각각 재현 테스트로 거부 코드 일치). 신규 컬럼(row_version·menu_groups 실사용·is_qa_reviewer)은 구버전에 대응값이 없어 대조 불가 — 신규 기능으로 별도 표시."
열린 질문
  • reset-password 엔드포인트는 현행 UI/서버 액션에 없다(create 시 1회성 임시 비밀번호뿐). 신규 요구인지, 이관 범위 밖인지 확인 필요 — 있으면 Supabase Admin API adminUpdateUser(password) 로 구현.
  • app.access_audit_log(kind IN scope_call·data_access·api_read·download) 의 쓰기 주체가 DDL 주석상 미정(§3 '알려진 미결', AU-1 별도 설계)이다. AD-5 는 이 표를 읽기만 하는데(계정 활동 로그 화면이 필요하면), 쓰기 설계가 끝나기 전엔 이 표에 실데이터가 없을 수 있다 — AD-1(인용 큐레이션)과 함께 AU-1 결과를 기다려야 한다.
  • menu_groups 편집 UI가 현행에 없다(스키마·세션 판정 로직만 존재, DB migration 0039 이후 미노출). 새 설계에서 PATCH 에 포함시키는 것이 맞는지, 아니면 이번 이관 범위 밖(향후 기능)인지 확인 필요 — 일단 endpoint 는 넣고 표시했다.
  • project_member(초대·역할·수락) 관리는 이 API 군(AD-5)에 넣지 않고 프로젝트 모듈(/v1/projects/{id}/members)로 넘겼다 — 경계가 맞는지 설계 리드 확인 필요. app.member_audit_log 도 그쪽 소관으로 간주.
  • is_qa_reviewer(app.user_account 신규 컬럼, 현행 profiles 에 없음)의 부여 권한자·UI 위치가 불명 — QA 콘솔(AD 밖)과 겹칠 수 있어 명시 확인 필요.
  • row_version(app.user_account, DDL 신규 컬럼) 을 PATCH 응답에 낙관적 락으로 노출할지 여부 — 현행엔 동시수정 충돌 처리가 없다(updatedAt 서버 강제만). 제안: If-Match 헤더 또는 body row_version 필드로 409 처리.
