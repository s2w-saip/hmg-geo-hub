검수 콘솔

app/api/v1/qa/ 패키지. router.py 가 APIRouter(prefix="/v1/qa", tags=["qa"], dependencies=[Depends(require_qa_reviewer)]) 하나를 만들고 하위 라우터 4개를 include 한다: answers.py(QA-1 목록·진행률·이웃·필터옵션 + QA-3 상세), reviews.py(QA-2 판정·락·세션·deltas), notes.py(QA-2 노트 목록·카운트·내보내기·단건 수정/삭제), 그리고 공통 deps.py·filters.py·coords.py·sql.py·locks.py. 경로 선언 순서 규칙: 정적 경로(/answers/progress, /notes/counts, /notes/export)를 경로 변수 경로보다 먼저 등록하고 job_id·note_id·session_id 는 uuid 타입으로 선언해 정적 세그먼트와 충돌하지 않게 한다. 읽기 핸들러는 api_ro 풀, 쓰기 핸들러는 api_rw 풀을 Depends 로 주입한다(PgBouncer transaction 모드, prepared statement 캐시 끔).

검수 콘솔(qa) 모듈은 단위 2개(QA-1 목록, QA-2 판정·노트·락)에 상세 조회 1개(QA-3, 설계 리드 신설)를 더해 엔드포인트 20개로 묶었다. 현행 getReviewAnswerDetail(qa-review.ts:652, feature-trace 207행)을 맡은 단위가 없어서 QA-3 을 새로 두었다. 확인된 주요 모순은 여섯 가지다. (1) 시간 축이 단위마다 달랐다: QA-1 은 measured_at, QA-2 는 round_date 였고 measured_at(현행 qa-review.ts:241-242)으로 통일했다. (2) 인증: G-18(a) 로 이미 결정돼 있어 QA-1 의 열린 질문을 닫았고 require_qa_reviewer 하나로 정리했다. (3) QA-2 의 경로 /v1/qa/reviews/{job_id} 가 /reviews/notes 같은 정적 경로와 충돌해 리소스 계층을 다시 짰다. (4) api_rw 에는 rd 스키마 USAGE 가 없다(DB-v2.sql 권한 절 4항). 그래서 QA-2 의 트랜잭션 안 rd.job 존재 확인은 실패한다. api_ro 사전 확인으로 옮겼다. (5) job_qa_list_idx 는 measured_at DESC(= NULLS FIRST)인데 현행 정렬은 NULLS LAST 라 인덱스 정렬을 쓰지 못한다. DDL 교정을 제안했다. (6) sendBeacon 은 Authorization 헤더를 보낼 수 없어 JWT 체계에서 락 해제 경로가 끊긴다. D8 위반은 없다: 현행 unstable_cache 두 곳(qa-review.ts:476-482, 527-528)을 없애고 매 요청 계산으로 바꾼다. QA-1 이 제안한 ing.answer.n_mentions/n_citations 투영은 기각했다(현행 값은 행 수라 불일치 위험이 있다). 대신 뷰 확장 3건과 인덱스 교정 1건을 제안으로 올렸다. 10배 기준 위험은 목록·진행률이 medium, 나머지는 low 다.

단위 간 정리
  • [누락] 상세 조회를 맡은 단위가 없다. 현행 getReviewAnswerDetail(qa-review.ts:652, feature-trace 207행)은 QA-1·QA-2 어디에도 없다. QA-3: GET /v1/qa/answers/{job_id} 를 신설해 이 모듈에서 설계한다(doc §3.3). 단위 설계자 재검토 대상
  • [시간 축 모순] QA-1 은 from/to 를 measured_at 에, QA-2 는 round_date 에 걸었다. 현행은 목록·노트 모두 같은 answerPredicates 의 measured_at 이다(qa-review.ts:241-242, notePredicates:931). measured_at(KST 날짜 경계: measured_at >= (:from::date)::timestamp AT TIME ZONE 'Asia/Seoul', < (:to::date + 1) 같은 방식)으로 통일한다. 근거: QA 는 지표가 아닌 원시 색인이고 rd.job 은 비파티션이며 job_qa_list_idx 가 measured_at 축이다. DB-보정.md:141(PR-01 수집 기간 = rd.job.measured_at)과도 일관된다. 현행 ::date 는 DB 타임존 기준이라 경계가 최대 9시간 달라질 수 있어 대조 항목에 넣는다
  • [필터 모델 분기] QA-2 노트 목록이 brand 를 빼고(bgrp WHERE 금지를 이유로) reviewer 에 노트 작성자까지 OR 로 넣었다. q 는 노트 본문까지 검색하고 state 기본값을 unreviewed 로 두었다. 현행 notePredicates = answerPredicates + 노트 3축(qa-review.ts:930-937)이다. 따라서 노트도 QaFilter 전체(brand 포함, bgrp 가 아니라 coords 해석 경로)를 공유한다. reviewer 는 rv.reviewer_name 만, q 는 프롬프트 텍스트만, state 는 비면 무제한으로 되돌린다(값 보존)
  • [인증 모순] QA-1 은 인증 축을 열린 질문으로 두고 role 스코프 교집합 적용도 언급했다. QA-2 는 G-18(a) 를 적용했다. DECISIONS.md G-18 은 이미 채택(a)(QA = Supabase 계정 + is_qa_reviewer)이다. 모듈 전체가 require_qa_reviewer 하나만 쓰고, 스코프 교집합은 적용하지 않으며 dropped_filters=[] 로 둔다. 현행 이름+공용 비밀번호 HMAC 쿠키(lib/qa/auth.ts:1-40, 기본 비밀번호 하드코딩 포함)는 폐지한다
  • [경로 충돌] QA-2 의 /v1/qa/reviews/{job_id} 와 /v1/qa/reviews/notes, /deltas, /sessions 가 같은 세그먼트 자리를 두고 겹친다.   • [권한 경계 위반] QA-2 는 api_rw 쓰기 트랜잭션 안에서 SELECT 1 FROM rd.job 을 한다. 그런데 api_rw 는 app USAGE 만 있다(DB-v2.sql 권한 4항). 따라서 실행 시 permission denied 가 난다. api_ro 로 먼저 확인(assert_job_exists)하고 나서 api_rw 트랜잭션을 연다

쿼리 설계
1) 필터 전처리(주 쿼리 전 1회, 모두 소형 조회): brand[] 가 있으면 app.brand 로 brand_bit 조회 → (a) SELECT project_key FROM rd.dim_project WHERE site_brand_bit = ANY($bits) → project_key 배열, (b) SELECT DISTINCT prompt_key FROM rd.catalog_entry WHERE brand_bit = ANY($bits) → prompt_key 배열. country[]/engine[]/lang[] 은 각 dim 표에서 code→key 조회. 2) 목록 본쿼리(단일 SELECT, 모두 '= ANY(상수 배열)' 또는 불리언):
SELECT j.answer_key, j.job_id, j.measured_at, j.surface, j.engine_key, j.geo_key, dp.text AS prompt_text, dp.lang_key
FROM rd.job j
LEFT JOIN rd.dim_prompt dp ON dp.prompt_key = j.prompt_key
WHERE ($surface_filter IS NULL OR j.surface = ANY($surface_filter))
  AND ($geo_filter    IS NULL OR j.geo_key    = ANY($geo_filter))
  AND ($engine_filter  IS NULL OR j.engine_key = ANY($engine_filter))
  AND ($brand_filter   IS NULL OR (j.surface <> 1 AND j.project_key = ANY($brand_project_keys)) OR (j.surface = 1 AND j.prompt_key = ANY($brand_prompt_keys)))
  AND ($from IS NULL OR j.measured_at >= $from) AND ($to IS NULL OR j.measured_at < $to + interval '1 day')
  AND ($q IS NULL OR dp.text ILIKE '%'||$q||'%')
  AND (커서 술어: (j.measured_at, j.answer_key) 튜플비교, NULL 구간은 기존 qa-review.ts:293-301 분기 유지)
ORDER BY j.measured_at DESC NULLS LAST, j.answer_key DESC LIMIT $limit+1.
reviewer[]/state[]/has_notes 는 LEFT JOIN app.qa_answer_review rv ON rv.job_id=j.job_id 로 붙여 WHERE 에 추가(구 코드 answerPredicates 의 state OR 분기 그대로). no_mentions 는 NOT EXISTS(rd.v_answer_mention_raw). 3) 페이지 내 50개 job_id 로 배치 후속 조회 2개: 락(app.qa_answer_lock WHERE job_id = ANY($page_ids)), 노트수(app.qa_review_note GROUP BY job_id WHERE job_id = ANY($page_ids)), mention/citation 카운트(제안된 뷰 확장 사용 시 answer_key = ANY 등치, 미승인 시 상세 이동 전까지 0/미표시로 폴백 — open_questions). 4) progress: countProgress(filter) 는 위와 같은 WHERE 로 COUNT(*)/COUNT(rv.job_id)/COUNT(*) FILTER (WHERE rv.status='issue')/COUNT(*) FILTER (WHERE EXISTS notes). total(무필터)은 같은 쿼리를 필터 없이 별도 실행(D8: DB 캐시 불가 — 비고의 근사치 대안 참고). 5) filters: brand=SELECT brand_code FROM app.brand ORDER BY sort_order; country=SELECT code FROM rd.dim_country WHERE kind='iso' ORDER BY code; engine=SELECT code FROM rd.dim_engine ORDER BY code; lang=SELECT code FROM rd.dim_lang ORDER BY code; reviewer=SELECT DISTINCT reviewer_name FROM app.qa_answer_review ORDER BY reviewer_name. 6) neighbors: anchor = SELECT measured_at FROM rd.job WHERE job_id=$job_id; 이후 같은 WHERE(필터)+prev/next 부등호로 LIMIT 1 두 번(qa-review.ts:390-431 패턴 그대로, rd.job 기준으로 치환).

성능(10배)

(3) deltas data = {locks:[{job_id,session_id,reviewer_name,acquired_at,heartbeat_at}], reviews:[{job_id,status,reviewer_name}]}. (4) 세션 POST data = {session_id}. 쿼리 설계
읽기(예: GET /v1/qa/reviews/notes): rd.job j 를 surface+round_date 로 먼저 가지치기해 후보 answer_key 집합을 좁히고, app.qa_review_note n 을 job_id 등치로 조인(테이블이 인간 생성 데이터라 작음 — n 을 드라이버로 잡아도 무방). 스케치:
```sql
SELECT n.note_id, n.job_id, n.target_kind, n.target_key, n.target_label, n.severity, n.body,
       n.reviewer_name, n.created_at, n.resolved_at, n.resolved_by,
       dp.text AS prompt_text, j.surface, de.code AS engine, dc.code AS country
  FROM app.qa_review_note n
  JOIN rd.job j        ON j.job_id = n.job_id
  LEFT JOIN rd.dim_prompt dp ON dp.prompt_key = j.prompt_key
  LEFT JOIN rd.dim_engine de ON de.engine_key = j.engine_key
  LEFT JOIN rd.dim_country dc ON dc.geo_key   = j.geo_key
 WHERE j.surface = ANY($surfaces)                         -- rd.job PK 좌표 가지치기
   AND j.round_date BETWEEN $from AND $to
   AND ($engines IS NULL OR j.engine_key = ANY($engine_keys))
   AND ($langs   IS NULL OR j.lang_key   = ANY($lang_keys))
   AND ($countries IS NULL OR j.geo_key  = ANY($geo_keys))
   AND ($target_kinds IS NULL OR n.target_kind = ANY($target_kinds))
   AND ($severities   IS NULL OR n.severity    = ANY($severities))
   AND ($include_resolved OR n.resolved_at IS NULL)
   AND ($cursor IS NULL OR (n.created_at, n.note_id) < ($cursor_ts, $cursor_id))
 ORDER BY n.created_at DESC, n.note_id DESC
 LIMIT $limit + 1;
```
state/reviewer 필터는 app.qa_answer_review 를 job_id 로 추가 LEFT JOIN해 WHERE 에 status/reviewer_name 조건을 더한다. q 는 `n.body ILIKE '%'||$q||'%' OR dp.text ILIKE ...`(P1 예외, 소규모 테이블이라 순차 스캔 허용).

쓰기 절차:
1. **판정 저장 PUT /v1/qa/reviews/{job_id}**: 트랜잭션 시작 → `SET LOCAL app.actor_id = :user_id` → `INSERT INTO app.qa_answer_lock(job_id, session_id, reviewer_name) VALUES(...) ON CONFLICT (job_id) DO UPDATE SET session_id=EXCLUDED.session_id, reviewer_name=EXCLUDED.reviewer_name, acquired_at=now(), heartbeat_at=now() WHERE qa_answer_lock.session_id = EXCLUDED.session_id OR qa_answer_lock.heartbeat_at < now()-interval '180s' RETURNING *`(재확인, 실패 시 롤백 후 409) → `INSERT INTO app.qa_answer_review(job_id, flag_*, reviewer_id, reviewer_name, session_id) VALUES(...) ON CONFLICT (job_id) DO UPDATE SET flag_*=EXCLUDED.*, reviewer_id=EXCLUDED.reviewer_id, reviewer_name=EXCLUDED.reviewer_name, session_id=EXCLUDED.session_id, updated_at=now() RETURNING status` → COMMIT.
2. **락 POST/PATCH/DELETE**: 위와 동일한 ON CONFLICT 패턴(단문 자동커밋), DELETE 는 `WHERE job_id=$1 AND session_id=$2`(소유자만).
3. **노트 CRUD**: 단문 INSERT/UPDATE/DELETE, actor_id 세팅 후 실행. UPDATE 는 patch 필드만 SET(부분 갱신), resolved 토글 시 resolved_at/resolved_by 함께 설정.
4. **세션 생성/heartbeat**: INSERT INTO app.qa_review_session(user_id, reviewer_name, user_agent, ip_hash) / UPDATE ... SET last_seen_at=now().
job_id 는 rd.job 소속 여부를 쓰기 전 SELECT 1 FROM rd.job WHERE job_id=$1 로 확인(스키마 간 FK 없음 — A17 경계라 cross-schema FK 미설정, 애플리케이션 검증), 없으면 404.
